# OLEANDER Operational Brand Rule Encoding Extension

Status: `CANDIDATE EXTENSION / VISUAL-DESIGN`

Use when a brand identity already exists and must be translated from descriptive guidelines into repeatable, testable rules across web, print, packaging, decks, social, signage or other media.

## Core principle

`BRAND SOURCE AUTHORITY → ASSET / ROLE INVENTORY → ALLOWED / FORBIDDEN → CONTEXT RULE → EXAMPLE / COUNTEREXAMPLE → MULTI-MEDIA APPLICATION → ACTUAL READBACK → RELEASE BOUNDARY`.

A brand guideline is not complete because it names fonts, colors and a logo. It becomes operational when a designer can determine what is allowed, what is forbidden, under which context a rule changes, and how to verify a real artifact against it.

## Source-authority gate

Before encoding rules, resolve the Current brand authority:

- approved logo/wordmark/symbol masters;
- approved typography and language rules;
- approved color roles and reproduction specifications;
- approved imagery/photography/illustration direction;
- approved layout/composition behavior when formalized;
- motion/interaction rules if they are part of the identity;
- current naming/version status;
- rights/licensing boundaries for fonts, images and third-party assets.

Do not create missing brand rules merely to make the system feel complete. Mark unresolved areas as OPEN/HOLD.

## Rule object

For each material brand rule, prefer an explicit object such as:

`RULE ID → SUBJECT → PURPOSE → ALLOWED → FORBIDDEN → CONTEXT / EXCEPTION → MEASURABLE OR VISIBLE EVIDENCE → SOURCE AUTHORITY → STATUS`.

Examples of rule subjects include:

- logo clearspace / minimum-size behavior;
- wordmark-symbol combinations;
- typography role assignment;
- color semantic role;
- photography crop/lighting behavior;
- icon/pictogram family;
- layout anchor or alignment system;
- packaging/POP hierarchy;
- motion signature;
- co-branding or partner-mark relationship.

The rule may be visual, semantic or technical. Not every rule needs a numeric value; every rule does need an observable consequence.

## Allowed + forbidden pair

Where misuse is plausible, pair the intended use with a concrete failure example.

A prohibition such as “do not distort the logo” is stronger when the system shows what counts as distortion: nonuniform scale, rotation, outline, effect, recolor, altered lockup, minimum-size failure or contrast failure as applicable.

Do not turn the manual into a gallery of bad examples. Use counterexamples only where they clarify a real boundary.

## Context-dependent rules

Brand rules may differ by medium, scale, background, language or functional state. Encode those conditions explicitly rather than forcing one universal treatment.

Examples:

- display typography may differ from UI/body typography;
- dark/light logo variants may depend on background and contrast;
- print spot/process color may differ from screen values while preserving the same brand role;
- compact lockups may be valid below a scale threshold;
- bilingual layouts may require script-specific optical adjustments;
- product UI semantic states may use accent colors differently from marketing compositions.

`CONSISTENCY ≠ IDENTICAL TREATMENT IN EVERY CONTEXT`.

## Brand tokens and assets

When the project has a Current token/asset registry, bind rules to stable asset/token identities. Do not duplicate approved values into multiple competing guideline files.

Keep:

- source master identity;
- derivative/export identities;
- approved variants;
- asset version;
- usage context;
- known replacement/superseded status.

A screenshot of the logo or color swatch is evidence of appearance, not a replacement for the authoritative editable/vector/token source.

## Manual / specimen gate

Operational rules should be shown at the point of use through appropriate specimens, drawings or matrices rather than left as prose only.

As applicable, show:

- clearspace geometry;
- minimum-size specimens;
- wordmark/symbol lockups;
- typography character/weight specimens;
- real color swatches and semantic roles;
- image crop/sequence examples;
- icon family samples;
- layout anchors/grids;
- media-specific variants;
- allowed and disallowed combinations.

The specimen must remain legible at the actual manual/output size.

## Multi-media stress test

Before calling a rule operational, apply it to more than one realistic artifact class when the identity is expected to span media. For example:

- responsive web/header;
- retail POP or packaging panel;
- presentation/board;
- social or campaign crop;
- small-size application such as favicon/icon/label;
- print and screen color contexts.

A rule that works only in the hero mockup is not yet a reusable identity rule.

## Change control

When a brand rule changes:

- name the affected rule/asset IDs;
- identify downstream artifacts that depend on it;
- preserve the previous version as superseded provenance where required;
- do not silently update third-party or already-approved deliverables;
- rerun relevant visual and delivery checks.

## Failure modes

Reject or revise when:

- a brand “system” is only a moodboard or adjective list;
- specific colors/fonts/assets appear without authority or rights status;
- rules exist only as prose with no usable specimen where one is required;
- allowed use is shown but foreseeable misuse boundaries are undefined;
- the same rule is duplicated with conflicting values across documents;
- logo/image geometry is redrawn from a raster reference instead of the Current master;
- a third-party brand's exact fonts, colors, lockups, templates or assets are copied as OLEANDER defaults;
- a brand manual is aesthetically polished but operationally ambiguous;
- one successful mockup is used as proof that the identity scales across media.

## Boundary

This extension does not define an OLEANDER house style and does not import any external brand identity. Brand-specific values, assets, layout signatures and proprietary rules remain with the brand that owns them.

External study provenance: official `resend/design-skills` brand Skill. The reviewed repository exposed no root license, so only independently worded high-level operational-rule patterns are retained; Resend-specific fonts, color values, logo assets, gradients, effects, dimensions and layout patterns are explicitly excluded.
