# OLEANDER Presentation Argument & Evidence Extension

Status: `CANDIDATE EXTENSION / STORY-AND-BOARD`

Use for live presentations, review decks, pitches, competition decks, teaching decks and project roadshows where the audience must understand a sequence of claims in limited time.

## Core distinction

`REPORT / DOCUMENT ≠ LIVE PRESENTATION`.

A report can preserve depth for reading. A live presentation must control attention over time. Do not convert a report into slides by reducing font size or distributing paragraphs across pages.

## Audience contract

Before slide authoring, resolve only the audience facts that materially affect the deck:

- who must understand or decide;
- their likely baseline knowledge;
- the central conclusion/decision the deck needs to establish;
- time available;
- what action, response or judgment should follow;
- which evidence is essential in-room versus available for later depth.

Do not optimize a deck for the presenter's source-document order when the audience needs a different explanatory sequence.

## Claim–Proof slide contract

For every material slide, define:

`AUDIENCE QUESTION → PRIMARY CLAIM / DECISION → PRIMARY PROOF → VISUAL RELATION → SPOKEN CONTEXT → NEXT NARRATIVE STEP`.

The headline may state a claim when that improves clarity. A topic label such as `Analysis`, `Results` or `Strategy` is not itself a claim.

The primary proof can be a real image, drawing, model, diagram, chart, comparison, artifact, quotation or other approved evidence. Decorative graphics cannot stand in for proof.

One slide may contain several supporting details, but it should have one dominant takeaway at live-reading speed.

## Shown versus spoken

Use the slide for what must be seen together:

- the claim/decision;
- the spatial, visual, quantitative or comparative proof;
- the minimum labels/captions needed to interpret it;
- a next action when the slide is a decision/closing point.

Use speech/notes for:

- elaboration;
- caveats that do not need permanent visual competition;
- examples or transitions;
- interpretive explanation already visible in the proof.

Do not place the presenter's full narration on the slide unless the deliverable is explicitly reading-first/asynchronous.

## Density and decomposition

When a slide becomes dense, identify what relation is being compressed before shrinking type.

Possible decompositions:

- one claim → one proof;
- overview → focused detail;
- before → after;
- object → explanation;
- question → evidence → decision;
- comparison A → comparison B → synthesis;
- process → critical transition → result.

If several independent claims need independent evidence, use multiple slides or an explicitly reading-first layout. `MORE CONTENT FITS ≠ BETTER PRESENTATION`.

## Structure instead of bullets

Do not default every 3–6 item set to a bullet list. Choose a relation structure that matches the content:

- ordered sequence / process;
- comparison;
- hierarchy;
- cause → effect;
- object → annotation;
- problem → intervention → consequence;
- evidence set → synthesis;
- timeline;
- matrix;
- paired artifact + rationale;
- key number / quantitative proof.

Bullets remain valid for genuinely parallel short items. They are not the default substitute for unmade diagrams or unresolved information architecture.

## Essential / depth separation

For time-variable presentations classify material as:

- `ESSENTIAL` — required for the central argument/decision;
- `SUPPORT` — useful when time allows or when a question needs proof;
- `APPENDIX / DEPTH` — detailed evidence retained for async review or Q&A.

Do not delete valid evidence merely to shorten the live path. Re-route depth to appendix/support while preserving no-loss traceability.

## Parallel-section consistency

When two or more cases/options/phases are meant to be compared, preserve comparable narrative roles across sections. The slide counts need not be identical, but the audience should be able to recognize corresponding questions/proof types.

Example:

`CONTEXT → KEY CONDITION → DESIGN RESPONSE → EXPERIENCE / ARTIFACT → PROOF`

repeated across two options with project-specific content.

Do not force identical templates when the evidence types differ materially.

## Progressive disclosure boundary

Progressive reveal is useful only when it controls a real reading or causal sequence. It must not conceal evidence needed to interpret the visible claim, block user-controlled navigation or make the exported/static state misleading.

Route temporal behavior to `oleander-motion`. The slide must retain an equivalent understandable state under Reduced Motion/static capture when required.

## Review

At actual playback size, check:

- can the primary claim be understood quickly;
- is the primary proof visually dominant enough to support it;
- does the proof actually support the claim;
- is the slide topic-centered or decision-centered;
- is presenter script competing with visible evidence;
- should dense content be decomposed rather than reduced;
- is evidence depth preserved somewhere when removed from the live path;
- do comparable sections remain cognitively comparable;
- does the next slide follow logically rather than merely stylistically.

## Required output

For formal deck work, return or persist:

- audience / decision contract;
- narrative sequence;
- per-slide Claim–Proof map for material pages;
- essential/support/appendix classification when timing matters;
- source/evidence binding;
- slide visual role;
- actual target-size readback;
- unresolved evidence or presentation HOLD.

## Boundary

This extension does not require every slide to use a sentence headline, a single image, a specific visual preset or a fixed content count. It preserves OLEANDER no-loss and evidence authority while making the live reading path deliberate.
