**Status:** ACTIVE / CURRENT ARCHITECTURE CONTROL VIEW

**Effective:** 2026-09-15

**Scope:** OLEANDER system architecture, runtime layers, canonical contracts, professional processes, state families, reviews/gates and execution owners.
**Authority position:** subordinate to `00-governance/README.md`, Current Project / Source Authority and `00-governance/complex-project-master-runtime-v1.0.md`. ## 1｜Canonical counting rule

When OLEANDER is discussed at system level, use the following count and terminology exactly:

```text
OLEANDER DESIGN OPERATING SYSTEM
= 1 CURRENT SYSTEM ARCHITECTURE

orchestrated by
= 1 COMPLEX PROJECT MASTER RUNTIME

expanded operationally as
= 11 STABLE RUNTIME LAYERS (R-A ... R-K)

containing / invoking
= multiple canonical contracts, domain processes, reviews, gates,
  state families, schemas, Skills, capabilities, tools and artifacts.
```

Therefore:

- **OLEANDER currently has one Current system architecture.**
- `R-A ... R-K` are **11 Runtime Layers**, not eleven separate architectures.
- `DD-01 ... DD-12` are shared design-development **responsibility dimensions**, not architectures and not professional stages.
- Architecture `ADD-00 ... ADD-17` are one profession's authentic **professional stages**, not Runtime Layers and not a universal OLEANDER stage system.
- `KI*`, `OE*`, `DQ*`, interface maturity, evidence codes, Job State and Project/Design State are **state families**, not architectures.
- Artifact Review, PAP, High-Fidelity Built-Environment, statutory/technical/evidence checks and Post-Generation Review are **review/gate owners**, not architectures.
- Skills, capabilities and tools are **execution owners/resources**, not professional processes and not architectures.

If a future document uses “architecture” for a local subsystem, it must qualify the term, for example `Knowledge Architecture`, `Information Architecture`, `Software Architecture` or `Project-specific Spatial Architecture`. An unqualified question such as **“OLEANDER 有几个架构？”** refers to the single Current OLEANDER system architecture defined here.


This diagram is intentionally simplified. The machine carrier records additional direct edges where a layer consumes several upstream owners.

`R-K → R-B` is a **bounded feedback edge**, not a dependency edge and not automatic knowledge promotion.

### 16.1 Reopen principle

A material change invalidates **only consumers of the changed relation at affected scope**.

```text
CHANGE
→ identify controlling owner
→ classify impact
→ mark consuming state STALE / REOPEN_REQUIRED
→ preserve unrelated valid state
→ rerun smallest sufficient upstream/downstream scope
→ actual readback
→ close or continue propagation
```

### 16.2 Minimum reopen routing

| Changed owner | Minimum affected targets when the changed relation is consumed |
|---|---|
| `R-A Authority` | every downstream packet/receipt/artifact that binds the changed authority snapshot |
| `R-B Knowledge` | DI/DD/professional decisions that cite or mount the changed knowledge input |
| `R-C Design Intelligence` | DD scope, affected professional processes, interfaces, execution/readback and Promotion claim |
| `R-D Shared DD` | affected professional stages, design-bearing artifacts, design readback, integration interfaces and Promotion |
| `R-E Professional Process` | consuming interfaces, capability requirements, native artifacts, professional/design review and Promotion |
| `R-F Integration` | consuming coordinated artifacts, integration readback, dependent review and Promotion |
| `R-G Capability/Tool route` | native execution/readback only where the route or output semantics materially change |
| `R-H Native Artifact` | actual readback + every review/receipt consuming the changed artifact; reopen D/E/F only if their design/professional relation changed |
| `R-I Review` | repair owner identified by the failed review + Promotion eligibility |
| `R-J Promotion/Sync` | authority/sync state; upstream design evidence remains valid unless the failure reveals a substantive contradiction |
| `R-K Learning` | no automatic upstream reopen; creates a bounded knowledge candidate for validation |

The runtime must not use whole-system invalidation when the dependency blast radius is known and bounded.

|---|---|---|---|---|
| schema/reference validity | **DECIDE** | observe | observe | N/A |
| dependency stale/reopen detection | **DECIDE within encoded rules** | challenge if semantics wrong | may override only by governance change | N/A |
| tool/capability availability | **DECIDE/observe** | observe | N/A | N/A |
| factual evidence sufficiency | assist / detect gaps | judge within competence | accept bounded project use | may govern where legally applicable |
| professional stage PASS | may validate required fields | **JUDGE** | accept/reject for project progression | may govern regulated scope |
| Design KEEP / DQ3-DQ5 | **FORBIDDEN TO SELF-AWARD** | **JUDGE** | approve project use/promotion | N/A unless regulated decision involved |
| Integration PASS | validate interface state | **joint/integration judgment** | accept project state | may govern regulated interface |
| Human Promotion | report eligibility only | recommend | **DECIDE** | does not substitute for project promotion |
| statutory/code approval | **FORBIDDEN** | cannot self-grant unless legally authorized | **FORBIDDEN** | **DECIDE where applicable** |

Hard boundary:

```text
MACHINE VALID
≠ PROFESSIONAL PASS
≠ DESIGN KEEP
≠ HUMAN PROMOTION
≠ STATUTORY APPROVAL
```

## 20｜Failure, Containment and Recovery

Failure handling must preserve still-valid work.

Canonical recovery sequence:

```text
DETECT FAILURE / CONTRADICTION
→ identify owner and blast radius
→ stop unsafe or duplicate mutation
→ preserve last verified state
→ mark affected dependency STALE / REOPEN_REQUIRED / HOLD
→ choose smallest valid recovery action
→ re-execute or reconcile
→ actual readback
→ rerun only affected reviews/receipts
→ restore RUNNABLE or READY_FOR_HUMAN_DECISION when justified
```

### 20.1 Failure classes

| Failure class | Default control action |
|---|---|
| authority conflict | `HOLD`; refresh Current authority; no parallel Current |
| stale dependency | `RECONCILIATION_REQUIRED`; reopen affected consumers |
| tool/runtime unavailable | choose allowed fallback owner/tool if semantics remain equivalent; otherwise `HOLD` |
| uncertain remote mutation | verify postcondition before retry; forbid blind duplicate side effect |
| native artifact failure | preserve prior verified artifact; repair/re-execute bounded scope |
| review failure | route to the owner of the failed relation; do not falsify still-valid evidence |
| integration failure | preserve local discipline evidence; block only integrated claim |
| persistence/sync failure | preserve design/professional evidence; block Promotion/sync claim as applicable |
| external authority missing | continue only inside declared claim ceiling; `HOLD` only where the decision genuinely depends on it |

### 20.2 Degraded operation

A provider/platform outage does not automatically invalidate local design state. The runtime may continue only when:

1. the required Current authority snapshot is already verified and not stale;
2. the unavailable surface is not the only legal write/readback authority for the next action;
3. no required cross-platform synchronization claim is being made;
4. all deferred writes/readbacks remain explicit blockers before Promotion where required.

## 21｜Architecture Evolution and Compatibility

OLEANDER architecture changes are classified before adoption.

| Change class | Meaning | Required action |
|---|---|---|
| `DOC_CLARIFICATION` | wording/diagram clarification with no semantic owner/state change | no receipt invalidation |
| `BACKWARD_COMPATIBLE_EXTENSION` | adds optional/triggered fields or new bounded owner behavior | update affected validators/adapters; existing valid state may remain current |
| `SEMANTIC_OWNER_CHANGE` | responsibility moves between canonical owners | reread affected authority; stale dependent packets/receipts |
| `STATE_CONTRACT_CHANGE` | state meanings/allowed transitions change | migrate/validate affected carriers; old states cannot be silently reinterpreted |
| `SCHEMA_BREAKING_CHANGE` | machine carrier no longer backward compatible | explicit migration + versioned parser/validator + affected readback |
| `PROFESSIONAL_PROCESS_REVISION` | authentic domain stage semantics change | reopen only projects/stages consuming the changed professional contract |
| `AUTHORITY_REPLACEMENT` | Current owner/carrier is superseded | explicit supersession, pointer update, dependent authority refresh and readback |

Compatibility invariants:

```text
OLD RECEIPT IS NOT SILENTLY REINTERPRETED
NEW FIELD DOES NOT AUTO-UPGRADE OLD EVIDENCE
RENAMING DOES NOT CREATE A NEW LOGICAL OBJECT
MIGRATION PRESERVES PROVENANCE
BREAKING CHANGE REQUIRES EXPLICIT AFFECTED-SCOPE REVALIDATION
```

The architecture control graph records its own version and compatible predecessor so runtime code can reject an unsupported future control contract rather than guessing.

```text
        ?

        ?
R-J Persistence / Promotion / Synchronization
        ?

```

### 22.1 Existing canonical owners compiled here

| Concern | Current owner |
|---|---|
| canonical filename / lifecycle / active-frontier / location rules | `00-governance/naming-status.md` |

### 22.2 Logical artifact model

```text
ONE LOGICAL ARTIFACT
? ONE artifact_id
? ONE Current revision
? N representations
? N locations only when justified

```

Canonical representation roles remain `SOURCE / NATIVE / CANONICAL / PREVIEW / PACKAGE`. Authority direction is one-way unless an explicit owner contract says otherwise: `SOURCE / NATIVE / CANONICAL ? DERIVED / PREVIEW / PACKAGE`.

A PNG, screenshot, render or flattened PDF cannot silently replace its editable/native authority.

### 22.3 Retained artifact identity and lifecycle

Every retained `CANDIDATE` or authority-bearing artifact must resolve `artifact_id / logical_object_id / project_or_scope_id / semantic_role / revision / lifecycle_state / authority_state / representation_role / native_or_editable_state / current_flag / source_or_parent_ref / supersedes-or-superseded_by / producer_owner / current_location_ref / hash-byte_size when material / dependencies / derived_from / readback_ref / persistence_state when triggered / sync_state when triggered / timestamps`.

Canonical lifecycle remains:

```text
WORKING / TEMP
? CANDIDATE
? CURRENT | SUPPORT | PROVENANCE | SUPERSEDED | REJECTED | DELETE_CANDIDATE
```

`EXPLORE/TEMP` may use lighter local identity, but cannot claim authority and cannot persist indefinitely without an exit disposition.

### 22.4 Material file operations

| Operation | Minimum control |
|---|---|
| `CREATE` | resolve owner + destination + lifecycle; do not create parallel Current |
| `EDIT` | verify current revision, mutation authority and dependencies; edit native/editable source when required |
| `DERIVE / EXPORT` | preserve upstream relation; assign representation role; do not reverse authority |
| `RENAME` | preserve `artifact_id`; update authority-bearing pointers/manifest |
| `MOVE` | preserve `artifact_id`; verify location integrity and Current pointers |
| `COPY` | declare a real reason; copy does not create new semantic authority |
| `SUPERSEDE` | create successor relation; demote predecessor in the same closure transaction |
| `ARCHIVE` | preserve provenance + retrieval path; archived object does not remain Current |
| `DELETE` | require explicit deletion authority, dependency check and recoverability/provenance decision; never infer from age alone |
| `PACKAGE` | manifest identities/checksums; package does not replace missing native source |
| `SYNC` | write + target-platform readback; upload/commit alone is not synchronized |

Physical folders remain shallow and role-oriented (`native / canonical / preview / package / checksums / receipts`). Project hierarchy, design reasoning and authority stay in stable IDs, registries, manifests, receipts and version control.

Location integrity is mandatory: `CURRENT IDENTITY + CURRENT GOVERNANCE + CURRENT LOCATION = REQUIRED FOR LIVE MUTATION`.

### 22.5 Dependency, persistence and observability

A file mutation is classified by semantic impact, not byte change alone:

```text
artifact mutation
? identify consumers
? NON_MATERIAL / LOCAL_MATERIAL / INTERFACE_MATERIAL / COUPLED_SYSTEM / PROMOTION_BREAKING
? stale only affected receipts / derivatives / interfaces
? regenerate / reread / re-review bounded scope
```

When PAP is triggered: `inventory ? local byte identity ? durable provider copy ? stable provider object ID ? independent retrieval ? SHA/size/open verification ? manifest ? cross-system readback`.

For any material artifact the runtime should answer: logical artifact identity, Current revision, representation role, editable/native authority, dependencies, derivation lineage, readback state, recoverability, location/pointer drift and next allowed file operation.

Hard invariants:

```text
FILENAME ? IDENTITY
RECENCY ? CURRENT
COPY ? NEW LOGICAL OBJECT
PREVIEW ? NATIVE AUTHORITY
PACKAGE ? SOURCE AUTHORITY
HASH ? VALIDITY
UPLOAD ? PERSISTENCE PASS
COMMIT ? SYNCED
ARCHIVE ? CURRENT
DELETE ? SUPERSEDE
ONE LOGICAL ARTIFACT ? ONE CURRENT REVISION ? N REPRESENTATIONS
SUCCESSOR ADOPTION ? PREDECESSOR CLOSURE IN THE SAME CONTROL TRANSACTION
```

OLEANDER already has a real Reader runtime. v2.1 makes it explicit in the architecture control view instead of leaving it as an implementation detail.

- the existing Notion `Knowledge Reader` surface over the canonical Notes registry;
- `00-governance/runtime/OLEANDER_REFERENCE_MATERIALIZATION_GATE_v1.0.md`.

### 23.1 Reader authority position

```text
NOTION CURRENT ROOT AUTHORITY + LIVE REGISTRIES
        ?
Canonical Knowledge Runtime
        ?
D1 manifest / chunks / lineage + Vectorize derivative index
        ?
Authority-aware search / Knowledge Pack
        ?
Knowledge Reader
        ?
lazy live-detail / relation / framework readback
        ?
Design Intelligence / task-scoped consumption
```

The Reader is a read/readback surface, not a second authority:

`READER ? KNOWLEDGE AUTHORITY / D1 ? CANONICAL KNOWLEDGE STORE / VECTOR HIT ? TRUSTED KNOWLEDGE / SEARCH RESULT ? OE / READABLE ? CONTENT COMPLETE / READABLE ? KI VERIFIED`.

### 23.2 AI file/source handling chain

```text
SOURCE LOCATOR / FILE REFERENCE
? resolve source identity + authority + requested operation
? choose minimum sufficient access route
? LIST/SEARCH when enough
? FIND/READ when text/structure is enough
? MATERIALIZE exact bytes only when local binary processing is required
? PARSE/RENDER with format-appropriate runtime
? preserve page/sheet/frame/object coordinates when material
? bind extracted content to source + revision/hash
? task-scoped interpretation
? authorized edit/derive only when requested and permitted
? ACTUAL READBACK
? persistence/sync only when triggered
```

The system must not materialize every file merely because it can, and it must not substitute a snippet/preview when full body or exact bytes are required.

### 23.3 Read-depth contract

`LIST / SEARCH / FIND / READ / MATERIALIZE / PARSE_RENDER / READBACK` are distinct operations. Explicit full-body review requires source-set enumeration and coverage accounting. Chapter/section work reads the whole relevant contiguous range. Incomplete or garbled parsed text escalates to actual page/image/bytes instead of inventing content. `READ COMPLETE` requires every declared source/range in scope to be read, not merely searched.

### 23.4 Source-surface routing

| Source surface | Default AI action | Escalate to bytes when |
|---|---|---|
| conversation attachment | parsed search/read first | editing, deterministic rendering, binary analysis or exact local operation requires bytes |
| persistent file library | semantic search/read first | local processing needs actual bytes |
| Notion canonical knowledge | Reader/Knowledge Pack + live detail readback | original binary or exact export is required |
| connected Drive/Dropbox/Box/OneDrive/SharePoint | connector-native list/read first | local processing requires materialized copy |
| Git/repository file | exact tracked file/revision read | native program/tool needs local binary access |
| public source | web/browser content read first | exact original file/reference is needed for binary processing/reconstruction |
| generated/native artifact | native source remains authority | derivative/export/readback needs another representation |

### 23.5 Reader task binding and mutation firewall

Reader knowledge and project execution meet only through `Reader canonical object + exact Canonical ID + current task_id + matching current Execution Receipt`. Without that binding, execution-owner state remains `NOT_HYDRATED / CURRENT_EXECUTION_CONTEXT_NOT_BOUND`; it is not inferred from title/domain/method.

```text
CAN READ ? CAN EDIT
CAN MATERIALIZE ? CAN OVERWRITE SOURCE
CAN DERIVE ? CAN PROMOTE
CAN UPDATE DERIVATIVE INDEX ? CAN CHANGE CANONICAL KNOWLEDGE
```

Before mutation, AI resolves `target identity / current revision / write authority / expected precondition / intended delta / dependent consumers / preservation-or-rollback path / required readback`. Uncertain remote writes require postcondition verification before retry.

Consequential reads expose source/locator, source surface, canonical-vs-derivative, revision/hash, access operation, coverage state, materialization state, parser/renderer, readback state, truncation/unknown blocks, stale-during-read, claim ceiling, bound task and next action. Partial/stale/timeout states fail closed rather than appearing as authoritative empty results.

## 24 ? Controlled Evolution Plane

OLEANDER is a **living, evolvable operating system**, but evolution is governed. Machine carrier for each proposed evolution: `00-governance/runtime/OLEANDER_EVOLUTION_CANDIDATE_CONTRACT_v1.0.json`. It learns from verified execution traces, failures, repairs, project outcomes, counterexamples and human steering; those signals become bounded candidates, not direct Current mutations.

### 24.1 Evolution loop

```text
RUN PROJECT / READBACK / REVIEW
? capture trace + failure + repair + counterexample + human steering
? G9 bounded lesson candidate
? classify evolution target
? freeze Current baseline + authority fingerprint
? build/reuse eval set from real cases + adversarial/counterexample cases
? generate isolated candidate variants
? run target-specific tests / project replay / regression / anti-pollution gates
? compare candidate against baseline on quality + reliability + cost + no-loss + authority invariants
? independent review
? CANDIDATE PR / migration plan
? human promotion decision
? bounded migration
? actual runtime/project readback
? regression monitoring
? retain rollback + provenance
```

A candidate may not mutate the Current runtime used by the same evaluation run.

### 24.2 Evolvable and protected surfaces

| Surface | Evolution | Minimum gate |
|---|---:|---|
| Skills / capability routing | yes | eval + regression + semantic-purpose preservation + project replay |
| tool descriptions / adapters | yes | contract tests + side-effect safety + readback + fallback tests |
| Reader/search/chunking/ranking | yes | retrieval benchmark + authority separation + stale/readback tests |
| file-handling/materialization routes | yes | byte identity + mutation safety + recovery/readback tests |
| validators / schemas | yes | fixture migration + compatibility analysis + false-pass/false-fail review |
| knowledge methods / reusable procedures | yes | Content/KI/OE + evidence + bounded transfer validation |
| professional-domain process definitions | yes, slowly | professional evidence + project replay + independent domain review + migration |
| architecture control graph | yes, slowly | full governance regression + dependency/reopen analysis + migration + human promotion |
| Current Authority identity | **not autonomously** | explicit governance/human authority change |
| active user constraints | **not autonomously** | only later explicit user instruction may change/revoke |
| human Design KEEP / Promotion right | **not autonomously** | never transferred to machine evolution |
| statutory/licensed authority | **never** | external authority only |

### 24.3 Evolution states and comparison

Separate lifecycle:

`EV0_OBSERVED ? EV1_CANDIDATE ? EV2_EVAL_READY ? EV3_EVAL_PASSED ? EV4_INDEPENDENT_REVIEWED ? EV5_PROMOTION_READY ? EV6_CURRENT_ADOPTED ? EV7_MONITORED`, with `EVH_HOLD / EVR_REJECTED` exits.

Candidates must prove at least: semantic purpose preserved, authority boundaries preserved, NO COMPRESSION / NO LOSS preserved, known regressions fixed, old valid cases still pass, adversarial cases pass, quality/reliability improves, false-promotion risk does not rise, file/readback/recovery remains valid, cost/latency tradeoff is justified, and rollback exists.

`CANDIDATE VARIANT ? CURRENT / EVAL PASS ? HUMAN PROMOTION / PR MERGED ? PROJECT DESIGN PASS / CURRENT ADOPTED ? OLD RECEIPTS REINTERPRETED`.

### 24.4 Evolution ownership

`R-K` is the intake for bounded learning but is not a hidden super-authority:

```text
R-K learning candidate
? Evolution Plane
? target canonical owner
? isolated candidate
? eval + review
? human promotion
? versioned Current
```

Adopted evolution records previous/new version, changed owner/behavior, affected carriers, compatibility class, migration scope, regression set, rollback pointer and adoption readback.
