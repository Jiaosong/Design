# 3. Intent versus Need

The internal project proposition is:

`让广渡文化重新由地方主体共同生活、判断与维护。`

The source explicitly says this is an **internal reconstruction proposition** and must not be packaged as an agreed public commitment before local confirmation, inheritor review, benefit rules, rights/responsibilities and exit mechanisms are resolved.

Therefore the typed replay must not classify the proposition as a validated stakeholder Need.

Preferred representation:

```text
PROJECT INTENT / PROJECT CLAIM CANDIDATE
    ↓ informs investigation
NEED CANDIDATES
    ↓ require stakeholder/local validation
AGREED / BASELINED NEED only after valid confirmation
```

The five core relationship groups and five relationship questions can seed `NEED_CANDIDATE` analysis, but they are not automatically `AGREED NEED`.


This is not a second Need state machine; it records origin credibility separately from lifecycle state.

# 5. Node template contains Requirement candidates but not yet baselined Requirements

Every relationship node is expected to record:

`原有关系 → 关系断点 → 目标关系 → 设计动作 → 参与规则 → 证据与评价`.

The broader Relation Statement also expects:

- subject/action/context/boundary;
- relation/evidence state;
- validation condition;
- revision/opposition/withdrawal/exit mechanism.

These fields can produce future Requirements, Constraints, Claims and Assurance questions, but the template itself is not a Requirement.

Migration logic should be:

```text
NODE / RELATION STATEMENT
→ extract obligation candidates
→ classify source/origin
→ split Need / Requirement / Constraint / Claim
→ define acceptance/verification only where justified
→ keep unresolved items DRAFT / CAPTURED / NOT_EVALUATED
```

`P3/REQ-RP03 TEMPLATE_FIELD_OR_METHOD_EXPECTATION_CANNOT_SELF_PROMOTE_TO_PROJECT_REQUIREMENT_WITHOUT_PROJECT_AUTHORITY_AND_SUBJECT_SCOPE`.

# 6. Participation rule is Claim-acceptance logic, not proof of participation

The source states that stamping, watching, photographing or clicking alone cannot prove participation. Effective participation must alter visible content, common outcome, role, decision or downstream system, and must define who reviews, maintains, revises or withdraws.

This is stronger than a general narrative preference. It functions as a **bounded acceptance logic for a participation claim**.

It should not be misread as evidence that participation already occurred.

Preferred typed chain:

```text
PROJECT_CLAIM type = PARTICIPATION / USER_EXPERIENCE / OPERATIONAL_OUTCOME
→ acceptance logic = material change to content/outcome/role/decision/system + governance owner
→ evidence needed = observed/reported/operational evidence appropriate to claim
→ assurance/validation = OPEN until actual evidence exists
```

## Replay result

`CONFIRMED_WITH_CLAIM_ACCEPTANCE_DELTA`.

### Replay-derived rule

`P3/CLM-RP03 CLAIM_ACCEPTANCE_LOGIC_MAY_BE_DEFINED_BEFORE_EVIDENCE_EXISTS; ACCEPTANCE_CRITERIA_DO_NOT_ESTABLISH_THAT_THE_CLAIM_OCCURRED`.

This is important for participatory, service and experience projects where the design defines what would count as success before in-use evidence exists.

# 7. Public communication threshold is a promotion/claim constraint, not a design Requirement

The project may only be communicated as a reconstruction proposal/method case until items such as the following are resolved:

- village representatives/collective confirmation;
- inheritor teaching/review/authorization confirmation;
- actual project/team roles;
- image/copyright/portrait/minor permissions;
- cultural interpretation, operation and professional authority boundaries;
- opposition/revision/veto/exit rights;
- benefit/distribution principles;
- heritage/life/production/privacy/risk boundaries;
- key data/coordinates/ownership/traffic/cost verification;
- real Before/Action/Result/Follow-up impact evidence.

These are heterogeneous prerequisites. Treating them all as design Requirements would corrupt semantics.

Preferred routing:

- external/legal/right boundary → `CONSTRAINT`;
- stakeholder/authority confirmation → Need/authority validation prerequisite;
- missing fact → `UNKNOWN` until better classified;
- evidence requirement → Assurance/evidence obligation;
- public wording limit → `PROJECT_CLAIM / PROMOTION CONSTRAINT`;
- design-specific obligation, if later authorized → `REQUIREMENT`.

`local culture is actually being jointly lived, judged and maintained by local actors`.

That outcome requires product/system validation against Need/intended-use evidence, not merely artifact/requirement verification.
