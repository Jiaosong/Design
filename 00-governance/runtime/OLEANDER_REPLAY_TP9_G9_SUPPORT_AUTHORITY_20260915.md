# 5. Counterexample and boundary analysis

## Boundary A — Required promotion gate

A promotion contract may explicitly require `Support Gate S = PASS` before parent promotion.

Correct interpretation:

```text
S PASS
→ parent becomes promotion-eligible on that prerequisite
→ authorized promotion process still decides/promotes parent
```

Incorrect interpretation:

```text
S PASS
→ parent automatically promoted
```

Therefore the G9 rule separates **promotion prerequisite** from **promotion authority/event**.

## Boundary B — Support object is authoritative for its own scope

A derived validation report can be the authoritative record of `schema conformance for file X`, while remaining non-authoritative for `native source model` or `design quality`.

Therefore `SUPPORT` does not mean “untrusted”; it means its semantic responsibility is bounded.

## Boundary C — Parent and support responsibilities intentionally coincide

If governance explicitly declares the checked property and the support/check result to be the controlling authoritative state for that exact parent property, then the object is no longer merely a non-authoritative support signal for that property. Classification/authority contract must say so explicitly.

## Boundary D — Promotion can be automated

The promotion event may be machine-executed when authority policy allows it. The rule does not require a human click. It requires an explicit promotion contract/event distinct from the bounded PASS itself.
