# OLEANDER｜NO COMPRESSION / NO LOSS / RESTRUCTURE WITHOUT INFORMATION LOSS v1.0

Status: ACTIVE UPON MERGE / GLOBAL DEFAULT EXECUTION PRINCIPLE
Scope: ALL OLEANDER PROJECTS / WORKSTREAMS / VALIDATIONS / CASES / PRACTICE / PUBLIC DELIVERY / INTERNAL DESIGN PRODUCTION
Date: 2026-08-16
Owner: 刘旋 / OLEANDER

## 0｜Core decision

OLEANDER must never confuse execution closure with design quality:

- `Artifact existence ≠ Design quality`
- `Traceability ≠ Professional finish`
- `Evidence correctness ≠ Visual excellence`
- `Process PASS ≠ MAIN KEEP`
- `Machine PASS ≠ Design PASS`
- `Executed ≠ Validated`

The global editorial and design-architecture default is:

> **NO COMPRESSION / NO LOSS / RESTRUCTURE WITHOUT INFORMATION LOSS**

A project may become clearer, more hierarchical, more visually restrained, better sequenced, more selective in emphasis, or more legible. It may not become smaller by silently deleting established architecture, chapter levels, content systems, design outcomes, interaction systems, audience logic, technical proof, evidence chains, or other independently valid project objects merely to make a shorter page, deck, film, document, or website.

## 1｜Global scope

This principle applies by default to every OLEANDER project and execution surface, including but not limited to:

- Business / Culture / IP / Spatial projects;
- product / industrial design / CMF / brand / visual identity / spatial / architecture / service / experience / digital / interaction / research / cultural translation / motion / modeling work;
- P2 Projects, P3 Workstreams, P4 Validations, Case editing, Practice outputs and shared-system application;
- Web / portfolio / boards / PDFs / documents / slides / films / App / prototypes / physical/product packages / model reviews / technical packages / evidence packages / integration and final-editing work.

This is a **global preservation and restructuring rule**, not a fixed universal chapter template.

A project-specific architecture may contain 5, 7, 12, 20 or another justified number of independent layers. OLEANDER does **not** require every project to use the C04 12-layer structure or any other universal count. The rule is: once independently valid architecture and outcomes exist, they cannot be silently collapsed or deleted for brevity.

## 2｜No silent compression

Do not:

1. reduce established independent layers merely to shorten a narrative;
2. merge independently valid chapters/systems until their distinct design function disappears;
3. delete complete design logic because of webpage length, board count, deck length, film duration, visual simplicity, or a desire for a cleaner presentation;
4. reduce mature existing outcomes to a sentence, label, caption, matrix cell or subordinate note when the underlying design warrants independent public or technical visibility;
5. use a cross-system rule to replace an independently necessary design chapter or proof layer;
6. hide Technical / Evidence / Reality / Manufacturing / Construction / Validation proof so completely that the design no longer shows why or how it is credible;
7. delete existing project assets merely to create room for newly added content;
8. treat a validation subset, release subset, current sprint subset, or latest presentation package as the whole project universe;
9. treat weak current pixels as proof that the underlying concept/design object should disappear;
10. use `compression`, `brevity`, `page count`, `cleaner deck`, `simpler website`, `less text`, or `shorter film` as a sufficient CUT reason.

## 3｜Allowed restructuring

The following are allowed and encouraged when they improve the work **without information loss**:

- reorder;
- split one chapter into several stronger chapters;
- group related items while preserving their independent identities and retrievability;
- add new layers or new evidence;
- reweight visual hierarchy;
- reduce visual clutter;
- shorten repeated copy while preserving underlying design/evidence content;
- move secondary material from MAIN to SUPPORT or PROCESS when the design reason is explicit;
- create cross-system rules that operate horizontally while retaining necessary vertical chapters;
- replace weak pixels with stronger representations of the same concept;
- remove genuine duplication after confirming no unique information/design function is lost.

Visual restraint is compatible with complete content. **Clarity is achieved by hierarchy and editing, not by silent deletion.**

## 4｜Mandatory concept / pixel / evidence separation

Every relevant integration or pruning decision must distinguish at least:

- `CONCEPT STATE` — KEEP / CURRENTIZE / REVISE / COMPETE / HOLD / DROP;
- `PRESENTATION STATE` — MAIN / SUPPORT / PROCESS / REDRAW / NOT-YET-SHOWN;
- `TRUTH / EVIDENCE STATE` — according to the applicable project authority and evidence model.

Therefore:

- `CONCEPT KEEP ≠ PIXEL KEEP`;
- `PIXEL FAIL ≠ DESIGN DELETE`;
- `VALIDATION SUBSET ≠ WHOLE PROJECT`;
- `SOURCE / AUTHORITY ≠ DERIVED PRESENTATION`.

A weak visual can be `CONCEPT KEEP / PIXELS REDRAW`.
A technically validated artifact can still be `VISUAL REVISE`.
A beautiful render can still be `EVIDENCE HOLD`.
A complete package can still be `NOT MAIN`.

## 5｜Design quality and governance are two separate ledgers

### Design ledger

Determines `MAIN / SUPPORT / REVISE / REJECT / DROP` through finished-output review appropriate to the artifact. Typical criteria include:

- first read;
- composition / scale / proportion;
- hierarchy / rhythm;
- project specificity;
- experience completeness;
- audience value;
- product / physical / spatial credibility;
- digital interaction quality and retreatability where applicable;
- motion quality where applicable;
- cross-media consistency;
- professional finish;
- truth-boundary legibility.

### Governance / evidence ledger

Determines traceability, authority, persistence, synchronization, evidence level, field/reality state, validation state and Promotion eligibility using applicable OLEANDER systems.

Examples:
- owner receipt / run manifest;
- Source Authority;
- GitHub branch / commit / PR / CI;
- Drive or other durable persistence;
- SHA-256 / byte size / independent retrieval;
- Artifact Review / PAP;
- evidence / reality / field / rights / engineering / human gates.

**The governance ledger has no authority to promote weak design into MAIN.**
The design ledger has no authority to manufacture evidence, field truth, rights, engineering validity, manufacturing readiness or Promotion.

## 6｜CUT / DEMOTE contract

If an established object, chapter or system genuinely should leave MAIN or leave the project, the decision must be explicit:

- `DEMOTE TO SUPPORT`
- `DEMOTE TO PROCESS`
- `HOLD / OPEN`
- `CUT`

Each decision must record a concrete reason. Valid reasons may include:

- genuine redundancy with no unique design/evidence function;
- contradiction with current authority;
- genericity that harms project specificity;
- visual or design weakness that remains after a fair redraw/currentization opportunity;
- experience harm or user-value conflict;
- technical/physical infeasibility at the applicable maturity level;
- evidence/truth/rights/safety conflict;
- supersession by a demonstrably stronger object while preserving provenance.

Invalid reasons by themselves:

- “too long”;
- “too many pages”;
- “need a cleaner deck”;
- “website should be shorter”;
- “film should be simpler”;
- “compression”;
- “minimalism”.

## 7｜New-content rule

When new content or a new design system is introduced:

1. first test whether the current architecture should **expand**;
2. if needed, **restructure** relationships and hierarchy;
3. preserve existing independently valid outcomes;
4. only then consider explicit `DEMOTE / CUT` decisions with recorded design reasons.

Never delete previous design outcomes simply to create layout space for new work.

## 8｜Project-specific inheritance

Each project inherits this global principle automatically unless a later explicit OLEANDER governance decision supersedes it.

Project-specific files may define stricter local rules or concrete architectures. They must not weaken this global no-loss principle without an explicit governance-level exception and documented rationale.

Examples:
- C04 Qingjiang currently uses a 12-layer public architecture. That **12-layer count is C04-specific**, while the no-compression/no-loss rule is global.
- A Product/CMF project may use a different architecture such as research → hard points → form → CMF → prototype → validation → release. Its independently valid layers must likewise be preserved unless explicitly DEMOTED/CUT.
- A Brand/Identity project may have Strategy / Identity / Verbal / Visual / Motion / Application / Production / Rights layers; visual minimalism does not authorize deleting the underlying systems.

## 9｜Relationship to existing OLEANDER governance

This policy extends, rather than replaces:

- Governance v1.1.1 no-loss / no-pollution;
- Canonical Project Flow v0.3;
- Artifact Review System;
- Mandatory Post-Generation Review;
- Production Asset Persistence Gate;
- Cross-platform Sync Contract;
- project-specific Source Authority / Reality / Field / Rights / Engineering / Human gates.

It does not create a shortcut around any existing gate and does not itself prove design quality, validation, Promotion or Release.

## 10｜Default execution question

Before restructuring any OLEANDER project, ask:

> **Can this become clearer without becoming less?**

If yes: restructure.
If not: do not compress. Use hierarchy, sequencing, visual restraint, progressive disclosure, SUPPORT/PROCESS layers, or explicit justified DEMOTE/CUT decisions instead.
