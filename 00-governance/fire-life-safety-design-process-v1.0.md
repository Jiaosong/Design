# OLEANDER Fire / Life Safety Design Process v1.0

**Status:** CANDIDATE PROFESSIONAL DOMAIN PROCESS / CONTROLLED EVOLUTION INPUT  
**Domain:** Fire / Life Safety (FLS)  
**Authority position:** subordinate to `complex-project-master-runtime-v1.0.md`, `OLEANDER_CURRENT_ARCHITECTURE_MAP_v2.1`, `professional-domain-process-contract-v1.0.md`, Current Knowledge Authority, Shared Design Quality, Cross-Disciplinary Integration, the project jurisdiction/AHJ, responsible fire-safety professionals and applicable statutory/licensed authorities.  
**Professional basis:** ISO 23932-1:2018 (reviewed and confirmed current in 2024) for fire-safety-engineering principles where performance-based engineering is applicable; ISO 20710-1:2022 for active-fire-protection-system engineering interfaces; SFPE Handbook of Fire Protection Engineering, 6th edition (2026) as current professional reference. These sources do not replace project jurisdiction, adopted codes, AHJ decisions or responsible-professional authority.  
**Existing OLEANDER knowledge context:** `IDX-ARCH-STRUCT-SAFETY-005` remains the L4 life-safety routing owner; existing alarm, suppression, smoke-control, firestopping, emergency-lighting and other FLS objects remain their Knowledge/System owners. This process mounts and consumes them; it does not create a second Fire Safety knowledge tree.

---

## 1｜Why this process exists

Fire/life-safety work is not a code checklist, an egress-distance overlay or a collection of fire-system product pages. It must connect the project use and hazard, jurisdiction and authority route, fire-safety objectives, credible fire/evacuation scenarios, passive and active protection, human response, cross-disciplinary geometry and systems, implementation evidence, testing/commissioning, approval/acceptance boundaries and in-use management.

Canonical professional chain:

```text
JURISDICTION / AHJ / APPOINTMENT / PROJECT USE
→ OCCUPANCY / HAZARD / FIRE-SAFETY OBJECTIVES
→ COMPLIANCE ROUTE: PRESCRIPTIVE / PERFORMANCE-BASED / HYBRID
→ FIRE + EVACUATION STRATEGY
→ EGRESS / HUMAN-BEHAVIOUR / ACCESSIBILITY INTERFACES
→ PASSIVE FIRE PROTECTION
→ ACTIVE FIRE PROTECTION + SMOKE / CONTROL / POWER INTERFACES
→ CROSS-DISCIPLINARY COORDINATION
→ PERFORMANCE ANALYSIS / SCENARIOS WHEN APPLICABLE
→ DESIGN DOCUMENTATION / SUBMITTAL / CONSTRUCTION CONTROL
→ INSPECTION / FUNCTIONAL TEST / COMMISSIONING / AHJ-PROFESSIONAL CLOSE
→ IN-USE MANAGEMENT / MAINTENANCE / CHANGE / INCIDENT READBACK
```

Hard boundaries:

```text
CODE CHECKLIST ≠ FIRE/LIFE-SAFETY PROFESSIONAL PASS
PRESCRIPTIVE COMPLIANCE CLAIM ≠ PERFORMANCE-BASED ENGINEERING CLAIM
PERFORMANCE MODEL PASS ≠ STATUTORY APPROVAL
EVACUATION MODEL ≠ HUMAN FIELD TRUTH
FIRE ALARM COMMAND ≠ PHYSICAL END-DEVICE STATE
SPRINKLER DATASHEET ≠ INSTALLED SYSTEM PERFORMANCE
FIRESTOP PRODUCT REPORT ≠ ASSEMBLY / PENETRATION COMPLIANCE
STRUCTURAL FIRE MODEL ≠ WHOLE-BUILDING FIRE-SAFETY PASS
EMERGENCY LIGHTING PASS ≠ COMPLETE EGRESS / LIFE-SAFETY PASS
DISCIPLINE PASS ≠ R-F INTEGRATION PASS
FLS PROCESS PASS ≠ DESIGN KEEP ≠ PROJECT PROMOTION
```

## 2｜Professional-source alignment and stage identity

ISO 23932-1 provides general principles and linkages for fire-safety engineering, including performance-based design, implementation and fire-safety management. It explicitly coexists with prescriptive regulatory approaches. OLEANDER therefore does **not** force every project into performance-based FSE.

The first professional decision is the applicable authority/compliance route. OLEANDER uses these internal domain-native carriers:

```text
FLS-BASIS        Jurisdiction / AHJ / appointment / use / hazard / claim boundary
FLS-STRATEGY     Objectives / acceptance criteria / prescriptive-performance-hybrid route
FLS-EGRESS       Occupancy / evacuation / human response / accessible emergency use
FLS-PASSIVE      Compartmentation / fire resistance / openings / penetrations / external spread
FLS-ACTIVE       Detection / alarm / suppression / smoke / emergency power-control interfaces
FLS-COORD        Cross-disciplinary geometry / systems / interface coordination
FLS-ANALYSIS     Fire / smoke / structural-fire / evacuation / risk analysis when applicable
FLS-DELIVERY     Documentation / submittal / construction control / inspection / testing / commissioning
FLS-INUSE        Fire-safety management / maintenance / change / emergency planning / incident return
```

These identifiers are **OLEANDER internal carriers**, not ISO or SFPE official stage IDs and not universal project phases. Work may iterate or run concurrently. A material change can reopen only the affected scope.

## 3｜Trigger / applicability

Trigger FLS professional work whenever a material project claim depends on fire or life safety, including:

- occupancy/use/hazard classification or fire-safety objectives;
- means of escape / evacuation / refuge / emergency movement;
- fire compartmentation, fire-resistance strategy or opening protection;
- structural-fire-performance interface;
- external-wall/facade fire-spread interface;
- fire alarm, detection, suppression, smoke-control or emergency communication;
- fire-service access / firefighting facilities;
- emergency power/control/cause-and-effect interfaces;
- accessibility during emergency conditions;
- alternative solution / performance-based design;
- high-risk changes, refurbishment, phased occupation or temporary conditions;
- fire-safety management, inspection, testing, maintenance or material change in use.

Do not infer FLS completion because Architecture reserved an egress route, MEP drew fire systems, a simulation was run, or an AHJ meeting occurred.

---

## 4｜Authority / compliance-route contract

Every FLS invocation must resolve:

`JURISDICTION → ADOPTED LAW/CODE/STANDARD → AHJ / APPROVAL ROUTE → RESPONSIBLE PROFESSIONAL → APPOINTMENT SCOPE → PROJECT USE/HAZARD → COMPLIANCE ROUTE → REQUIRED SUBMITTAL / REVIEW / TEST / ACCEPTANCE`.

Allowed route classes:

- **PRESCRIPTIVE:** the project claim is demonstrated through applicable prescriptive provisions and required professional/AHJ evidence;
- **PERFORMANCE-BASED:** a performance-based route is accepted/allowed and is supported by explicit objectives, acceptance criteria, scenarios, methods, uncertainty and review;
- **HYBRID:** prescriptive and performance-based routes coexist by scope.

`PERFORMANCE-BASED CAPABILITY ≠ PERMISSION TO DEPART FROM CODE`.

No OLEANDER source may silently override the local jurisdiction/AHJ. International guidance is method/professional evidence unless adopted by the project authority route.

## 6｜Cross-cutting FLS control objects

### 6.1 Fire / Life Safety Basis & Authority Register

Record at minimum:

- jurisdiction / AHJ / reviewing body;
- project use, occupancy and operating states;
- fire/life-safety appointment and exclusions;
- prescriptive / performance / hybrid route by claim;
- responsible professional and approval responsibility;
- current code/source editions and applicability;
- unresolved interpretations / variances / alternative-solution questions;
- claim ceiling and `does_not_prove`.

### 6.2 Fire-Safety Objectives / Acceptance Register

For each material claim record:

`OBJECTIVE → PERSON / ASSET / OPERATION AFFECTED → HAZARD → ACCEPTANCE BASIS → METHOD / PRESCRIPTIVE PROVISION → EVIDENCE → REVIEW OWNER → STATUS → REOPEN TRIGGER`.

Performance criteria must be explicit enough to test; prescriptive provisions must be bound to actual applicability and version.

### 6.3 Fire / Evacuation Scenario Register

Where scenarios are used, preserve:

- ignition/fire location and fuel/hazard basis;
- occupancy/user state and time state;
- detection/notification assumptions;
- door/compartment/smoke-control states;
- suppression availability/failure states;
- evacuation/assisted-evacuation assumptions;
- fire-service assumptions;
- environmental/system failure combinations;
- evidence/source and uncertainty;
- acceptance criterion and rejected/critical scenarios.

A selected design scenario is not proof that untested scenarios are safe.

### 6.4 Compartment / Opening / Penetration Register

Track:

`BOUNDARY ID → REQUIRED FUNCTION → FIRE-RESISTANCE / SMOKE FUNCTION SOURCE → CONSTRUCTION → OPENINGS → DOORS/DAMPERS → PENETRATIONS/JOINTS → TEST/ASSESSMENT IDENTITY → INSTALLATION/QC → CHANGE STATUS`.

### 6.5 Cause-and-Effect / Fail-State Register

For active and controlled systems:

`EVENT / INPUT → DECISION LOGIC → COMMAND → PHYSICAL END STATE → FEEDBACK → FAILSAFE → MANUAL OVERRIDE → TEST METHOD → ACTUAL READBACK`.

A controller output or BMS indication is not proof that the physical end state occurred.

### 6.6 Fire-Safety Interface Register

At minimum address Architecture, Structure, MEP/Electrical, Envelope, Interior, Lighting, Accessibility, Vertical Transportation, Controls/BMS, Security, FM/Operations and Construction.

Actual interface maturity/disposition remains owned by R-F Cross-Disciplinary Integration.

## 7｜FLS-BASIS — Jurisdiction / Authority / Use / Hazard Basis

**Professional question:** What fire/life-safety claim is being made, under which jurisdiction and authority route, for what use/hazard and professional appointment?

Resolve jurisdiction/AHJ, use/occupancy, operating states, hazard profile, project/alteration condition, responsible professional, adopted sources, evidence gaps and claim ceiling.

**Native outputs:** FLS Basis & Authority Register; use/hazard matrix; approval-route map; current source register; open interpretation list.

**Does not prove:** code compliance, selected strategy, system design or approval.

---

## 8｜FLS-STRATEGY — Objectives / Compliance Route / Strategy

**Professional question:** Which fire-safety strategy and compliance route credibly address the project objectives and controlling hazards?

Develop:

- life-safety/property/operational/environment/heritage objectives as applicable;
- prescriptive/performance/hybrid route by issue;
- compartmentation and evacuation concepts;
- detection/suppression/smoke-control concepts;
- fire-service provisions;
- structural/envelope fire-performance interfaces;
- emergency control/power/communication intent;
- acceptance criteria and required analyses/reviews.

**Native outputs:** Fire & Life Safety Strategy; objectives/acceptance register; strategy plans/diagrams; analysis plan; authority questions.

**Does not prove:** detailed system design, numerical performance, approval or field implementation.

---

## 9｜FLS-EGRESS — Occupancy / Evacuation / Human Response

**Professional question:** Can the declared occupants, including people needing assistance or different emergency information, reach an appropriate place of safety under the applicable strategy and evidence ceiling?

Address applicable occupancy distribution, exit/route topology, capacity assumptions, travel/queuing interfaces, door/vertical circulation states, refuge/assistance, evacuation communication, phased/staged evacuation, after-hours/event states, accessibility and fire-service interaction.

**Native outputs:** egress/evacuation strategy plans; occupancy/state matrix; assisted-evacuation interface requirements; scenario/readback register.

**Does not prove:** formal egress compliance, real human behaviour, evacuation-time validity or AHJ acceptance.

---

## 10｜FLS-PASSIVE — Passive Fire Protection

**Professional question:** Are fire/smoke boundaries and fire-resistance functions defined as complete assemblies and coordinated through openings, penetrations, joints and interfaces?

Address compartmentation, structural fire protection, floors/walls/shafts, fire/smoke doors, dampers, penetrations, firestopping, joints, cavity/spandrel/perimeter conditions and external-fire-spread interfaces.

**Native outputs:** compartment/boundary plans; passive-fire schedule; opening/penetration register; assembly evidence matrix; details and inspection points.

**Does not prove:** installed conformity, product suitability outside tested/assessed configuration or authority acceptance.

---

## 11｜FLS-ACTIVE — Active Fire Protection / Smoke / Control

**Professional question:** Are triggered active systems, their performance basis, physical interfaces and fail states resolved at the current professional claim ceiling?

Address applicable detection/alarm, suppression/water supply, smoke control, emergency communication, emergency lighting interface, emergency/firefighter power, control logic, monitoring and firefighting facilities.

**Native outputs:** active-system performance requirements; system topology/interface diagrams; cause-and-effect matrix; fail-state register; commissioning/test requirements.

**Does not prove:** detailed design by other responsible disciplines, product approval, installed performance or functional test success.

---

## 12｜FLS-COORD — Cross-disciplinary Coordination

**Professional question:** Do geometry, systems, boundaries, controls, access and operational assumptions agree across all materially coupled domains?

Typical critical interfaces include:

- exit geometry × Structure/MEP/Interior;
- fire boundaries × doors/dampers/penetrations/facade;
- smoke strategy × Architecture/MEP/controls/power;
- suppression/detection × ceilings/lighting/equipment;
- firefighter access × site/vertical transport/security;
- accessibility × evacuation/refuge/communication;
- maintenance/testing × FM/operations.

**Native outputs:** FLS interface register; coordinated strategy/model overlays; unresolved critical conflicts; change-impact log.

**Boundary:** FLS may define and review fire-safety interface requirements; actual interface maturity/disposition remains R-F-owned.

---

## 13｜FLS-ANALYSIS — Performance / Scenario Analysis When Applicable

**Applicability:** triggered only where the compliance route or design uncertainty requires engineering analysis.

**Professional question:** Do the declared methods, scenarios, inputs, uncertainties and acceptance criteria support the bounded performance claim?

Possible analyses include fire dynamics, smoke movement, evacuation, structural fire response, suppression performance, reliability/risk and sensitivity/uncertainty analysis.

Record exact model/method/version, geometry/configuration, boundary conditions, source data, assumptions, scenarios, sensitivity, uncertainty, reviewer and what is not proven.

`MODEL PASS ≠ APPROVAL ≠ INSTALLED/FIELD TRUTH`.

---

## 14｜FLS-DELIVERY — Documentation / Construction / Inspection / Test / Close

**Professional question:** Has the accepted fire-safety intent survived documentation, procurement, installation, change and testing within the declared authority route?

Control:

- design documentation and fire strategy revisions;
- statutory/AHJ/professional submissions;
- specialist calculations/submittals;
- product/system identity and substitutions;
- shop drawings/interface details;
- inspection/test plans;
- installation nonconformities;
- cause-and-effect / integrated functional testing;
- commissioning/readback;
- as-built records and unresolved conditions.

**Native outputs:** submission package; review log; submittal/change register; inspection/test/commissioning evidence; as-built fire-safety record; closure/open-item register.

**Does not prove:** statutory approval unless actual authority evidence exists, or construction acceptance beyond the inspected/tested scope.

---

## 15｜FLS-INUSE — Management / Maintenance / Change / Incident Return

**Professional question:** Does the fire-safety strategy remain valid through occupation, maintenance and material change?

Address management procedures, impairment controls, inspection/testing/maintenance, evacuation planning/training, change of use/layout/occupancy, door/firestop/system modifications, temporary works, recurring faults, incidents/near misses and authority updates.

Operational evidence may reopen design claims and may create G9 candidates, but does not automatically become reusable universal knowledge.

**Native outputs:** fire-safety management requirements; inspection/maintenance basis; change triggers; incident/impairment readback; G9 candidate inputs.

## 16｜Professional review / assurance

Triggered assurance remains separated:

- FLS Professional Domain review;
- R-F Cross-Disciplinary Integration review;
- evidence/truth review;
- specialist engineering reviews;
- statutory/AHJ/licensed-professional review;
- construction inspection/testing/commissioning;
- Design Quality review.

No PASS substitutes for another triggered class.

A project FLS professional receipt must bind exact scope/configuration, current authority/source basis, native outputs/readback, open items, reviewer/decision owner and claim ceiling.

---

## 17｜Change / reopen contract

Material changes that may reopen affected FLS scope include:

- jurisdiction/AHJ/source edition or interpretation;
- project use/occupancy/hazard/load;
- building geometry, compartmentation, exits or vertical circulation;
- structural/envelope/passive-fire assembly;
- alarm/suppression/smoke/control/power architecture;
- product/system substitution or configuration;
- accessibility/assisted-evacuation basis;
- construction deviation;
- failed inspection/test/commissioning;
- operation/maintenance impairment;
- incident/near-miss evidence.

Reopen only affected consumers; preserve unrelated valid evidence.

---

## 18｜Completion boundary

A bounded FLS Professional Process PASS may state only that the declared professional scope has met its exact exit criteria and evidence ceiling.

It does not automatically prove:

- statutory/AHJ approval;
- licensed-professional sign-off outside the recorded scope;
- R-F Integration PASS;
- installed/field conformity outside readback evidence;
- all possible fire scenarios safe;
- Design KEEP;
- Current Knowledge promotion;
- Project Promotion.

`PROFESSIONAL PASS ≠ APPROVAL ≠ FIELD TRUTH ≠ DESIGN KEEP ≠ PROMOTION`.
