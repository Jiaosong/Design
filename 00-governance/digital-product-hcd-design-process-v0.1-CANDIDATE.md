# OLEANDER Digital Product / HCD Design Process v0.1 — CANDIDATE

**Status:** `CANDIDATE PROFESSIONAL DOMAIN PROCESS / R-E / NOT CURRENT / NO PROMOTION`

**Domain:** Digital Product / Human-Centred Design

**Process ID:** `OLEANDER-DIGITAL-PRODUCT-HCD-DESIGN-PROCESS`

**Authority position:** subordinate to the OLEANDER Master Runtime, Current Knowledge Architecture, `professional-domain-process-contract-v1.0.md`, Cross-Disciplinary Integration, applicable organisational/legal/accessibility/security authority, and responsible HCD/product practitioners.

**Purpose:** provide a domain-authentic HCD/product-development process from scope and research authority through context-of-use/user needs, concept/interaction/content, prototyping/evaluation, detailed product/design-system handoff, release readiness and live performance without equating UI completion with user-centred evidence.

**Candidate boundary:** Current Architecture Map remains authoritative where it states `Digital Product / HCD = CONTRACT_ENVELOPE_AVAILABLE / DOMAIN PROCESS OPEN`.

---

## 1｜Why this candidate exists

Current OLEANDER already has:
- Design Intelligence and shared DD;
- `oleander-design-process`;
- physical-product extensions;
- web/UI production Skills;
- system/interface/process governance;
- C04 digital interaction, route, offline/fallback, state-machine and editable UI assets.

What is not yet formalized is an R-E professional owner that can distinguish:

`DIGITAL DESIGN ARTIFACT EXISTS`

from:

`USER CONTEXT UNDERSTOOD → USER NEED / REQUIREMENT AUTHORITY → INTERACTION DESIGN → RESEARCH / USABILITY EVIDENCE → ACCESSIBILITY → CONTENT → PRIVACY / SECURITY HANDOFF → INSTRUMENTATION → RELEASE / LIVE READBACK`.

Without that owner, a polished prototype can be overclaimed as HCD completion.

## 2｜Professional-source basis and freshness

### ISO 9241-210:2019

Current ISO page states Edition 2 (2019) was reviewed and confirmed in 2025 and remains current.

Use:
- human-centred design throughout the interactive-system lifecycle;
- context of use, user needs/requirements, design and evaluation as recurring responsibilities.

Not used as:
- a universal OLEANDER stage numbering system;
- a substitute for detailed method, accessibility, security or engineering evidence.

### ISO 9241-11:2018

Current ISO page confirms the usability framework remains current.

Use:
- usability is an outcome in a specified context of use for specified users/goals;
- effectiveness, efficiency and satisfaction must be tied to actual use/evaluation.

### ISO 9241-115:2024

Current standard explicitly covers:
- conceptual design;
- user-system interaction design;
- user-interface design;
- navigation design.

Use:
- to prevent “screen styling” from substituting for conceptual/interaction/navigation design.

### W3C WCAG 2.2

Current W3C Recommendation.

Use:
- web/digital accessibility technical requirements where applicable.

Boundary:
- a claimed conformance level requires actual evaluated evidence;
- this process does not machine-award WCAG conformance.

### GOV.UK Service Manual — current public practice evidence

Current guidance explicitly covers:
- user research;
- inclusive/accessibility work;
- prototypes;
- content;
- analytics/performance;
- privacy/security;
- continuous live research and improvement.

Use:
- task/practice evidence and failure-pattern support;
- not imported as UK-government stage authority for every product.

`PROFESSIONAL TASK EVIDENCE ≠ UNIVERSAL STAGE AUTHORITY`.

## 5｜Trigger contract

### Project-flow trigger

A material project claim requires human-centred digital research/design/evaluation or a digital interaction is relied upon for user outcomes.

### Typical professional questions

- Who are the users and what context/tasks/resources constrain use?
- What user needs and use-related requirements actually have evidence?
- What conceptual model, IA, interaction and content best support the task?
- Does the prototype work for representative users including disabled users?
- Are error/recovery, fallback, accessibility, content and state behaviour resolved?
- Can engineering implement the intended interaction without losing design logic?
- What privacy/security/data consequences arise from the interaction?
- What should be instrumented and how will live outcomes be read back?
- What observed live evidence requires iteration or reopen?

### Not triggered when

- a visual mockup is only a presentation device;
- a website is only a static exhibition surface with no material user task claim;
- a UI screenshot is used as communication but no interaction/usability claim is made.

## 6｜Claim ceiling

The effective HCD claim ceiling is the lowest valid ceiling across:

`CONTEXT-OF-USE EVIDENCE × USER-NEED/REQUIREMENT EVIDENCE × DESIGN ARTIFACT × RESEARCH/EVALUATION × ACCESSIBILITY × CONTENT × PRIVACY/SECURITY HANDOFF × ENGINEERING/RUNTIME READBACK × LIVE/ANALYTICS EVIDENCE`.

High-fidelity UI cannot outrun missing user evidence.

# 8｜HCD-DP0 — Scope, Authority & HCD Plan

**Professional question:** What user/product claim is being made, what HCD evidence is required, and who owns research/design/evaluation/security/accessibility decisions?

### Native outputs
- HCD scope/authority register;
- research/evaluation plan;
- initial user/context assumptions register;
- HCD interface owner map;
- claim ceiling.

### Exit
Enough scope and authority exist to begin bounded context/user research.

### Does not prove
user needs, usability, accessibility, privacy/security, implementation or live performance.

# 9｜HCD-DP1 — Context of Use & User Research

**Professional question:** Who is trying to achieve what, under which technical/physical/social conditions, and what evidence supports that understanding?

### Required work
- research questions;
- participant/recruitment logic;
- contextual inquiry/interviews/observation/usability of existing service as appropriate;
- support/offline/channel context;
- disabled/low-confidence/edge users where material;
- evidence/confidence/limitations;
- research-data/privacy handling.

### Native outputs
- context-of-use description;
- user/task/resource/environment model;
- research plan;
- session/research evidence refs;
- findings with confidence;
- unresolved research questions.

### Exit
Context/use evidence is sufficient for bounded need/requirement work.

### Does not prove
solution quality, usability of a proposed design, accessibility conformance or market demand.

# 10｜HCD-DP2 — User Needs, Use Requirements & Experience Architecture

**Professional question:** What evidence-backed user needs/outcomes and use-related requirements should govern the product before detailed UI?

### Required work
- distinguish need/outcome from feature;
- derive use-related requirements;
- define acceptance/evaluation criteria;
- establish end-to-end journey/service boundary;
- define conceptual model;
- establish IA/navigation/task architecture;
- identify content and no-digital/support relations;
- identify conflicting needs/trade-offs.

### Native outputs
- user-needs ledger;
- use-related requirements;
- experience/journey architecture;
- conceptual model;
- IA/navigation model;
- acceptance/evaluation criteria.

### Exit
Enough evidence-backed requirements exist to generate/test product concepts.

### Does not prove
that any proposed UI meets them.

# 11｜HCD-DP3 — Concept, Interaction, Content & State Design

**Professional question:** Which interaction concept best supports the user tasks and requirements, including failure/recovery and content depth?

### Required work
- materially different concepts where needed;
- task flows;
- interaction scenarios;
- content hierarchy;
- navigation;
- states;
- permissions;
- error/recovery;
- offline/degraded/unknown;
- accessibility-aware interaction;
- content/source ownership;
- design consequences for privacy/security.

### Native outputs
- interaction concept set;
- flow/state model;
- low/mid-fidelity prototypes;
- content model;
- state/error/recovery matrix;
- design-review disposition.

### Exit
A concept is coherent enough to evaluate with users at appropriate fidelity.

### Does not prove
usability, accessibility conformance, engineering feasibility or production readiness.

# 12｜HCD-DP4 — Prototype Evaluation, Usability & Accessibility

**Professional question:** Does the current prototype actually help representative users achieve intended goals with acceptable effectiveness/efficiency/satisfaction and inclusive access?

### Required work
- define research/evaluation questions before sessions;
- choose participant profiles;
- conduct usability evaluation at appropriate fidelity;
- include disabled users/assistive technologies when claim requires;
- capture task success/failure, errors, recovery and qualitative evidence;
- accessibility inspection/audit appropriate to maturity;
- analyse severity and causal hypothesis;
- revise/retest material findings.

### Native outputs
- evaluation plan;
- participant/sample boundary;
- test/prototype identity;
- task/scenario set;
- findings/severity;
- accessibility findings;
- repair/retest record;
- usability/evaluation receipt.

### Exit
Material usability/accessibility blockers for the current claim are resolved or explicit HOLDs.

### Does not prove
production accessibility, production performance, live outcomes or security/privacy approval.

- search;
- completion/failure;
- error/recovery;
- funnel/task evidence;
- qualitative feedback;

## 16｜C04 applicability boundary

C04 already contains strong digital design evidence:
- coherent public IA;
- TODAY / ROUTE / READ / MY BOOK / SERVICE;
- explicit Return priority;
- NORMAL / DEGRADED / CLOSED / UNKNOWN;
- FULL / LIGHT / OFF;
- digital-off/no-phone fallback;
- offline-first intent;
- AR/GPS/live-service claim limits;
- relational/NTS map boundary;
- editable HTML/SVG;
- localStorage memory;
- design crit;
- fail-closed UNKNOWN;
- field/promotion HOLD.

This does **not** establish professional HCD PASS.

Missing professional evidence includes:
- user research participants/sessions;
- context-of-use evidence beyond design inference;
- tested user-need/use-requirement ledger;
- usability task testing;
- disabled-user/assistive-tech research;
- WCAG evaluation/audit;
- actual browser runtime in current v1.2 readback;
- localization/content-language test;
- privacy/security review;
- analytics/instrumentation evidence;
- live user outcomes;
- production service reliability.

A C04 exercise must preserve E as completed design work and classify the missing evidence; it must not redraw or restart the product.

## 17｜Hard HOLD / mandatory REVISE conditions

Hold or revise when:
- personas/user needs are unsupported design assumptions;
- one stakeholder interview is treated as user research;
- a polished prototype substitutes for usability evidence;
- static checks substitute for actual interaction;
- accessibility is claimed from visual inspection only;
- WCAG conformance is claimed without evaluated evidence;
- UNKNOWN/degraded states fail open;
- error recovery/return path is missing;
- analytics events are added without an outcome/decision purpose;
- analytics are treated as causal proof;
- privacy/security-sensitive interaction has no specialist handoff;
- user-research data lacks consent/privacy handling;
- content/localization is assumed from one language/context;
- implementation diverges materially from tested prototype;
- release PASS is inferred from prototype/design KEEP;
- live outcome is claimed without live evidence.
