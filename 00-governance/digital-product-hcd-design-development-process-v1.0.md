## 1｜Purpose and authority position

This process defines an authentic professional route for **Digital Product / Human-Centered Design (HCD)** when a material project claim depends on how people understand, decide, act, recover, return, complete tasks or move between service/product states.

It exists to prevent common false closures such as:

- attractive UI presented as user-centered design;
- a persona, sitemap or journey map presented as user evidence;
- a clickable prototype presented as production behavior;
- heuristic review presented as representative user validation;
- accessibility lint presented as accessibility conformity;
- one SUS/task-completion number presented as universal usability truth;
- front-end behavior presented as backend/service truth;
- browser PASS presented as Design KEEP;
- project observation promoted as reusable HCD knowledge without transfer/counterevidence.

The process is **not** a universal Double Diamond, Design Thinking diagram, sprint cadence, Lean UX recipe, service-blueprint taxonomy, Figma workflow, product-management lifecycle or software-development process.

It does not replace:

- Current Project / Source / Design Authority;
- `professional-domain-process-contract-v1.0.md`;
- `design-quality-and-design-development-specification-v1.0.md`;
- `design-intelligence-routing-and-review-v1.0.md`;
- `cross-disciplinary-design-integration-v1.0.md` and R-F interface ownership;
- Research quality / primary-human-research protocol ownership;
- Visual Communication / UI Visual Composition ownership;
- Accessibility, legal, privacy, security, safety or regulated-domain authority;
- Software/backend/data engineering ownership;
- Systems Engineering system-architecture ownership;
- R-I actual readback / review;
- R-J Promotion/Persistence/Sync;
- R-K G9 / Knowledge Return.

`HCD PROCESS PASS ≠ DESIGN KEEP ≠ ACCESSIBILITY CERTIFICATION ≠ BACKEND CORRECTNESS ≠ R-F INTEGRATION PASS ≠ PROJECT PROMOTION`.

## 3｜Trigger and claim ceiling

Trigger this process when a material project claim depends on one or more of:

- target users/populations, tasks or operating context;
- product/service proposition or user outcome;
- task flow, journey, cross-channel/service handoff;
- information architecture, labeling or route recovery;
- interaction state, feedback, interruption, error, Return/back or re-entry;
- cognitive/physical demand or human-factors relation;
- accessibility/inclusion behavior in the designed interaction;
- prototype evidence;
- representative usability or human task evaluation;
- product/service transition and in-use learning.

Do **not** trigger this process merely because an artifact contains screens, typography, icons or a website. Static visual-composition work without a material human/task/service claim may remain with its actual visual/editorial owner.

The HCD claim ceiling is always the lowest applicable Current ceiling across:

`project/source authority / human-evidence quality / population-task-context applicability / product-state truth / content authority / technical implementation truth / accessibility authority / R-F interface state / prototype fidelity / representative evaluation / actual readback / independent review / external approval`.

## 4｜Core professional carriers

The process may use the following native/editable carriers when relevant. The carrier does not earn authority merely by existing.

### 4.1 Human / Stakeholder Evidence Register

For every consequential human input record:

`evidence ID → population / actor / role → task/context → method → sample/coverage basis → date/configuration → observed evidence → interpretation → uncertainty/bias → applicability → source/authority → decision consequence`.

`INTERVIEW QUOTE ≠ POPULATION TRUTH`.

### 4.2 Need / Task / Outcome Model

For each material need or task:

`actor / trigger / desired outcome / current behavior or workaround / precondition / task steps / information needed / decision point / error/recovery / completion state / service or system dependency / evidence status`.

### 4.3 Journey / Service-State Model

Use only when the product/service unfolds across time, channels or actors:

`entry → orientation → decision → action → feedback → branch/error → recovery/return → handoff → completion → later re-entry`.

The journey is an analytical/interaction carrier, not proof that users actually behave as drawn.

### 4.4 Information Architecture / Content Model

For non-trivial information spaces record:

`user goal → canonical object/home → grouping/placement → stable label → entry paths → orientation cues → route decisions → destination recognition → recovery/search/return → content authority`.

### 4.5 Interaction State Model

For each material interactive object or flow record:

`object / user intent / state / trigger / guard / transition / feedback / next possibility / interruptible-by / cancel-return behavior / error-unavailable behavior / re-entry / input modality / accessibility semantics / persistence consequence`.

### 4.6 Prototype Fidelity / Claim Matrix

For every prototype or simulation used as evidence:

`claim/question → minimum faithful medium → represented behavior/content/data/context → intentionally simplified elements → failure mode exposed → failure mode not exposed → runtime/configuration → readback method → evidence ceiling`.

### 4.7 Evaluation / Human-Factors Matrix

For every material evaluation question:

`decision question → target population / exclusions → task/environment → representative-condition rationale → method → observable / error / workload / comprehension / completion measure → predeclared interpretation rule where closure intended → observed result → anomaly → design consequence → revalidation trigger → residual HOLD`.

### 4.8 Product / Service Change-Impact Record

For every material change:

`changed requirement/content/state/interaction/data/service/visual-accessibility dependency → affected task/actor/state/interface → affected prototype/evaluation evidence → reuse justification or stale scope → repair → retest/revalidation → new evidence ID`.

## 5｜HCD-00 — Human / Service Problem Framing

**Professional question**

> What human, service or product-use problem is actually in scope, for whom, in which context, and what must remain explicitly unknown before research/development begins?

### Required work

- identify Current project/product/service authority and decision owner;
- define target actors/populations, relevant exclusions and stakeholder roles;
- define task/environment/channel/state scope;
- separate business/project goals from user needs and from assumed solutions;
- identify consequential accessibility/inclusion, legal/privacy/security, safety or regulated-domain interfaces;
- identify existing evidence, contradictions and unknowns;
- define research/development questions that can materially change the design.

### Native outputs

- HCD framing brief;
- actor/population/task/context map;
- assumption/unknown register;
- initial human-evidence/source map;
- initial interface/responsibility map.

### Exit criteria

The problem and actor/task/context boundary is specific enough to guide evidence collection and option work, while material unknowns and authority limits remain explicit.

### Handoff / reopen

Hand research questions to Research/HCD evidence owners and responsibility/interface needs to R-F as applicable. Reopen on project-goal, target-population, task, channel, risk, accessibility or service-boundary change.

**Does not prove:** user need validity, problem prevalence, solution direction, accessibility conformity, desirability or product-market fit.

## 6｜HCD-01 — Human Research and Evidence Basis

**Professional question**

> What evidence is required to understand the in-claim people/tasks/context, and is the resulting evidence strong enough for the decisions it is being asked to support?

### Required work

- route consequential primary research through an appropriate protocol before collection;
- distinguish orientation, exploratory, evaluative and validation research purposes;
- define participant/population/task/environment coverage based on decision risk rather than convenience;
- select methods capable of answering the question rather than choosing familiar methods first;
- preserve source/evidence/interpretation/assumption/decision separation;
- record bias, missing groups, contradictory evidence and context limits;
- do not convert one participant, one quote or one convenience sample into a population claim.

### Research-design and evidence-strength depth

Research design must begin from the **decision risk and uncertainty**, not from the preferred method.

For each consequential research question, make explicit as applicable:

- which design decision could change because of the evidence;
- target population / actor / role and material exclusions;
- task, environment, channel, device and operational state being represented;
- whether the question concerns discovery, prevalence, comprehension, task performance, comparison, failure mode, accessibility interaction, service handoff or another bounded purpose;
- what kind of observation would support, weaken or contradict the working hypothesis;
- recruitment source and the bias it may introduce;
- coverage across relevant experience, capability, role, frequency-of-use or contextual variation where material;
- moderator / observer / prototype-fidelity effects capable of changing the finding;
- privacy / consent / data-handling dependencies routed to the proper owner where personal data is collected;
- the ceiling at which qualitative evidence, quantitative evidence or mixed evidence can be used for the actual decision.

Do not use a fixed participant count, “saturation” label or statistical-looking percentage as a universal adequacy rule. The coverage rationale must relate to the heterogeneity and failure risk of the decision in claim.

Preserve negative cases and participants who succeed for a different reason than intended. A smooth aggregate narrative that deletes contradiction is weaker evidence than an explicit bounded finding.

`METHOD COMPLETED ≠ EVIDENCE ADEQUATE FOR DECISION`.

### Evidence analysis / synthesis depth

Define the **unit of observation** and the path from raw evidence to interpreted finding before synthesis.

For qualitative evidence, preserve as applicable:

- source / participant / session / task / context locator;
- exact observed behavior / statement / artifact before interpretation;
- coding / category rationale where coding is used;
- negative, contradictory and boundary cases;
- enough raw examples or locators that an independent reviewer can challenge the interpretation;
- whether repetition reflects true recurrence, repeated exposure to the same condition, or researcher aggregation.

Repeated mention is not automatically prevalence. One vivid quote is not automatically importance. Treat frequency, consequence and strategic relevance as separate dimensions unless the method justifies combining them.

For quantitative survey / behavioral evidence, preserve as applicable:

- exact question / measure / event definition;
- denominator and missing-data basis;
- population / segment / context represented;
- uncertainty appropriate to the evidence and decision;
- recruitment / response / survivorship / instrumentation bias that can distort the result;
- whether the measure is direct, proxy or self-report;
- any weighting / normalization / filtering that materially changes interpretation.

Where consequence is high, use proportionate second review / adjudication of interpretation or coding rather than converting analyst agreement into a universal threshold.

Keep the reasoning chain explicit:

`observed evidence → interpretation → competing interpretation / contradiction → confidence / applicability boundary → design implication → evidence still needed`.

Synthesis should show which evidence supports, weakens or leaves each design claim unresolved. Do not collapse ambiguity into a single “insight” merely to make the design process look decisive.

When qualitative, quantitative, telemetry, support and expert-review evidence are combined, preserve each method's unit of observation, population/coverage, timing/configuration, denominator and inferential ceiling. For each material claim, show **convergence, divergence and missing evidence** explicitly; do not average unlike evidence into one confidence score. A survey attitude, observed task failure and production metric may describe different phenomena. Where methods disagree, test plausible explanations such as sampling/coverage, wording, instrumentation, context, learning, implementation defect or different time horizon, then state which decision remains supportable and which remains `OPEN`.

### Native outputs

- research/evidence plan or protocol ref;
- recruitment/coverage rationale where applicable;
- evidence register;
- observation/insight/uncertainty synthesis;
- contradiction and limitation register;
- design-question consequences.

### Exit criteria

The decisions carried forward are traceable to evidence at an explicit applicability/confidence boundary; unsupported assumptions remain visible and do not masquerade as findings.

### Handoff / reopen

Hand evidence-backed human constraints/opportunities to HCD-02 onward. Reopen when population, task, environment, source quality, contradictory evidence or research method validity changes materially.

**Does not prove:** representative validation, causality, universal behavior, future adoption or Design KEEP.

## 7｜HCD-02 — Needs, Tasks and Service / Journey Model

**Professional question**

> What do the in-claim actors need to accomplish, how does the real task/service context unfold, and where do uncertainty, handoffs, errors, attention or recovery materially shape the design?

### Required work

- translate evidence into needs/outcomes without inventing unsupported features;
- model critical tasks, preconditions, information needs, decision points and completion states;
- identify current workaround/failure/error/recovery behavior where evidence exists;
- map attention/cognitive/physical demand where material;
- model cross-channel, staff, operational or service handoffs when the user experience depends on them;
- distinguish required task path from optional content/engagement;
- identify degraded/offline/permission/unavailable or safety-critical states when they change the task.

### Task-analysis, workload and error-depth

For each critical task, model the relation:

`trigger / goal → prerequisite information/resources → action/decision steps → system/service response → user interpretation → next action → completion / recovery / abandonment`.

Deepen the task model where material by recording:

- frequency and consequence of failure rather than treating every task as equal;
- time pressure, interruption, multitasking or handoff to another actor;
- working-memory / recall demand versus recognition / visible state;
- choice count, ambiguity and information needed at the decision point;
- physical reach, precision, posture or sensory condition where HCD depends on body/task fit;
- error opportunities: slip, mode error, wrong target, wrong state, omission, duplicate action, premature commit or misunderstanding;
- recoverability, reversibility and cost of error;
- staff/manual workaround that currently compensates for a product/service defect;
- cross-channel or cross-role dependencies that move the user out of the nominal interface;
- setup / teardown / return / later re-entry tasks, not only the central “happy path”.

Where task duration or workload is important, define what is being measured and why. Faster is not always better if it increases error, hides comprehension failure or shifts work to another actor.

Where cognitive demand can cause consequential error, identify what the user must perceive, remember, compare, decide and retain across each decision point. Distinguish information that can remain visible from information the design implicitly asks the user to remember, including mode/state, prior choices, pending work, prerequisites and consequences. For interrupted or error-prone tasks, provide and test resumption cues that reveal current state, what has persisted, what remains unresolved and the next safe action. Recovery evidence should observe whether people can diagnose what happened and resume without reconstructing hidden state or repeating completed work. HCD owns the human-facing demand/recovery requirement; technical owners retain truth for persistence, transaction state and system behavior.

`TASK FLOW DRAWN ≠ COGNITIVE / PHYSICAL DEMAND UNDERSTOOD`.

### Native outputs

- need/outcome ledger;
- critical-task model;
- journey/service-state model where triggered;
- demand/attention map;
- failure/recovery opportunity map;
- HCD requirements to product/service/system owners.

### Exit criteria

Critical tasks and service states are traceable to evidence or explicit assumptions, and the model exposes decision/recovery/handoff conditions rather than only a nominal happy path.

### Handoff / reopen

Hand task/outcome/state requirements to concept, systems, content, operations and technical owners. Reopen on new evidence, actor/task/service/channel or operating-state change.

**Does not prove:** chosen concept quality, task success, service feasibility, backend capability or observed user performance.

## 8｜HCD-03 — Experience Concept and Product / Service Architecture

**Professional question**

> Which materially distinct experience/product/service concept best answers the evidence-backed needs and constraints, and what principle must remain true as detail develops?

### Required work

- generate materially different concept routes where the decision is not already fixed by authority;
- define each concept's task/service model, primary interaction relation, channel/automation/human split and major assumptions;
- compare concepts under fixed criteria linked to needs, task risk, accessibility/inclusion, operational burden, technical dependencies and Design intent;
- expose trade-offs rather than presenting only the selected route;
- preserve a generative principle/invariant that constrains downstream IA, interaction and presentation;
- identify which implementation questions remain outside HCD authority.

### Experience-concept trade and falsification depth

Compare concept routes on the **human / service mechanism they change**, not presentation polish.

For each materially retained option, trace as applicable:

- critical tasks and the failure / recovery states the concept changes;
- information burden and decision complexity;
- human-versus-automation allocation and what happens when automation is unavailable or wrong;
- accessibility / inclusion consequence at the current evidence ceiling;
- staff / operations / support burden and handoff complexity;
- cross-channel continuation / recovery;
- technical / service dependencies capable of invalidating the experience concept;
- likely maintenance / content / policy / configuration change burden;
- privacy / trust / consent consequence where the concept changes data or decision visibility;
- which Design DNA / experience invariant must survive downstream implementation.

Mark assumptions whose failure would reverse concept selection, then define the **cheapest faithful evidence** capable of attacking them before downstream detail hardens: targeted research, task prototype, service simulation, technical spike, interface proof or another owner-native evidence route.

Separate hard human/service constraints from tradeable preferences. A concept cannot compensate for an in-claim critical-task, safety or accessibility requirement merely by scoring well on aesthetics, novelty, engagement or implementation convenience.

Preserve why rejected concepts failed and what later evidence would justify reopening them. A polished prototype of one route is not evidence that credible alternatives were inferior.

`BEST PRESENTED CONCEPT ≠ BEST SUPPORTED CONCEPT`.

### Native outputs

- concept set;
- concept comparison/trade study;
- selected experience/product-service concept;
- generative principle/invariant set;
- rejected-option lessons/open questions.

### Exit criteria

A concept is retained for explicit reasons and its user/task/service consequences are testable; selection is not justified only by visual preference or implementation convenience.

### Handoff / reopen

Hand experience invariants and controlled variables to IA/content, interaction, visual, systems and technical owners. Reopen when controlling needs, task risk, service assumptions, technical feasibility or evidence invalidate the selection basis.

**Does not prove:** final usability, implementation feasibility, visual quality, accessibility compliance, backend correctness or market success.

## 9｜HCD-04 — Information Architecture, Content Structure and Wayfinding

**Professional question**

> Can people find, understand and recover within the information/product structure using stable task-oriented relationships and truthful content?

### Required work

- map important user tasks and plausible entry points before locking navigation;
- define canonical homes/objects and prevent duplicate competing sources of truth;
- group by user task/mental model rather than internal implementation structure unless users actually share that model;
- establish stable, recognizable labels across navigation, search, headings and actions;
- resolve orientation, route decision, route monitoring, destination recognition and recovery where structure is non-trivial;
- define content role, action/consequence wording, error/recovery and empty/loading/success semantics where words materially shape behavior;
- preserve content/source/legal truth; HCD copy cannot invent backend consequence, consent, availability or recovery.

### IA / content-structure edge-case depth

For non-trivial information spaces, attack more than the primary navigation tree:

- direct/deep entry from search, notification, external link or saved state;
- multiple legitimate routes to the same object without creating competing homes or conflicting labels;
- object lifecycle: draft / active / archived / unavailable / deleted / expired / permission-limited states where material;
- search / filter / sort / facet behavior when the object set is too large for browse-only navigation;
- no-result, partial-result and stale-result conditions;
- localization / variable-length labels / terminology changes where content structure depends on language;
- permission / role differences that alter visible structure, actions or destination availability;
- cross-channel continuation where the user must resume on another device, physical touchpoint or human-service channel;
- breadcrumb/history/Back semantics when the route into an object is not unique;
- migration/redirect behavior when canonical homes or taxonomy change.

Labels should be tested against the **decision they enable**, not only internal consistency. A technically accurate label that users cannot distinguish at the moment of choice remains a design problem.

Test orientation and route choice under the conditions that most reduce legibility: first entry, deep-link entry, return after interruption, long or localized labels, zoom/text scaling, constrained viewport, dense result sets and time-pressured or low-attention use where material. At each critical decision point, verify that current location/object, available next actions, consequence-bearing distinctions and a credible Back/Return/recovery route remain perceivable without relying on memory. In shared-device, public-display or shoulder-view contexts, also identify which labels, previews, notifications, recent-history or route states may expose sensitive information and what human-facing conceal/reveal behavior is required. Privacy/legal owners control data/privacy requirements; HCD owns legibility, comprehension and route behavior.

Search success cannot rescue an incoherent canonical structure if users repeatedly need search because primary grouping/wayfinding fails.

### Native outputs

- task-entry / IA model;
- canonical-home/content-object map;
- navigation/wayfinding/recovery model;
- content-role/action-consequence model;
- representative labels and high-risk state content;
- content authority and unresolved truth/compliance holds.

### Exit criteria

Critical tasks have coherent entry/orientation/destination/recovery paths and stable content semantics; deep entry and wrong-turn recovery are testable in a prototype/native surface.

### Handoff / reopen

Hand structural content/route requirements to interaction, content, implementation and visual owners. Reopen on task, object taxonomy, content authority, navigation, localization, permission or service-state change.

**Does not prove:** observed findability, user comprehension, visual hierarchy quality, search quality, localization quality or physical wayfinding performance.

## 10｜HCD-05 — Interaction Model, State, Feedback and Recovery

**Professional question**

> Does each material user intent have a coherent, interruptible, recoverable and semantically accessible state model whose behavior matches the promised product/service consequence?

### Required work

- define intent before event-handler or animation implementation;
- enumerate material states including unavailable/error/degraded/permission/loading/empty/success where applicable;
- define guards, transitions, acknowledgement, feedback and next possibility;
- define Back/Return/Cancel, interruption and re-entry behavior;
- align pointer/touch/keyboard/other relevant input methods with the same intent;
- treat focus, programmatic name/role/state and dynamic announcement as state architecture where relevant;
- preserve user preference behavior such as reduced motion where triggered;
- route motion only after state semantics are defined;
- distinguish reversible, destructive, publishing/sharing, payment/permission and other high-stakes actions by actual consequence.

### Interaction concurrency, latency and commit-depth

Critical interaction models should expose states that appear only under imperfect runtime conditions:

- delayed response / uncertain completion;
- duplicate input / repeated tap / retry;
- optimistic update later rejected by the service;
- concurrent edit or stale data;
- partial save / partial upload / partial transaction;
- network loss during a multi-step action;
- permission/session expiry mid-task;
- external-system handoff that returns late, cancelled or with changed state;
- background completion after the user has navigated away;
- device / viewport / input-mode change during an unfinished task.

Where multiple people or roles can act on the same object, queue, case, booking, document or service request, model the human-visible coordination state: current owner/actor, editable versus read-only state, pending approval, stale information, conflicting change, handoff, escalation and resolution. Test what each actor can see about another actor's action and whether the design prevents duplicate work, silent overwrite, contradictory commitments or false assumptions that someone else has completed the task. Where role authority differs, make the limitation and next legitimate route legible at the point of action. HCD specifies coordination and conflict-recovery behavior; identity, authorization, locking, merge and data-consistency mechanisms remain with Software/Systems/Security owners.

For consequential actions, distinguish **intent expressed**, **request accepted**, **operation completed**, **result persisted**, and **user informed**. The UI must not present a success state before the product/service owner can support that claim, nor keep the user uncertain after a completed operation.

For irreversible or costly actions, make commit point, consequence, review/confirmation and recovery/escalation explicit. Confirmation dialogs are not a universal repair; reduce preventable error upstream where possible.

When offline/degraded behavior is in claim, define which information remains trustworthy, which actions are queued, which are blocked and how reconciliation/conflict is surfaced on return. HCD specifies the human-facing state model; software/data owners retain implementation/data-consistency authority.

Model consequential **service recovery** as its own state sequence:

`failure detected → user informed → ownership/status visible → safe fallback or human handoff → corrective action/redress where the responsible service/policy owner permits → proof of restored state → re-entry without unnecessary repetition`.

Recovery quality includes what information/work the user must repeat, what remains persisted, how duplicate actions are prevented and how unresolved cases escalate. Where consent or personal-data choice is part of the flow, preserve purpose/scope, the material consequence of acceptance/refusal, later withdrawal/revocation and the resulting product state. HCD owns comprehension/interaction consequences; Legal/Privacy owners determine validity, required wording and lawful processing.

Trust-relevant design evidence is truthful status, consequence visibility, reversible choice where applicable, consistent follow-through and explicit uncertainty—not reassuring tone alone.

`SPINNER PRESENT ≠ ASYNCHRONOUS STATE RESOLVED`.

### Native outputs

- interaction object/intents register;
- state/transition model;
- input/focus/selection model;
- interruption/return/re-entry contract;
- accessible-interaction requirements;
- error/loading/empty/success behavior;
- technical/backend dependency handoff.

### Exit criteria

Every in-claim critical action can be traced from intent through state change, feedback and recovery, and no critical path depends on a decorative lock or an unstated backend behavior.

### Handoff / reopen

Hand executable behavior to UI interaction/software/runtime owners and accessibility requirements to the applicable accessibility/technical owner. Reopen on state, action consequence, data/service availability, permission, navigation, input method, focus model or accessibility requirement change.

**Does not prove:** production implementation, accessibility conformity, task success, backend/service correctness or interaction Design KEEP.

## 11｜HCD-06 — Prototype, Visual / Technical Integration and Evaluation Readiness

**Professional question**

> Is there a minimum faithful prototype/current implementation capable of exposing the task, content, state, interaction and accessibility relations that the next professional question depends on?

### Required work

- state each prototype question and required fidelity before choosing the tool/medium;
- use one Current editable/native source for the bounded implementation object where applicable;
- bind IA/content/state/interaction requirements into the prototype rather than presenting disconnected screens;
- integrate real or bounded content/data/service behavior at the fidelity needed for the claim;
- coordinate visual hierarchy/design language without allowing visual polish to hide broken task/state logic;
- coordinate responsive/adaptive states where they materially change hierarchy, order or interaction;
- perform real runtime/browser/device readback for behavior being claimed;
- identify which service/backend/data/security/accessibility behaviors are simulated and which are real;
- prepare representative evaluation tasks and instrumentation/readback without pre-biasing success.

### Evaluation-readiness fidelity attacks

Before evaluation, identify which prototype simplifications could make the task artificially easy or hard. Common distortions include:

- preloaded perfect data that removes search, error or loading states;
- researcher-created shortcuts or seeded content unavailable in production;
- clickable hotspots larger than the visible control;
- simulated backend responses that always succeed instantly;
- absent authentication, permission, latency or cross-channel handoff;
- content shorter/cleaner than real content;
- evaluator guidance compensating for missing labels/orientation;
- desktop-only behavior standing in for a materially different mobile/input state;
- fake notifications, confirmations or persistence that do not match the real service consequence.

The evaluation-readiness record must state which of these are intentionally simulated and whether the simplification weakens any intended inference. If the prototype cannot expose the failure mode, do not ask the study to close that claim.

### Native outputs

- editable prototype/native runtime source;
- prototype fidelity/claim matrix;
- requirement/task/state coverage map;
- visual/interaction/accessibility/technical handoff register;
- runtime/browser/device readback;
- evaluation-readiness record and explicit simulated/held behavior.

### Exit criteria

The prototype/runtime can faithfully expose the in-claim user tasks and failure/recovery states, with known simplifications and technical truth boundaries visible.

### Handoff / reopen

Hand the evaluated configuration, task scripts/questions and claim limits to HCD-07. Reopen on material content, IA, visual hierarchy, state, interaction, responsive behavior, data/service dependency or prototype-fidelity change.

**Does not prove:** usability, accessibility conformity, production readiness, backend/security correctness, visual Design KEEP or representative validation.

## 12｜HCD-07 — Representative Evaluation, Human Factors and Accessibility Evidence

**Professional question**

> What does representative task evidence show about the current design, where do people fail or compensate, and which design claims can actually close at the tested population/task/context/configuration?

### Required work

- bind evaluation to an explicit decision question rather than “get feedback”;
- identify target population, exclusions, task/environment and why the participants/conditions are adequate for the decision risk;
- distinguish formative learning from claim-closing validation;
- capture task completion, error, workaround, comprehension, orientation, recovery, cognitive/physical demand and other observables appropriate to the claim;
- preserve qualitative evidence and failure detail instead of hiding it behind one aggregate score;
- treat observed error as possible design/system evidence, not default “user error”;
- run keyboard/focus/semantic/preference/assistive-technology interaction checks where applicable;
- keep automated accessibility scans as defect detectors only;
- route standards/legal accessibility conformity to the proper authority and current standard;
- separate usability/HCD evidence from visual Design Quality judgment;
- preserve exact tested prototype/configuration and reopen evidence after material change.

### Evaluation method, severity and interpretation depth

For each claim-closing evaluation question, predeclare as applicable:

- task start condition, completion condition and material prohibited assistance;
- observable failure / critical error / workaround / abandonment conditions;
- which facilitator prompts are allowed and how prompting changes interpretation;
- prior experience / learning / repeated-task effects relevant to the study;
- order / carry-over effects when alternatives or repeated tasks are compared;
- environment, device, input method, assistive technology and content/data state;
- qualitative evidence to preserve even when a metric is collected;
- how issue severity relates to frequency/coverage, consequence, recoverability and affected population rather than one arbitrary score;
- what evidence would trigger `REVISE`, `HOLD` or additional study instead of claiming success.

Do not treat think-aloud, moderator intervention or a training briefing as neutral if the real product will not provide that support. Record when the study itself changes the task.

For comparisons, avoid declaring one concept better because of a small observed difference when participant/task/order/configuration uncertainty could plausibly explain it. The process does not install a universal significance threshold; select analysis appropriate to the evidence and decision.

Accessibility interaction evidence should bind actual assistive technology / browser / device / input configuration where relevant. A scan or one assistive-technology path cannot automatically generalize to all configurations.

Accessibility evidence should represent material variability within and between users: fatigue, temporary/situational impairment, zoom/text scaling, input switching, assistive-technology personalization, language/literacy and changing sensory/cognitive conditions where these alter the task. Do not treat one disabled-user profile or one assistive-technology path as the stable boundary of use.

When a component library / design system carries interaction behavior, preserve intent/state/focus/name-role-state/error/recovery invariants across component variants, composition, responsive states and local overrides. A component-level PASS does not prove a composed flow if nesting or override changes order, announcement, target, timing or recovery. HCD owns the human-facing behavior requirement; Visual/Design-System implementation and accessibility conformity remain with their proper owners.

`TASK COMPLETED WITH MODERATOR HELP ≠ INDEPENDENT TASK SUCCESS`.

### Native outputs

- evaluation plan / decision questions;
- participant/task/context coverage record;
- as-run configuration and method record;
- task/evidence logs;
- observed error/workaround/comprehension/recovery findings;
- accessibility interaction evidence where triggered;
- issue severity/decision consequence register;
- repair + re-evaluation set;
- bounded HCD verdict and residual HOLD.

### Exit criteria

Each in-claim HCD conclusion is supported by evidence from the actual tested configuration and bounded to the represented population/task/context; blocking failures are repaired/retested or remain explicit HOLD.

### Handoff / reopen

Hand design defects back to HCD-02…06 by cause, technical/accessibility findings to their owners and bounded findings to Design Review/R-I. Reopen on user group, task, content, IA, state, interaction, visual hierarchy, implementation, platform, accessibility requirement or operational-context change.

**Does not prove:** universal usability, accessibility certification, conversion/business performance, future field behavior, production reliability, Design KEEP or Project Promotion.

## 13｜HCD-08 — Transition, Operation, In-use Learning and Change

**Professional question**

> After handoff/release/operation, what actual use evidence changes the product/service design, which prior HCD claims become stale, and what may be returned as a bounded learning candidate?

### Required work

- preserve the released/operated configuration and known HCD limits;
- define monitoring/support/feedback inputs that can answer a real design question rather than collecting vanity metrics;
- distinguish telemetry/analytics/support reports/observed behavior from causal explanation;
- compare in-use behavior with prior task, journey, accessibility and validation assumptions;
- classify product/service change impact on tasks, states, content, IA, interaction and human evidence;
- reopen and revalidate only affected scope unless coupling shows broader consequence;
- route project repair immediately through existing owners when required;
- route reusable lesson only as G9/Knowledge/Evolution **candidate** with explicit transfer boundary and counterevidence requirement.

### In-use analytics and causal-inference discipline

Operational data is only useful when its instrumentation and denominator are understood. For any metric used to change design, record as applicable:

- event / state definition and exact product/service version producing it;
- who or what is included/excluded from the denominator;
- missing events, blocked tracking, duplicate events, bots/test traffic or instrumentation changes;
- cohort / role / channel / device / acquisition or other segmentation needed for the design question;
- exposure opportunity: users cannot fail a step they never reached;
- seasonality, campaign, content, staffing, pricing, policy or service changes that may confound the observation;
- survivorship / self-selection / support-channel bias;
- privacy / consent / retention authority for personal or behavioral data;
- whether the metric is observation, association or evidence from an actual controlled/credible causal design.

When an in-use metric changes after a design release, preserve alternative explanations and use the smallest discriminating follow-up possible—qualitative investigation, segmented analysis, instrumentation check, controlled comparison or additional observation—before attributing cause.

Vanity metrics such as total clicks, time spent or raw engagement do not automatically equal user value; interpret them through the task/outcome model and possible failure behavior.

Separate **episode-level task performance** from repeated-use adoption. A user completing a representative task once does not show that the product becomes part of real practice. For adoption claims, define the recurring opportunity to use, eligible cohort, first-use and return/repeat behavior, abandonment or workaround, support burden, role/process dependence and the observation window appropriate to the task cadence. Distinguish non-use because no need/opportunity occurred from rejection after opportunity, and distinguish novelty/training effects from stable repeated behavior.

Compare longitudinal evidence with prior task evidence so a flow can be easy in-session yet fail to be adopted because setup, trust, policy, handoff, maintenance or recurring effort is unacceptable.

`METRIC MOVED AFTER RELEASE ≠ DESIGN CAUSED THE CHANGE`.

### Native outputs

- transition/handoff HCD constraints;
- release/operation configuration record;
- in-use observation and support evidence;
- designed-vs-observed comparison;
- change-impact/revalidation record;
- bounded project lesson;
- G9/Knowledge/Evolution candidate refs where justified.

### Exit criteria

Each bounded in-use question has an explicit observation period/context/configuration, affected Current claims are reopened/revalidated where necessary, and reusable claims remain candidate-only until their separate lifecycle closes.

### Handoff / reopen

Project defects return to the responsible HCD/technical/operations owner without waiting for Knowledge promotion. Reusable learning routes R-K → R-B as feedback, not dependency. Reopen on new contradictory evidence, material product/service change or changed population/task/context.

**Does not prove:** causality from correlation, universal user behavior, transferable knowledge, Current Knowledge, product-market fit, future performance or runtime self-mutation.

`HCD COORDINATION ≠ R-F INTERFACE PASS`.

`PROMISED USER CONSEQUENCE → TECHNICAL/SERVICE OWNER → INTERFACE REQUIREMENT → ACTUAL IMPLEMENTATION/READBACK → HCD INTERPRETATION`.

HCD cannot invent technical truth to make a prototype coherent.

`HEURISTIC DEFECT ≠ OBSERVED USER FAILURE`

## 18｜Native source and actual readback

Possible authoritative HCD carriers include, as applicable:

- structured research/evidence data and protocol records;
- editable task/journey/service-state models;
- editable IA/content models;
- native interaction/state definitions;

The required chain is:

`INTENDED HUMAN / TASK / EXPERIENCE RELATION → IMPLEMENTED IN CURRENT NATIVE CARRIER → OBSERVED IN ACTUAL RUNTIME / TASK READBACK → PROFESSIONAL INTERPRETATION → BOUNDED HCD VERDICT`.

## 19｜Professional review and failure attacks

Independent/professional review should attack at least:

- problem framing that merely restates the proposed solution;
- convenience sample treated as representative without a claim boundary;
- persona/journey map with no evidence or falsifiable consequence;
- task flow containing only the happy path;
- IA mirroring internal organization/code structure instead of user goals without evidence;
- labels/copy promising behavior the product/service cannot perform;
- missing error/permission/offline/degraded/return/re-entry states;
- interaction state duplicated across unsynchronized variables/carriers;
- motion or loading locking critical recovery/Return;
- pointer path succeeding while keyboard/touch/assistive path fails where in claim;
- accessibility deferred until after interaction architecture is locked;
- responsive adaptation reversing semantic/focus order;
- prototype visual fidelity mistaken for behavioral fidelity;
- prototype/browser technical PASS mistaken for HCD/user PASS;
- heuristic review or automated scanner reported as user validation;
- one aggregate usability score hiding task failure/error/workaround;
- observed user failure dismissed as “user error” without design/system rival cause;
- test evidence attached to the wrong build/configuration;
- product/service change preserving stale user evidence;
- analytics/telemetry observation promoted to causal explanation;
- project-specific success promoted to reusable Knowledge without transfer/counterevidence.

## 20｜Change / supersession / revalidation

A material change to any of the following must compute affected scope:

`target population / task / service context / content authority / IA / navigation / interaction state / user-visible consequence / backend-service dependency / visual hierarchy / responsive relation / platform/input / accessibility requirement / product configuration / operational procedure`.

Then apply:

`CHANGE → AFFECTED HCD STAGES / TASKS / INTERFACES → AFFECTED PROTOTYPE / USER EVIDENCE → PRESERVE HISTORICAL EVIDENCE → STOP CURRENT CONSUMPTION WHERE STALE → REPAIR → R-I READBACK / PROFESSIONAL REVIEW → REVALIDATE AFFECTED CLAIM → SUCCESSOR / REVALIDATION RECEIPT`.

Only affected consumers become stale unless the dependency graph demonstrates wider consequence. Historical research/test evidence remains truthful for its original population/task/context/configuration and is not rewritten to impersonate the successor.

`NEW PRODUCT REVISION ≠ OLD USER EVIDENCE UPDATED`.
