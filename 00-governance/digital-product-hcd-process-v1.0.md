**Status:** CANDIDATE PROFESSIONAL DOMAIN PROCESS / CONTROLLED EVOLUTION INPUT

**Authority position:** subordinate to `complex-project-master-runtime-v1.0.md`, `OLEANDER_CURRENT_ARCHITECTURE_MAP_v2.1`, `professional-domain-process-contract-v1.0.md`, Current Knowledge Authority, Shared Design Quality, Cross-Disciplinary Integration, product/project authority and applicable privacy, security, accessibility, safety and regulatory owners.

## 1｜Why this process exists

Digital product design is not a screen-production pipeline and is not proven by a polished UI, component library, prototype, analytics dashboard or successful software build. A human-centred digital product process must preserve a traceable relation between the people affected by the system, their context of use, human-centred requirements, competing design solutions, representative evaluation, implementation constraints and actual in-use outcomes.

Canonical professional chain:

```text
AUTHORITY / PRODUCT INTENT / CLAIM BOUNDARY
→ PEOPLE / STAKEHOLDERS / CONTEXT OF USE
→ HUMAN-CENTRED NEEDS + REQUIREMENTS
→ COMPETING INTERACTION / SERVICE-TOUCHPOINT CONCEPTS
→ INFORMATION / INTERACTION / CONTENT STRUCTURE
→ PROTOTYPE / DESIGN SOLUTION
→ REPRESENTATIVE HUMAN-CENTRED EVALUATION
→ DELIVERY / IMPLEMENTATION READBACK
→ RELEASE-BOUNDARY SUPPORT WHEN APPOINTED
→ IN-USE / ACCESSIBILITY / SUPPORT / FAILURE / OUTCOME READBACK
→ REOPEN / G9 CANDIDATE RETURN
```

Hard boundaries:

```text
POLISHED UI ≠ HUMAN-CENTRED DESIGN PASS
DESIGN SYSTEM EXISTS ≠ PRODUCT USABILITY
PROTOTYPE TEST ≠ PRODUCTION EXPERIENCE
ANALYTICS SIGNAL ≠ USER INTENT / CAUSATION
CONVERSION IMPROVEMENT ≠ HUMAN-CENTRED QUALITY
ACCESSIBILITY CHECKER PASS ≠ ACCESSIBILITY CONFORMANCE
WCAG CONFORMANCE ≠ COMPLETE HCD
FRONT-END BUILD PASS ≠ DESIGN KEEP
USABILITY STUDY ≠ PRODUCT-MARKET FIT
USER REQUEST ≠ REQUIREMENT WITHOUT INTERPRETATION / PRIORITIZATION
PERSONA ≠ REPRESENTATIVE USER EVIDENCE
AI-SIMULATED USER ≠ HUMAN VALIDATION
HCD PROCESS PASS ≠ SECURITY / PRIVACY / LEGAL / SAFETY APPROVAL
HCD PROCESS PASS ≠ DESIGN KEEP ≠ PROJECT PROMOTION
```

## 2｜Professional-source alignment and stage identity

ISO 9241-210 defines requirements and recommendations for human-centred design principles and activities throughout the life cycle of interactive systems. ISO 9241-220 describes organizational processes and outcomes for enabling, executing and assessing HCD; ISO 9241-221 provides a process assessment model. ISO 9241-11 defines usability concepts and explicitly treats usability as an outcome of use rather than a visual property of an interface.

OLEANDER therefore uses internal **domain-native decision carriers** that expose the ISO activity logic without pretending that ISO publishes these stage identifiers:

```text
HCD-FRAME       Authority / product intent / scope / ethics / claim boundary
HCD-CONTEXT     People / stakeholders / tasks / environments / context of use
HCD-REQ         Human-centred needs / usability / accessibility / experience requirements
HCD-CONCEPT     Competing concepts / journeys / information + interaction structures
HCD-SOLUTION    Detailed interaction/content/visual/system behaviour solution
HCD-PROTOTYPE   Representative prototype / experiment / instrumentation when material
HCD-EVAL        Human-centred evaluation against requirements in representative context
HCD-DELIVERY    Implementation handoff / design-system / content / analytics / QA readback
HCD-INUSE       Production use / accessibility / support / failure / outcome / lifecycle review
```

These identifiers are OLEANDER internal carriers. They are **not ISO stage IDs**, do not imply a waterfall, and never synchronize by number with Architecture `ADD-*`, Interior `ID-PW*`, Lighting `LGT-*`, software-development sprints, Product Management roadmaps or Systems Engineering processes.

Iteration is expected. A later evaluation may reopen context, requirements or concept rather than merely patching a final screen.

## 3｜Trigger / applicability

Trigger this professional process when a project makes material claims about one or more of the following:

- interactive-system usability or human-centred quality;
- digital product experience, user journey, task completion or interaction behaviour;
- information architecture, navigation, findability or content interaction;
- interface states, error prevention/recovery, feedback or user control;
- accessibility/inclusive interaction within the HCD appointment;
- onboarding, account, transaction, workflow or service touchpoints mediated by an interactive system;
- human interaction with AI/automation/recommendation/decision-support;
- safety-relevant or high-consequence human-system interaction;
- representative user research, prototyping or usability evaluation;
- design-system/component behaviour where it affects human use;
- production instrumentation/analytics used to evaluate experience outcomes;
- post-release support/failure patterns used to revise HCD conclusions.

Do not infer a completed HCD claim merely because:

- a visual UI exists;
- a product manager wrote stories;
- a design system has components;
- a prototype received positive comments;
- software tests pass;
- analytics moved in the desired direction;
- an automated accessibility scan returned zero issues.

For consequential scope, `NOT_REQUIRED` must be explicit under the Current trigger/applicability contract. Omission is not `NOT_REQUIRED`.

## 4｜Authority / responsibility boundary

Digital Product / HCD owns professional human-centred design reasoning and its native outputs within the appointment. It does not absorb adjacent authorities.

Separate at minimum:

- **Product / business authority:** objectives, investment, roadmap, pricing, business viability and release authority;
- **HCD authority:** context of use, human-centred requirements, interaction/information/content design within scope, representative evaluation and HCD readback;
- **Software / technical authority:** architecture, code, performance, reliability, deployment and technical verification;
- **Security / privacy authority:** threat, data protection, consent/legal basis, security acceptance and incident obligations;
- **Accessibility authority:** accessibility requirements, testing and any formal conformance/assurance route;
- **Safety / regulated human-factors authority:** domain-specific safety or regulatory human-factors processes where triggered;
- **Service Design authority:** broader service organization, backstage operations, policy and non-digital touchpoints when materially in scope;
- **R-F Integration:** actual interface maturity/disposition across these owners.

`HCD REQUIREMENT ≠ PRODUCT ROADMAP AUTHORITY`.

`DESIGN INTENT ≠ SOFTWARE TECHNICAL PASS`.

`ACCESSIBILITY DESIGN ≠ FORMAL ACCESSIBILITY APPROVAL`.

## 6｜Cross-cutting HCD control objects

### 6.1 Human-Centred Basis / Responsibility Matrix

Record:

- system/product/service boundary;
- appointed HCD scope and exclusions;
- affected stakeholder/user groups;
- decision and release authority;
- research/evaluation responsibility;
- accessibility/privacy/security/safety interfaces;
- Product / Engineering / Content / Data / Service Design / Operations responsibilities;
- evidence and representative-participant requirements;
- decisions requiring independent or specialist review.

### 6.2 Context-of-Use Register

For each materially different context preserve:

```text
USER / AFFECTED PERSON
→ GOAL / TASK / WORKFLOW
→ FREQUENCY / CONSEQUENCE
→ PHYSICAL / SOCIAL / TECHNICAL ENVIRONMENT
→ DEVICE / CHANNEL / ASSISTIVE TECHNOLOGY
→ PRIOR KNOWLEDGE / LANGUAGE / CAPABILITY
→ CONSTRAINT / INTERRUPTION / FAILURE CONTEXT
→ DATA / PRIVACY / SAFETY EXPOSURE
→ EVIDENCE SOURCE + LIMITATION
→ RECHECK TRIGGER
```

### 6.3 Human-Centred Requirement Register

Each consequential requirement should resolve:

`NEED / PROBLEM → CONTEXT → REQUIREMENT → PRIORITY / AUTHORITY → MEASURE / EVALUATION METHOD → EVIDENCE → STATUS → CHANGE IMPACT`.

Do not collapse business KPI, technical requirement, accessibility requirement and human-centred outcome into a single score.

### 6.4 Interaction / Information / Content Model

Maintain explicit models for materially important:

- task flows and state transitions;
- information architecture / navigation;
- object/content model;
- permissions and roles as experienced by users;
- errors, recovery and irreversible actions;
- empty/loading/offline/degraded states;
- notification/feedback timing;
- AI/automation states, uncertainty and override where applicable.

### 6.5 Research / Evaluation Register

Record:

- research/evaluation question;
- target population and inclusion/exclusion basis;
- participant/source identity boundary and recruitment method;
- representative tasks/scenarios;
- prototype/product revision;
- environment/device/accessibility conditions;
- moderator/instrumentation;
- qualitative/quantitative measure definitions;
- observation versus interpretation;
- counterevidence and failed tasks;
- limitation / transfer boundary;
- decision and reopen trigger.

### 6.6 Experiment / Analytics Register

Production or controlled experiments preserve:

`HYPOTHESIS → METRIC DEFINITION → POPULATION → EXPOSURE / ASSIGNMENT → GUARDRAILS → DURATION → RESULT → UNCERTAINTY → CONFOUNDERS → HUMAN-CENTRED INTERPRETATION → DOES_NOT_PROVE`.

Analytics may identify behaviour patterns; it does not replace context research or infer motive/causality without evidence.

## 7｜HCD-FRAME — Authority / Product Intent / Claim Boundary

**Professional question:** What interactive system and human-centred claims are actually in scope, for whom, under whose decision authority and with what ethical/evidence boundary?

Resolve:

- system/product/service boundary;
- product/business intent as an input, not HCD authority;
- affected people/stakeholders and high-consequence groups;
- appointment / HCD responsibility;
- privacy/security/accessibility/safety/regulatory triggers;
- research access, consent and data-handling constraints;
- current product/legacy/brownfield condition where applicable;
- open authority/evidence gaps.

**Native outputs:** HCD Basis / Responsibility Matrix; initial stakeholder map; initial claim boundary; research/evaluation plan; open-risk register.

**Exit:** scope and responsibility are explicit enough to begin context research without inventing user truth.

**Does not prove:** validated needs, usability, accessibility conformance, technical feasibility or product viability.

---

## 8｜HCD-CONTEXT — Understand and Specify Context of Use

**Professional question:** Who uses or is affected by the system, to accomplish what, under which physical, social, technical and organizational conditions?

Develop evidence for:

- primary/secondary/indirectly affected people;
- goals/tasks/workflows and current workarounds;
- frequency, severity and consequence of failure;
- devices/channels/environments;
- language, literacy, capability and assistive technology;
- collaboration, interruption and handoff;
- organizational/policy constraints;
- current-system evidence and support/failure patterns.

**Native outputs:** Context-of-Use Register; task/workflow models; affected-person map; evidence gaps; research readback.

**Exit:** consequential context claims are evidence-bound, including populations not yet represented.

**Does not prove:** final requirement, preferred solution or transferability to unstudied contexts.

---

## 9｜HCD-REQ — Human-Centred Needs and Requirements

**Professional question:** What human-centred outcomes and interaction requirements must the solution satisfy in the declared contexts?

Translate evidence into explicit, testable requirements for applicable:

- effectiveness / task outcome;
- efficiency / effort / time where meaningful;
- satisfaction / confidence / comprehension;
- accessibility and inclusive use;
- error prevention / recovery / reversibility;
- learnability / discoverability;
- workload and information demand;
- trust / transparency / control in automation/AI;
- continuity across channels/touchpoints;
- safety/harm-related human interaction;
- support and recovery.

**Native outputs:** Human-Centred Requirement Register; priority/authority map; evaluation criteria; unresolved trade-offs.

**Exit:** requirements are traceable to context/evidence and have an evaluation route.

**Does not prove:** implementation, achievement of requirements or business viability.

---

## 10｜HCD-CONCEPT — Competing Human-Centred Concepts

**Professional question:** Which fundamentally different interaction/information/service-touchpoint concept best resolves the current human-centred requirements and constraints?

Develop controlled alternatives for:

- task/interaction model;
- information architecture;
- navigation/orientation;
- content strategy and terminology;
- workflow sequencing;
- cross-channel handoff;
- automation/manual control balance;
- error and recovery model;
- accessibility/inclusion strategy;
- support/escalation strategy.

Use design rationale and explicit trade-offs. Avoid decorative variants that preserve the same mechanism while pretending to be alternatives.

**Native outputs:** competing flows/models; concept prototypes; option comparison; rationale; interface requirements to Product/Engineering/Content/Data/Service/Operations.

**Exit:** selected mechanism is justified against human-centred requirements and key rejected alternatives remain traceable.

**Does not prove:** detailed usability, production feasibility or implementation quality.

---

## 11｜HCD-SOLUTION — Detailed Interaction / Information / Content Solution

**Professional question:** Is the selected human-centred mechanism resolved across meaningful states, content, accessibility and implementation interfaces?

Resolve at appropriate fidelity:

- screen/view/state structure;
- task and state transitions;
- information hierarchy and content;
- input/control behaviour;
- validation and error recovery;
- loading/offline/timeout/degraded states;
- permissions and role differences;
- responsive/device/channel behaviour;
- keyboard/focus/assistive-technology interaction where applicable;
- visual language and component behaviour;
- telemetry hooks needed for bounded in-use evaluation;
- implementation constraints and open questions.

**Native outputs:** interaction specification; information/content model; state/flow model; detailed prototype; component/behaviour requirements; accessibility annotations; implementation handoff package.

**Does not prove:** coded behaviour, production accessibility or user performance.

---

## 12｜HCD-PROTOTYPE — Prototype / Experiment

**Applicability:** conditional but expected where material human-use uncertainty cannot responsibly close from documentation alone.

**Professional question:** What must be made interactive or simulated to expose uncertainty before downstream commitment?

Prototype exact questions such as:

- navigation/findability;
- workflow sequencing;
- comprehension/terminology;
- error recovery;
- complex data entry;
- AI explanation/uncertainty/override;
- accessibility interaction;
- cross-device/channel handoff;
- high-consequence task behaviour.

Record exact revision, fidelity, fake/live data boundary, task coverage and what the prototype cannot prove.

`PROTOTYPE WORKS ≠ PRODUCTION WORKS`.

---

## 13｜HCD-EVAL — Human-Centred Evaluation

**Professional question:** Does the current solution satisfy the declared human-centred requirements for representative people, tasks and contexts within the evidence ceiling?

Evaluation may combine, as appropriate:

- expert/heuristic inspection;
- accessibility inspection and assistive-technology testing;
- moderated/unmoderated usability studies;
- task-performance observation;
- comprehension testing;
- comparative experiment;
- field/pilot study;
- support/failure evidence;
- quantitative measures with defined denominators and uncertainty.

Human evaluation must preserve participant/context representativeness and failed cases. A positive average cannot erase a severe subgroup or high-consequence failure.

**Native outputs:** evaluation protocol; participant/context matrix; findings/evidence; requirement disposition; severity/impact; design decisions; retest requirements.

**Exit:** triggered critical human-centred requirements have evidence-bound dispositions and material failures are either repaired/retested or explicitly block the claim.

**Does not prove:** all populations, production implementation, formal accessibility certification, safety/regulatory approval or product-market fit.

---

## 14｜HCD-DELIVERY — Implementation Handoff / Production Readback

**Professional question:** Has the implemented product preserved the human-centred design mechanism and requirements that were actually reviewed?

Handoff/readback covers as applicable:

- design source identity and component/state specs;
- content/copy and localization;
- responsive and accessibility behaviour;
- interaction timing/state transitions;
- error/recovery states;
- analytics/event definitions;
- Product/Engineering decisions and accepted deviations;
- implemented build readback;
- targeted regression / accessibility / usability checks;
- release-blocking HCD defects within appointment.

`DESIGN FILE MATCH ≠ BEHAVIOURAL MATCH`.

`CODE COMPLETE ≠ HCD CLOSED`.

**Native outputs:** implementation review/readback; deviation register; accepted/rejected implementation differences; production-evaluation plan.

---

## 15｜HCD-INUSE — In-Use / Lifecycle Human-Centred Review

**Professional question:** What does actual use reveal about the current human-centred assumptions, and which product conclusion must reopen now?

Read back, where available:

- task success/failure evidence;
- support/contact reasons;
- accessibility barriers;
- abandonment/retry/recovery patterns;
- qualitative user feedback;
- field observation;
- analytics with denominator/segment definitions;
- harm/complaint/incident evidence;
- changes in population/context/device/policy;
- model/AI behaviour drift where relevant.

Separate project/product repair from reusable knowledge promotion:

`OBSERVED OUTCOME ≠ CAUSAL EXPLANATION`.

`PROJECT REOPEN ≠ REUSABLE KNOWLEDGE REVISION`.

Reusable lessons route through R-K/G9 candidate intake and existing Knowledge validation; they do not self-promote from analytics or one product success/failure.

## 16｜Cross-disciplinary interfaces

Material interfaces may include:

- Product Management / Business: objectives, prioritization, roadmap, release and commercial constraints;
- Software Engineering / Architecture: technical constraints, implementation, performance, reliability and deployment;
- Systems Engineering: system context, stakeholder needs, system requirements, interfaces and verification/validation where applicable;
- Service Design / Operations: backstage processes, policy, human service channels and recovery;
- Content / Localization: content model, terminology, translation and governance;
- Data / Analytics: event definitions, metrics, experimentation and data quality;
- AI/ML: model capability, uncertainty, failure modes, evaluation and human oversight;
- Security / Privacy: identity, permissions, consent, data use, threat/risk and legal basis;
- Accessibility: requirements, specialist testing and formal conformance route;
- Safety / Regulatory / Human Factors: domain-specific high-consequence validation;
- Customer Support / Operations: failure evidence, escalation and service continuity.

R-F remains the owner of actual interface maturity/disposition. HCD declares and consumes interface requirements; it cannot self-close another domain's interface acceptance.

## 17｜Evidence and evaluation discipline

For every consequential HCD finding preserve:

`QUESTION → METHOD → POPULATION / SOURCE → CONTEXT → REVISION → TASK / EXPOSURE → OBSERVATION → INTERPRETATION → UNCERTAINTY → COUNTEREVIDENCE → DECISION → RETEST / REOPEN`.

Use numeric metrics only with explicit denominator, segmentation, instrumentation and analysis boundary. Avoid fabricated precision from small qualitative samples.

Where accessibility, safety or regulated human-factors approval is triggered, route to the applicable specialist/authority. HCD evidence may support that process but cannot award its approval.

---

## 18｜AI collaboration boundary

AI may assist with:

- research coding/synthesis when source provenance is retained;
- structured hypothesis generation;
- information/interaction alternatives;
- content variants;
- prototype/code assistance;
- issue clustering and traceability;
- accessibility/test preparation;
- analytics query assistance.

AI may not be treated as:

- a representative participant population;
- a substitute for affected-person consultation where required;
- proof of comprehension, usability, trust or accessibility;
- a source of invented behavioural evidence;
- an independent human/professional reviewer merely because a different model/session is used.

`SYNTHETIC USER ≠ HUMAN EVIDENCE`.

---

## 19｜Professional completion / readback

A Digital Product / HCD professional-process claim may close only within the declared scope when:

1. context-of-use evidence is sufficiently resolved for the claim;
2. human-centred requirements are traceable and current;
3. the delivered design mechanism is explicit across material states;
4. material HCD uncertainties have an appropriate evaluation route;
5. representative evaluation findings are resolved or explicitly held;
6. implementation readback has checked material behaviour, not only visual similarity;
7. critical cross-domain interfaces have the required R-F maturity/disposition;
8. open items remain inside the stated claim ceiling;
9. required independent/specialist review is complete where triggered;
10. actual evidence and does-not-prove boundaries are retained.

Hard separation:

```text
HCD PROCESS PASS ≠ DESIGN KEEP
HCD PROCESS PASS ≠ SOFTWARE PASS
HCD PROCESS PASS ≠ ACCESSIBILITY / SECURITY / PRIVACY / SAFETY / LEGAL APPROVAL
HCD PROCESS PASS ≠ PRODUCT-MARKET FIT
HCD PROCESS PASS ≠ PROJECT PROMOTION
```

## 20｜G9 / lifecycle return

Production use may reopen the product immediately when material evidence contradicts a prior assumption. Reusable learning remains a separate route:

`ACTUAL USE → PROJECT/PRODUCT REOPEN WHEN NEEDED`  
`ACTUAL USE → BOUNDED G9 LESSON CANDIDATE → EXISTING KNOWLEDGE OWNER / EVOLUTION ROUTE`.

No user study, analytics pattern, A/B result or product outcome may silently mutate the live Knowledge corpus or this professional process.
