## 1｜Why this process exists

Lighting design is not the arithmetic placement of luminaires after Architecture or Interior Design, and it is not identical to electrical engineering. It develops the relationship between natural light, electric light, darkness, surface, material, colour, form, human vision, activity, time, controls, energy, maintenance and the spatial/experiential intent of a project.

A professional lighting process must therefore connect creative design with measurable performance and delivery evidence:

```text
SCOPE / PEOPLE / VISUAL TASK / PLACE
→ LIGHTING QUESTION + DAYLIGHT / DARKNESS CONTEXT
→ CONCEPT / EXPERIENCE / HIERARCHY
→ SCHEME + PHOTOMETRIC / CONTROL STRATEGY
→ CROSS-DISCIPLINARY COORDINATION
→ TECHNICAL LIGHTING DESIGN
→ MOCKUP / SAMPLE / PROTOTYPE WHEN MATERIAL
→ PRODUCTION / SUBMITTAL / PROCUREMENT SUPPORT
→ COMMISSIONING / AIMING / MEASUREMENT / HANDOVER
→ IN-USE / POST-OCCUPANCY / MAINTENANCE READBACK
```

Hard boundaries:

```text
LUX TARGET ≠ LIGHTING DESIGN
CALCULATION PASS ≠ INSTALLED VISUAL QUALITY
RENDER ≠ PHOTOMETRIC / FIELD TRUTH
LUMINAIRE DATASHEET ≠ PROJECT PERFORMANCE
DALI / CONTROL NETWORK PASS ≠ LIGHTING EXPERIENCE PASS
ELECTRICAL CIRCUIT PASS ≠ LIGHTING DESIGN PASS
EMERGENCY-LIGHTING INTERFACE ≠ STATUTORY FIRE/LIFE-SAFETY APPROVAL
DAYLIGHT MODEL ≠ ELECTRIC-LIGHTING DESIGN PASS
MOCKUP KEEP ≠ ALL INSTALLED WORK CONFORMS
COMMISSIONING COMPLETE ≠ DESIGN KEEP
LIGHTING PROCESS PASS ≠ DESIGN KEEP
INTEGRATIVE / CIRCADIAN CLAIM ≠ PROVEN HEALTH OUTCOME
```

## 2｜Professional-source alignment and stage identity

Current SLL guidance does not require OLEANDER to pretend that Lighting has the same professional stages as Architecture, Structural or MEP. LG23 addresses the overall architectural lighting design process and combines design creativity with compliance and delivery. The SLL Lighting Handbook explicitly spans initial design decisions, technical solution selection, detail design, commissioning and handover. Commissioning Code L adds commissioning-management, pre-commissioning, functional commissioning, handover and post-occupancy checks.

OLEANDER therefore uses **domain-native professional decision carriers**, not claimed SLL official stage numbers:

```text
LGT-BASIS          Scope / people / place / visual-task / evidence basis
LGT-CONCEPT        Lighting concept / hierarchy / experience / darkness
LGT-SCHEME         Daylight-electric scheme / photometric + controls strategy
LGT-COORDINATION   Architecture / Interior / Landscape / MEP / Envelope integration
LGT-TECHNICAL      Detailed photometry / luminaires / optics / colour / controls / energy
LGT-PROTOTYPE      Mockup / sample / visual experiment / aiming benchmark when material
LGT-PRODUCTION     Tender / submittal / equivalent / fabrication / procurement support
LGT-CX             Installation readback / commissioning / aiming / measurement / handover
LGT-INUSE          Post-occupancy / seasonal-time-state / maintenance / performance review
```

These identifiers are OLEANDER internal carriers. They are **not** SLL-published stage IDs and never synchronize by number with Architecture `ADD-*`, Structural `SE-SPW*`, MEP `BSP-*`, Interior `ID-PW*`, Landscape `LA-PW*` or any other profession.

`LGT-PROTOTYPE` is triggered when a material visual, optical, material, detail, aiming, controls or human-experience uncertainty cannot be responsibly closed through drawings/calculation alone. It is not universally mandatory simply because a project contains luminaires.

## 3｜Trigger / applicability

Trigger Lighting Design when the project makes material claims about one or more of the following:

- visual task and visibility;
- spatial hierarchy, orientation, focal emphasis or darkness;
- atmosphere, character, material/surface appearance or art direction through light;
- daylight and electric-light integration;
- glare, veiling reflection or visual comfort;
- colour appearance, colour rendering or spectral characteristics;
- luminance / illuminance distribution;
- facade, exterior, landscape or night-time environmental lighting;
- lighting controls, scenes, occupancy/daylight response or user interaction;
- luminaire optical performance, mounting, shielding, integration or custom detail;
- lighting energy / power / controls intent;
- maintenance, access, cleaning, replacement or lifecycle claims;
- emergency-lighting interface where the Lighting designer is materially involved;
- mockup / sample / aiming / commissioning / field measurement;
- integrative/non-visual lighting claims;
- post-occupancy visual or operational performance.

Do **not** infer Lighting professional completion merely because:

- Architecture or Interior selected decorative fixtures;
- MEP/Electrical issued a luminaire circuit plan;
- a renderer produced a convincing image;
- a manufacturer produced a photometric file or datasheet;
- an illuminance simulation returned target values.

For promotion-relevant scope, `NOT_REQUIRED` must be explicit under the Current trigger/applicability contract. Omission is not `NOT_REQUIRED`.

## 5｜Cross-cutting Lighting control objects

### 5.1 Lighting Basis / Responsibility Matrix

Record:

- appointment/scope and exclusions;
- spaces/areas/states covered;
- actor/user groups and visual tasks;
- Architecture / Interior / Landscape / MEP / Electrical / Fire / Controls / AV / Theatre / Exhibition / FM boundaries;
- daylight responsibility;
- emergency-lighting responsibility;
- controls specification/programming/commissioning responsibility;
- mockup/aiming/site attendance responsibility;
- measurement/performance-verification responsibility;
- product procurement/supply responsibility where applicable.

### 5.2 Visual Task / Experience / Time-State Matrix

For each materially different space or scene preserve:

```text
SPACE / ZONE
→ USER / ACTIVITY / VISUAL TASK
→ TIME / DAYLIGHT STATE
→ DESIRED PERCEPTION / EXPERIENCE
→ BRIGHTNESS / DARKNESS HIERARCHY
→ ORIENTATION / FOCAL OBJECT
→ GLARE / REFLECTION RISK
→ COLOUR / MATERIAL CONSEQUENCE
→ CONTROL SCENE
→ SAFETY / ACCESSIBILITY INTERFACE
→ MAINTENANCE STATE
→ VALIDATION METHOD
```

### 5.3 Daylight–Electric Light Integration Register

Record:

- daylight apertures / orientation / shading / surface response;
- temporal daylight states;
- glare/view considerations;
- daylight-sensitive electric-light response;
- daylight-harvesting assumptions;
- manual override / user control;
- commissioning and seasonal verification needs.

Daylight evidence remains bounded to its model, weather, geometry and evaluation method.

### 5.4 Luminaire / Optical / Product Register

Preserve at minimum when material:

- unique luminaire/product/system ID;
- location / application / mounting;
- luminous distribution / optical accessory;
- lumen output / power / driver state;
- colour characteristics;
- glare/shielding/visibility concern;
- dimming/control protocol;
- emergency function if applicable;
- ingress/environmental constraints;
- serviceability / replacement / access;
- source revision / photometric file identity;
- approved sample/submittal/equivalent state;
- `does_not_prove`.

### 5.5 Lighting Controls / Scene Register

Controls must preserve intent through implementation:

```text
SCENE / MODE
→ TRIGGER / USER ACTION / SENSOR
→ TARGET GROUPS
→ LEVEL / CURVE / FADE / SEQUENCE
→ DAYLIGHT INTERACTION
→ OVERRIDE / FAILSAFE
→ INTERFACE TO BMS / AV / SHADING / OTHER SERVICES
→ COMMISSIONING TEST
→ ACTUAL READBACK
```

A gateway/controller state is not proof of actual emitted light at the space.

### 5.6 Mockup / Aiming / Benchmark Register

Material uncertainties may require:

- sample board / bench test;
- luminaire optical test;
- full-scale room/zone mockup;
- facade/exterior/night trial;
- detail/recess/trim/mounting mockup;
- control-scene prototype;
- aiming benchmark;
- material/colour under actual light test.

Record test conditions and what the mockup does not prove.

## 6｜Professional stages

## LGT-BASIS｜Scope / People / Place / Evidence Basis

**Professional question:** What must light enable, reveal, protect or avoid, for whom, where, when, and under what authority/evidence boundary?

Resolve:

- appointment and responsibility;
- project/space/use context;
- users and visual tasks;
- architecture/interior/landscape intent;
- daylight/site/night context;
- safety/accessibility/project-type constraints;
- existing lighting conditions for retrofit;
- applicable current standards/guidance;
- energy/sustainability/maintenance scope;
- integrative-lighting applicability if claimed;
- required surveys/measurements/mockups.

Native outputs:

- Lighting Basis / Scope / Responsibility Matrix;
- Visual Task / Experience / Time-State Matrix;
- existing-condition survey/readback where applicable;
- lighting Design Question / assumptions / open items;
- knowledge-mount refs.

Exit requires the lighting problem to be explicit. It does not require a luminaire family to be selected.

---

## LGT-CONCEPT｜Lighting Concept / Hierarchy / Experience

**Professional question:** What light-and-darkness logic generates the intended spatial perception and experience?

Develop alternatives for:

- daylight/electric-light relationship;
- brightness/luminance hierarchy;
- darkness and restraint;
- orientation / focal emphasis;
- vertical / horizontal / object / ambient / accent roles;
- surface/material/light interaction;
- colour character;
- transition and sequence;
- exterior/night-time character;
- broad controls/time states;
- maintenance/lifecycle consequences of the concept.

Required design readback should include more than a mood image. Depending on scope use sections, lighting diagrams, luminance/brightness studies, physical/digital experiments, spatial views and written design mechanism.

A concept may be visually strong while still holding technical/interface questions open.

---

## LGT-SCHEME｜Integrated Scheme / Photometric + Controls Strategy

**Professional question:** Can the concept become a coherent lighting system across spaces, time states, tasks and daylight conditions?

Resolve at appropriate maturity:

- lighting layers and zone hierarchy;
- indicative luminaire/optical families;
- daylight/electric integration;
- preliminary photometric evidence;
- glare/reflection risk;
- colour/rendering approach;
- preliminary controls topology/scenes;
- emergency-lighting interface;
- energy/power implications;
- exterior/night environmental impact where triggered;
- prototype/mockup needs;
- maintenance/access implications.

Native outputs may include lighting plans/sections, lighting intent diagrams, preliminary luminaire schedule, preliminary calculations, controls/scene matrix and interface register.

`PRELIMINARY CALCULATION PASS ≠ TECHNICAL DESIGN PASS`.

---

## LGT-COORDINATION｜Cross-Disciplinary Coordination

**Professional question:** Are lighting-controlled variables coordinated with the physical and operational systems that must carry them?

Material interfaces may include:

- Architecture: openings, volumes, sections, surfaces, facade, reflected geometry;
- Interior: ceiling systems, joinery, materials, furniture, display, sight lines;
- Landscape: paths, vegetation, ecology, public realm, darkness/night strategy;
- MEP/Electrical: supply, circuits, driver location, load, containment, access;
- Controls/BMS/AV/Shading: protocols, sensors, gateways, scenes, interfaces;
- Fire/Life Safety: emergency lighting and signage boundaries;
- Accessibility: visual accessibility and user controls;
- Envelope: daylight, shading, facade integration;
- Structures: mounting/support where material;
- Acoustics: integrated ceiling and fixture conflicts;
- Exhibition/Theatre/Specialist systems where triggered;
- FM/Operations: access, replacement, aiming and control ownership.

R-F remains the owner of actual interface maturity/disposition. Lighting only declares and consumes interface requirements.

## LGT-TECHNICAL｜Detailed Lighting Design

**Professional question:** Is the lighting intent technically specified, calculable, coordinated, serviceable and bounded by appropriate evidence?

Develop as applicable:

- exact luminaire/optical characteristics;
- mounting/integration detail;
- photometric model and calculation assumptions;
- illuminance/luminance/uniformity evidence;
- glare and reflected-glare evidence;
- colour rendering / chromaticity / spectral criteria where material;
- temporal-light-artifact/flicker considerations where material;
- controls points/groups/scenes/sequences;
- daylight response;
- energy/power / operating mode assumptions;
- emergency-lighting interfaces;
- night-time/exterior spill/obtrusive-light constraints;
- circularity/embodied/lifecycle requirements where triggered;
- access / heat / cleaning / replacement / aiming;
- mockup and commissioning requirements;
- measurement/performance-verification plan.

Native output may include coordinated plans, sections, details, schedule/specification, calculation model/report, control narrative/points/scenes, commissioning requirements and updated interface register.

Technical compliance evidence does not award design quality.

## LGT-PRODUCTION｜Tender / Submittal / Equivalent / Fabrication Support

**Professional question:** Does procurement/production preserve the approved lighting intent and technical boundary?

Review when appointed:

- luminaire schedules/specification;
- tender clarifications;
- proposed equivalents/substitutions;
- photometric files and driver/control changes;
- samples;
- shop/fabrication drawings;
- mounting/coordination details;
- mockup revisions;
- controls hardware/software substitutions;
- cost/value-engineering consequences;
- circularity/maintenance/replacement consequences.

Never approve by model number alone. A product substitution may reopen concept, photometry, glare, colour, detail, controls, energy, maintenance and commissioning scopes.

`EQUIVALENT LUMENS ≠ EQUIVALENT LIGHTING DESIGN`.

## LGT-CX｜Installation Readback / Commissioning / Aiming / Measurement / Handover

**Professional question:** Does the installed lighting system actually realise the bounded design intent and functional requirements?

Use current commissioning requirements. Where applicable verify:

- installation completeness and product revision;
- aiming/orientation;
- visual inspection;
- controls address/group/scene/function;
- sensor and daylight-response operation;
- interfaces to other services;
- emergency-lighting interface tests under proper authority;
- illuminance/luminance or other agreed measurements;
- colour/control state where specified;
- user/operator controls;
- O&M information;
- operator training;
- snag/defect closure;
- post-completion adjustments.

Actual readback is mandatory for closure at an installed-performance claim ceiling.

`CALCULATION ≠ COMMISSIONING MEASUREMENT`.

`CONTROLLER COMMAND ≠ LUMINAIRE OUTPUT READBACK`.

## LGT-INUSE｜Post-Occupancy / Maintenance / Performance Review

**Professional question:** Does lighting continue to support people, design intent and operation after occupation and across relevant time/maintenance states?

Review where applicable:

- occupant/operator feedback;
- visual task and comfort observations;
- actual scene/control usage;
- daylight response;
- night/exterior impact;
- energy data where valid and in scope;
- cleaning/maintenance/replacement;
- degradation/failure/driver/luminaire changes;
- aiming drift;
- changed room/use/furniture/display/material conditions;
- seasonal or operating-hour conditions;
- measured performance verification.

In-use evidence may trigger bounded reopen. It does not rewrite historical commissioning evidence.

## 7｜Special technical / evidence boundaries

### 7.1 Daylight

Daylight is integrated into Lighting Design where scope requires it, but daylight geometry/environmental evidence remains tied to its actual model, weather/climate input, time basis, shading state, surrounding obstruction and evaluation method.

`DAYLIGHT MODEL PASS ≠ FIELD DAYLIGHT TRUTH`.

### 7.2 Emergency lighting

Lighting Design may own or contribute to luminaire/layout/controls/commissioning tasks only within appointment and competence. Fire/life-safety strategy, statutory interpretation and approval stay with their proper owners.

`EMERGENCY LIGHTING DRAWING ≠ FIRE APPROVAL`.

### 7.3 Controls

DALI-2 or another protocol/system can be an implementation route. Protocol conformance/interoperability does not prove spatial lighting design, scene quality or actual commissioned output.

### 7.4 Integrative / non-visual lighting

Use the current SLL integrative-lighting position and current CIE/other applicable evidence. Separate:

```text
established visual-lighting requirements
≠ mature non-visual evidence
≠ emerging evidence
≠ marketing claim
```

Any circadian/wellbeing claim must state metric, measurement/evaluation method, exposure/time assumptions, evidence maturity, uncertainty and `does_not_prove`. Do not infer clinical or health outcomes from a lighting metric alone.

### 7.5 Colour / material appearance

Screen renders, RGB values and supplier photographs do not prove field colour/material appearance. Material/surface reflectance, gloss, texture, spectral power distribution, adaptation and surrounding contrast can materially change perception.

### 7.6 Exterior / night-time environment

Where triggered, address obtrusive light, ecology, neighbours, safety, orientation, facade/landscape intent, curfew/time-state and maintenance. Brightness is not a proxy for safety or quality.

## 11｜Change / stale / reopen

Reopen affected Lighting scope when material changes occur in:

- project brief / activity / visual task;
- Architecture / Interior / Landscape geometry or material;
- daylight opening/shading/site obstruction;
- luminaire / optic / driver / spectral/colour properties;
- controls hardware/software/grouping/scene logic;
- MEP/Electrical supply/interface;
- emergency-lighting/fire strategy interface;
- furniture/display/equipment/task location;
- budget/value-engineering substitution;
- mockup result;
- site condition or installation nonconformity;
- commissioning/measurement contradiction;
- operation/maintenance/use;
- applicable evidence/standard/authority.

Reopen only consumers of the changed relation at affected scope. Preserve unrelated valid work.

Where the professional action mutates multiple physical/control surfaces, Current multi-surface reconciliation rules apply. A known partial commit cannot support dependent handoff readiness or DAG advance.

Where recovery is needed, Current Observability/Recovery contract applies. Incident closure does not itself restore a professional PASS; it restores only the bounded relation proven by post-recovery readback.

## 12｜Completion / claim ceiling

A Lighting process instance may close only when:

- triggered stages have resolved their exit conditions or explicit bounded terminal disposition;
- consequential knowledge mounts are current;
- required native outputs exist;
- material interfaces have valid R-F state or allowed open disposition at claim ceiling;
- required professional review is recorded;
- required actual readback is present;
- commissioning/performance evidence exists when installed-performance claims are made;
- open items are explicit and compatible with the claim ceiling;
- current professional receipt is issued within actual authority.

Professional process closure does not prove:

```text
DESIGN_KEEP
INTEGRATION_PASS outside actual R-F state
FIRE / LIFE-SAFETY APPROVAL
ACCESSIBILITY APPROVAL
ELECTRICAL APPROVAL
FIELD_TRUTH beyond measured/read-back scope
HEALTH OUTCOME
STATUTORY APPROVAL
PROJECT_PROMOTION
UNIVERSAL_TRANSFERABILITY
```
