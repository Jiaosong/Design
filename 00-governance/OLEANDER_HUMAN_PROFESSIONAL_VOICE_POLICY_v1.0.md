# OLEANDER Human Professional Voice Policy v1.0

Status: CURRENT CROSS-PROJECT LANGUAGE CONSTRAINT
Role: extends existing anti-template / project-specificity / evidence-led presentation rules; it is not a new Skill, Method family, Gate family, or writing taxonomy.
Scope: all OLEANDER project-facing and knowledge-facing prose unless a machine-readable/status-token format is explicitly required.

## Purpose

Remove generic AI-like wording, report-template prose, synthetic marketing filler, and process narration from OLEANDER outputs. Public and professional-facing language must read as if it was written by a competent designer, researcher, engineer, curator, or project team who knows the specific object, site, material, behavior, evidence, and decision.

This policy governs language quality only. It must not alter Source Authority, evidence state, dimensions, rights, engineering boundaries, field truth, or design intent.

## 1. Where this applies

Apply this rule to:

- project introductions and project summaries;
- Web/UI visible copy, section titles, captions, navigation labels, calls to action and microcopy;
- exhibition boards, portfolios, decks, books and reports;
- architectural / landscape / product / brand design descriptions;
- analysis-diagram titles, labels and explanatory notes;
- brand/packaging/POP communication text;
- storyboard narration and motion captions;
- Notion Canonical Knowledge prose and METHOD explanations;
- README / handoff / PR prose intended for human understanding.

Machine-readable IDs, hashes, enum values, lifecycle tokens, validation receipts, CI names, file paths, exact status labels and Required Native Output fields may remain technical. Do not rewrite precise governance tokens merely to sound more natural.

## 2. Human Professional Voice standard

Prefer language that names the actual thing and the actual relationship.

Write:

`对象 / 动作 / 关系 / 条件 / 结果`

before:

`概念 / 氛围 / 方法名 / 宏大总结 / 自我解释`.

Good project language is usually specific enough that another project cannot reuse it unchanged.

Prefer:

- concrete nouns: platform, handrail, sponge layer, river bend, return path, mast, product head, interface state;
- observable verbs: folds, narrows, exposes, separates, drains, redirects, locks, opens, returns;
- explicit relations: above/below, before/after, near/far, inside/outside, user/object, route/return, body/material;
- bounded evidence: what is known, inferred, provisional, selected, rejected, or still open;
- project-specific terms only when they actually clarify the design.

## 3. AI-like / generic language to remove

A phrase is not banned merely because it appears below. Reject it when it substitutes for specific content.

High-risk patterns include:

- `本项目旨在……` / `本方案通过……` / `通过……实现……` repeated as the default sentence structure;
- `基于以上分析` / `综合来看` / `值得注意的是` / `可以看出` / `由此可见` when they add no information;
- `不仅……更……` / `从……到……` / `既……又……` used as formulaic rhetorical scaffolding;
- `打造 / 赋能 / 重塑 / 激活 / 链接 / 融合 / 共生 / 多维 / 沉浸式 / 场域 / 叙事 / 系统性 / 一体化 / 全方位` when the specific mechanism is not stated;
- abstract chains such as `形成独特的体验价值`、`构建多层次空间叙事`、`实现文化与自然的深度融合` without visible project evidence;
- repeated `Context / Tension / Insight / Proposition / System / Experience / Proof` or methodology labels exposed as public-facing copy when the project itself could be named instead;
- excessive explanation of the design process instead of describing the design result;
- generic inspirational conclusions, manifesto-like endings, motivational language, or self-congratulatory claims;
- symmetric paragraph structures that sound generated because every section uses the same rhetorical rhythm;
- noun stacking that hides agency: `体验系统构建逻辑优化策略` instead of stating what changes and why;
- faux precision: confident causal or evaluative claims that are not supported by evidence;
- conversational AI framing such as `我们可以看到`、`接下来我们将`、`下面将从几个方面`、`首先/其次/最后` when the artifact itself can carry the structure.

## 4. Project Specificity Swap Test

For any important public-facing paragraph, title set, or project introduction:

1. remove the project name, site name, brand name and unique proper nouns;
2. mentally substitute another unrelated project;
3. if the paragraph still sounds equally valid, mark `GENERIC / AI-LIKE = REVISE`;
4. rewrite using actual project objects, decisions, relations, materials, behaviors, evidence or consequences;
5. rerun the test.

A reusable design principle may remain generic inside METHOD / Knowledge, but project copy must not masquerade as a universal method paragraph.

## 5. Evidence-to-language rule

Language must not outrun evidence.

- FACT stays factual.
- INFERENCE states the relation being inferred.
- ASSUMPTION / DESIGN TEST remains visibly provisional.
- UNKNOWN / FIELD OPEN remains open.
- Decision language states what was selected, rejected or changed and on what basis.

Do not convert uncertainty into confident polished prose merely to make a page sound complete.

## 6. Design-writing rule

For public design work, prefer the designed object before the methodology.

Use:

`what the visitor/user/body/object encounters → what changes → why that relation matters`

rather than:

`our methodology → our framework → our system → our multidimensional strategy`.

A design page should not read like an analysis report explaining that design happened. It should let the design itself carry the argument, with text used only where it adds information the visual cannot.

## 7. Analysis-diagram language

Analysis graphics must avoid both AI-report prose and pseudo-academic inflation.

- headings name the actual variable or relation;
- labels stay short and spatial/behavioral;
- captions state the observation and design consequence directly;
- do not use abstract slogans as diagram labels;
- do not repeat the same sentence in title, callout and caption;
- visual evidence should carry hierarchy; prose does not compensate for a weak diagram.

Preferred pattern:

`OBSERVED RELATION → DESIGN CONSEQUENCE`

Example structure:

`回程入口与主游线重叠 → 高峰时段将返程提示前置到分叉前`

rather than:

`通过对游客行为路径的系统性分析，构建更高效、更具人性化的导览体验。`

## 8. Knowledge-base language

Notion Canonical Knowledge should use neutral expert prose, not chat-style explanation.

- define terms once;
- state source and scope;
- distinguish evidence from interpretation;
- avoid `你可以 / 我们可以 / 接下来 / 简单来说` unless a teaching note explicitly needs second-person instruction;
- remove duplicated summaries generated by prior conversations;
- preserve exact professional terminology when it is more precise than a friendly paraphrase;
- do not convert project-specific findings into universal claims through polished wording.

## 9. Technical / validation language

Validation and governance reports should be concise and factual.

Prefer:

`STEP reopened; bounding dimensions match 20×10×5 mm.`

not:

`通过本轮全面而系统的验证，我们成功证明了该模型在多维度技术链路中具备较高可靠性。`

Keep exact PASS / REVISE / HOLD and proof boundaries. Remove congratulatory language, process theatre and status inflation.

## 10. Editing procedure

For a material text object:

`SOURCE / CURRENT TEXT → FACT & DECISION LOCK → AI-LIKE RESIDUE SCAN → PROJECT SPECIFICITY SWAP TEST → CONCRETE REWRITE → READ ALOUD / PAGE READBACK → FACT CHECK → FINAL`

Do not rewrite everything into one house style. Preserve the appropriate voice of the medium:

- brand copy can be concise and expressive;
- architectural description can be spatial and material;
- research can be precise and evidence-led;
- technical writing can be terse;
- interface microcopy can be direct and behavioral.

The goal is not uniform tone. The goal is removal of generic synthetic language.

## 11. Review result

Public/project-facing language may receive:

- `KEEP` — specific, concise, professionally credible, consistent with evidence and medium;
- `REVISE` — contains generic/AI-like scaffolding, unnecessary methodology narration, duplicated claims, inflated abstraction, or weak project specificity;
- `REJECT` — wording materially distorts evidence, invents facts, hides uncertainty, or replaces the actual project with generic conceptual language.

Language review does not grant Design KEEP, Evidence PASS, Engineering PASS, Field PASS or publication rights.

## 12. Hard constraints

`POLISHED PROSE ≠ PROJECT-SPECIFIC PROSE`

`HUMAN-SOUNDING ≠ FACTUALLY VALID`

`METHOD LANGUAGE ≠ PROJECT LANGUAGE`

`AI ASSISTED DRAFT ≠ FINAL PROJECT VOICE`

`PUBLIC COPY MUST NOT EXPOSE INTERNAL PROCESS THEATRE`

`REMOVE AI-LIKE LANGUAGE WITHOUT REMOVING MATERIAL INFORMATION`

`NO COMPRESSION / NO LOSS` still applies: rewrite and restructure, but do not silently delete real design decisions, evidence boundaries or technical meaning just to make the text shorter.
