# OLEANDER Built-Environment Accessibility Professional Process v1.0

**Status:** CANDIDATE PROFESSIONAL DOMAIN PROCESS / CONTROLLED EVOLUTION INPUT  
**Domain:** Built-Environment Accessibility / Inclusive Access (ACC)  
**Authority position:** subordinate to `complex-project-master-runtime-v1.0.md`, `OLEANDER_CURRENT_ARCHITECTURE_MAP_v2.1`, `professional-domain-process-contract-v1.0.md`, Current Knowledge Authority, Shared Design Quality, Cross-Disciplinary Integration, applicable rights/legal authority, project jurisdiction and responsible accessibility/design professionals.  
**Professional basis:** ISO 21542:2021 is the current published second edition for accessibility and usability of the built environment; as of 2026-09 it is at ISO systematic-review stage 90.60, so this candidate treats it as the current published edition **under review**, not as a 2026 reconfirmed standard. Applicable jurisdictional law/codes, rights obligations and project evidence remain controlling.  
**Existing OLEANDER knowledge context:** `IDX-ACCESSIBILITY-INCLUSIVE-001` remains the L4 canonical index separating Digital Accessibility, Physical Accessibility, Rights & Accommodation and Inclusive Design. `IDX-ARCH-STRUCT-SAFETY-005` remains the Architecture life-safety routing owner. This professional process consumes those routes; it does not create a second Accessibility knowledge tree or absorb Digital Accessibility/WCAG authority.

## 1｜Why this process exists

Built-environment accessibility is not a dimension checklist and not equivalent to “wheelchair compliance”. Professional accessibility work must preserve a continuous relationship between rights and project duties, affected people and tasks, approach/entry/circulation/use/egress, sensory and information access, fixtures/equipment/controls, emergency use, reasonable accommodation, detailed implementation, representative task testing and actual field conditions.

Canonical professional chain:

```text
JURISDICTION / RIGHTS / APPOINTMENT / CLAIM BOUNDARY
→ PEOPLE / DISABILITY / CAPABILITY / TASK / CONTEXT
→ CONTINUOUS ACCESS & USE JOURNEY
→ SITE / ARRIVAL / ENTRY / CIRCULATION / VERTICAL MOVEMENT
→ SPACE / FIXTURE / EQUIPMENT / CONTROL USE
→ INFORMATION / WAYFINDING / SENSORY COMMUNICATION
→ EMERGENCY / FIRE-LIFE-SAFETY INTERFACES
→ CROSS-DISCIPLINARY COORDINATION
→ MOCKUP / REPRESENTATIVE TASK / SPECIALIST TEST WHEN MATERIAL
→ DOCUMENTATION / PROCUREMENT / SITE INSPECTION / READBACK
→ IN-USE ACCOMMODATION / SUPPORT / COMPLAINT / CHANGE RETURN
```

Hard boundaries:

```text
DIMENSION CHECKLIST ≠ ACCESSIBILITY PROFESSIONAL PASS
ONE ACCESSIBLE ROUTE SEGMENT ≠ CONTINUOUS ACCESS
WHEELCHAIR FIT ≠ ALL ACCESSIBILITY NEEDS
UNIVERSAL DESIGN PRINCIPLE ≠ STATUTORY COMPLIANCE
WCAG ≠ PHYSICAL-BUILT-ENVIRONMENT COMPLIANCE
AUTOMATED / DRAWING CHECK ≠ REAL TASK USABILITY
CODE MINIMUM ≠ INCLUSIVE USE FOR EVERY PERSON
ACCESSIBILITY PASS ≠ RIGHTS / ACCOMMODATION OBLIGATIONS EXHAUSTED
MODEL / SIMULATION ≠ FIELD CONDITION
ACC PROCESS PASS ≠ R-F INTEGRATION PASS
ACC PROCESS PASS ≠ DESIGN KEEP ≠ PROJECT PROMOTION
```

## 2｜Professional-source alignment and stage identity

ISO 21542:2021 addresses accessibility/usability of building access, circulation, normal egress, evacuation in fire and related site access features. It provides requirements/recommendations, not one universal professional stage sequence. Local laws, building regulations, civil-rights duties, reasonable-accommodation obligations and approval routes vary by jurisdiction.

OLEANDER therefore uses internal domain-native carriers:

```text
ACC-BASIS       Jurisdiction / rights / appointment / medium / claim boundary
ACC-CONTEXT     People / disability-capability / tasks / environments / accommodation needs
ACC-JOURNEY     Continuous site-arrival-entry-circulation-egress journey
ACC-USE         Space / furniture / fixture / equipment / reach-transfer-operation use
ACC-INFO        Wayfinding / visual-auditory-tactile information / communication
ACC-SYSTEM      Doors / lifts / controls / services / safety / emergency interfaces
ACC-COORD       Cross-disciplinary geometry / operation / rights coordination
ACC-TEST        Mockup / representative task / specialist or user test when material
ACC-DELIVERY    Documentation / procurement / installation / inspection / field readback
ACC-INUSE       Accommodation / support / feedback / complaint / change / post-occupancy return
```

These are **OLEANDER internal carriers**, not ISO stage IDs. They do not synchronize by number with Architecture `ADD-*`, Interior, HCD, FLS or other professional stages.

## 3｜Trigger / applicability

Trigger this built-environment Accessibility process when a project makes material claims about:

- public/user/staff access to site, buildings, facilities or physical products integrated into the environment;
- continuous accessible route or vertical circulation;
- accessible rooms, toilets, changing, bathing, seating, counters or service points;
- doors, gates, controls, handles, switches, intercoms or physical interfaces;
- transfer, approach, reach, manoeuvring or assisted-use requirements;
- visual, auditory, tactile or cognitive wayfinding/information in the built environment;
- accessible parking/drop-off/arrival or external approach tied to the facility;
- emergency egress/refuge/evacuation/communication interfaces;
- alteration/refurbishment constraints affecting accessibility;
- reasonable accommodation or project-specific access needs interacting with design;
- representative physical task testing / mockups / field inspection.

Digital UI accessibility remains routed to the existing Digital Accessibility owner unless a physical-digital interface is materially coupled.

## 4｜Rights / technical / experience separation

Every invocation must distinguish at least three layers:

1. **RIGHTS / DUTY / ACCOMMODATION** — applicable law, equality/disability rights, procurement/contract duties, reasonable accommodation, participation and complaint/feedback routes;
2. **TECHNICAL ACCESSIBILITY** — applicable building/accessibility requirements, drawings, dimensions, products, details, installation and inspection;
3. **REAL USE / INCLUSION** — whether representative people can actually complete relevant tasks under the declared context, including conditions not fully captured by minimum technical provisions.

These layers interact but are not interchangeable.

`TECHNICAL CHECK PASS ≠ ALL RIGHTS DUTIES CLOSED`.

`MINIMUM CODE COMPLIANCE ≠ UNIVERSAL USABILITY`.

`INCLUSIVE DESIGN METHOD ≠ STATUTORY STANDARD`.

## 6｜Cross-cutting Accessibility control objects

### 6.1 Accessibility Basis / Duty Register

Record:

- jurisdiction and applicable rights/statutory route;
- project type/use and affected spaces/services;
- appointed accessibility scope and exclusions;
- responsible professional/specialist/AHJ or reviewing owner;
- user groups/tasks and known accommodation needs;
- current SOURCE editions/status, including review/revision state;
- existing-building constraints where applicable;
- approval/verification route;
- open interpretations and claim ceiling.

### 6.2 Actor–Task–Barrier Register

For each material task preserve:

`ACTOR / CAPABILITY / DISABILITY / ASSISTIVE DEVICE → TASK → CONTEXT → BARRIER → CONSEQUENCE → REQUIREMENT / ACCOMMODATION → DESIGN RESPONSE → TEST / EVIDENCE → STATUS → REOPEN TRIGGER`.

Do not use disability labels as complete design specifications; the actual task/context remains necessary.

### 6.3 Continuous Journey Register

Track the whole journey rather than isolated dimensions:

`SITE BOUNDARY / TRANSPORT → DROP-OFF / PARKING → EXTERNAL PATH → ENTRY → SECURITY / RECEPTION → HORIZONTAL CIRCULATION → VERTICAL CIRCULATION → DESTINATION / FACILITY → AMENITIES → EXIT / EMERGENCY STATE → RETURN / SUPPORT`.

Any broken required segment can invalidate a continuous-access claim even if other segments pass.

### 6.4 Space / Fixture / Control Use Register

For material uses record approach, manoeuvre/transfer, reach, force/operation, clearances, posture, assistance, privacy/dignity, fixture/equipment interface, maintenance state and validation method.

### 6.5 Accessible Information / Wayfinding Register

Coordinate applicable:

- spatial orientation and decision points;
- visual contrast/legibility at the applicable source boundary;
- tactile/Braille/auditory information where required;
- alarms/emergency communication;
- signage height/location/obstruction;
- language/cognitive-load considerations;
- digital interfaces only through their own Digital Accessibility authority.

### 6.6 Accommodation / Exception Register

When a specific person/group requires an accommodation or when existing conditions constrain a standard route, record:

`DUTY / REQUEST → PERSON/TASK → STANDARD DESIGN STATE → BARRIER → PROPOSED ACCOMMODATION / ALTERNATIVE → AUTHORITY / CONSENT → EFFECT ON OTHERS / SAFETY → IMPLEMENTATION → REVIEW → STATUS`.

A project accommodation is not automatically a reusable universal accessibility rule.

## 7｜ACC-BASIS — Jurisdiction / Rights / Appointment Basis

**Professional question:** What accessibility claim is actually in scope, under which rights/statutory/professional route and for which physical environment and users?

Resolve jurisdiction, duties, building/use context, appointment, responsible reviewer, source editions/status, existing conditions, known user/accommodation needs and open authority questions.

**Native outputs:** Accessibility Basis/Duty Register; scope/authority map; current source register; initial Actor–Task–Barrier Register; open interpretation list.

**Does not prove:** accessibility compliance, continuous usable route, accommodation closure or field condition.

---

## 8｜ACC-CONTEXT — People / Tasks / Context / Barriers

**Professional question:** Who must use or is affected by the physical environment, to perform what tasks, with which capabilities/assistive devices and under what conditions?

Address mobility, reach/strength/dexterity, vision, hearing, cognition/communication, neurodiversity where relevant, fatigue/stamina, children/older people, carers/companions, temporary impairments and intersection with operational/security conditions without turning categories into stereotypes.

**Native outputs:** Actor–Task–Barrier Register; affected-person/task map; evidence gaps; accommodation triggers.

**Does not prove:** final dimensional requirement, universal representation or compliance.

---

## 9｜ACC-JOURNEY — Continuous Physical Access Journey

**Professional question:** Is there a continuous, legible and operable route through the full in-scope journey rather than isolated compliant fragments?

Coordinate site approach, drop-off/parking where applicable, external path, thresholds/entries, security, corridors, doors, ramps/changes in level, lifts/vertical circulation, destination access, amenities and exit/emergency interfaces.

**Native outputs:** continuous-access plans/sections; journey register; level/threshold/door/lift interface schedule; critical pinch list.

**Does not prove:** field installation, all user needs, fire-emergency strategy or statutory approval.

---

## 10｜ACC-USE — Space / Fixture / Equipment / Operation

**Professional question:** Can the required task actually be performed at the destination with appropriate approach, manoeuvre, transfer, reach, operation, privacy and assistance?

Apply to relevant sanitary/changing/bathing spaces, seating, work/service counters, kitchens, bedrooms, workplaces, equipment, storage, furniture, controls and other project-specific uses.

**Native outputs:** task-use plans/elevations/details; fixture/equipment interface register; clear-zone/transfer/operation diagrams; unresolved task risks.

**Does not prove:** every body/device configuration, supplier installation, field conformity or real-use success.

---

## 11｜ACC-INFO — Information / Wayfinding / Communication

**Professional question:** Can people identify, understand and act on the information required to navigate and use the physical environment?

Address applicable orientation, signage, room/door identification, visual/tactile/auditory information, alarms, queue/service communication and physical-digital touchpoints.

**Native outputs:** accessible wayfinding/information requirements; decision-point map; signage/interface schedule; emergency-information requirements.

**Boundary:** Digital UI implementation/conformance remains owned by Digital Accessibility when triggered.

---

## 12｜ACC-SYSTEM — Doors / Lifts / Controls / Safety / Emergency Interfaces

**Professional question:** Do building systems and controlled elements support accessible use in normal, degraded and emergency states?

Coordinate doors/gates, lifts/platforms, access/security, intercoms, call points/controls, sanitary/support systems, emergency communication, refuge/assisted evacuation and fire/life-safety interfaces.

**Native outputs:** system-interface requirements; operating-state/fail-state matrix; assisted-use/emergency interface register; test requirements.

**Does not prove:** FLS PASS, lift/electrical approval, product certification or integrated commissioning.

---

## 13｜ACC-COORD — Cross-disciplinary Coordination

**Professional question:** Are accessibility requirements preserved through Architecture, Interior, Landscape, Structure, MEP, FLS, Lighting, Wayfinding, Product/FF&E, Security and Operations interfaces?

Typical conflict attacks:

- accessible route vs drainage/levels/landscape;
- door clearance vs structure/MEP/security/fire rating;
- toilet/fixture use vs partitions/services/equipment;
- lift/refuge/egress vs FLS strategy;
- signage/contrast vs visual language/lighting;
- accessible control vs security/AV/BMS/equipment;
- maintained clear space vs furniture/operations/temporary use.

Actual interface maturity/disposition remains R-F-owned.

**Native outputs:** accessibility interface register; coordinated plans/sections/details; critical conflict log; downstream change requirements.

---

## 14｜ACC-TEST — Mockup / Representative Task / Specialist Test

**Applicability:** trigger when material uncertainty cannot responsibly close through drawings/source review alone.

Possible tests include:

- 1:1 room/fixture mockup;
- doorway/threshold/control operation;
- route traversal with relevant mobility/assistive-device conditions;
- wayfinding/information task;
- seating/transfer/reach task;
- representative user/specialist review;
- emergency-information or assisted-use scenario.

Record exact participant/equipment/task/context, mockup or installed configuration, limitations, failed cases and what the test does not prove.

`SIMULATION / DESIGNER TRY-OUT ≠ DISABLED-PERSON VALIDATION`.

---

## 15｜ACC-DELIVERY — Documentation / Procurement / Site Readback

**Professional question:** Has the accessibility intent survived details, product selection, substitutions, installation and actual site conditions?

Control:

- plans/sections/details/schedules;
- statutory/specialist submissions;
- product/equipment identity and operating characteristics;
- shop drawings/submittals;
- substitutions;
- inspection points;
- site dimensions/levels/clearances;
- door/control/fixture operation;
- signage/information installation;
- nonconformities and corrective work;
- as-built/open-item record.

**Native outputs:** accessibility documentation package; submittal/change review; site inspection/readback; task verification where triggered; closure/open-item register.

**Does not prove:** statutory approval, rights/accommodation closure or real-use success beyond tested scope.

---

## 16｜ACC-INUSE — Accommodation / Support / Feedback / Change

**Professional question:** Does the environment remain usable and rights-compatible through operation, furnishing, maintenance and changing users/tasks?

Read back furniture/temporary obstructions, door/control settings, lift/service outages, signage changes, maintenance, accommodation requests, complaints, support incidents, emergency events and user feedback.

Operational evidence may reopen design claims or form G9 candidates, but one accommodation/request/incident does not become universal reusable knowledge automatically.

**Native outputs:** in-use accessibility issue register; accommodation/change log; post-occupancy task evidence; reopen actions; G9 candidate inputs.

## 18｜Freshness / source-status rule

Accessibility sources are time- and jurisdiction-sensitive. Every consequential claim records source identity, edition/date, jurisdiction/applicability and review status.

For ISO 21542 specifically, the current published edition is `ISO 21542:2021`, but as of 2026-09 ISO reports stage `90.60` systematic review. Therefore:

- it may support current published international technical context;
- it must not be described as newly reconfirmed in 2026;
- a future revision/confirmation outcome is a source-change trigger;
- project compliance still resolves through applicable local law/code/AHJ/professional authority.

## 19｜Change / reopen contract

Material triggers include:

- jurisdiction/law/standard/rights interpretation change;
- user/task/accommodation basis change;
- site levels/routes/entries;
- room layout/furniture/equipment;
- doors/lifts/security/controls;
- FLS/emergency strategy;
- fixture/product substitution;
- wayfinding/information change;
- field dimensional/operational contradiction;
- failed task/user test;
- complaint/accommodation/incident evidence;
- source review/revision outcome.

Reopen only affected scope and dependent interfaces.

---

## 20｜Completion boundary

A bounded Accessibility Professional Process PASS states only that the declared physical accessibility professional scope has met its exact evidence and exit criteria.

It does not automatically prove:

- all rights/accommodation duties are exhausted;
- local statutory/building-control approval;
- Digital Accessibility/WCAG conformance;
- FLS or emergency-evacuation approval;
- every disabled person can use every feature without accommodation;
- field conditions outside readback evidence;
- R-F Integration PASS;
- Design KEEP;
- Current Knowledge promotion;
- Project Promotion.

`ACCESSIBILITY PROFESSIONAL PASS ≠ UNIVERSAL USABILITY ≠ RIGHTS CLOSE ≠ DESIGN KEEP ≠ PROMOTION`.
