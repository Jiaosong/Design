## 1｜Current Web narrative diagnosis

The current 13-system Web architecture successfully preserves the full design universe, but the **story is over-repeated**.

### 1.1 Journey is introduced three times
Current flow repeats the same orientation logic in:
- Hero: BOAT / CABLE / WALK / RETURN;
- Culture: another BOAT → CABLE → WALK → RETURN spine;
- Journey: ARRIVE / BOAT / CABLE / WALK / RECOVER / RETURN;
- Game Map: again explains how the route works.

The principle “culture enters at the right moment in the journey” is valid, but the **actual route explanation must have one primary owner**.

Decision:
- Hero = promise only;
- Culture = what is worth noticing/reading;
- Journey + Map = how the visit actually moves.

### 1.2 R06 / R13 are carrying too many chapter jobs
R06/R13 currently reappear across Culture, Thirteen Imprints, Scene Interaction, Audience, Technical and Motion.

Repetition is only valid when each occurrence proves a different thing.

Owner roles:
- Thirteen Imprints = object/library identity;
- Scene Interaction = actual experience/action logic;
- Audience = same-scene depth difference;
- Technical = how selected physical/spatial relation works;
- Motion = temporal continuity only.

Culture should not carry full R06/R13 scene deepening. It may use one short example only to prove that content changes what a visitor notices.

### 1.3 Memory currently closes too early
Current Web places `Memory` before `Technical`, `Motion`, and the final `Return` chapter.

This breaks the project’s intended closure:
`RETURN → RECOGNITION → RECORD → TAKE AWAY`.

Decision:
- Memory must move **after Return recognition**, or the two must become one final paired act.
- Technical proof must not interrupt the emotional/experience close after memory has already started.

### 1.4 Technical proof is required but should not become the narrative climax
Technical Proof remains an independent visible system. It is not appendix-only and must be near-readable.

But its story job is:
> “why this selected design can plausibly work to the current concept/technical boundary”

It does not answer:
- what Qingjiang is;
- how the visitor moves;
- what the visitor does;
- what the visitor remembers.

Therefore Technical belongs after the main experience/body design is understood and before the final Return/Memory closure, or as a clearly separated proof interlude.

### 1.5 Motion is synthesis, not a separate new concept
`ARRIVE → CROSS → OPEN → PASS → RETURN` should summarize the journey in time.

Motion must not introduce a second abstract story vocabulary and must not repeat contact-sheet logic. It should synthesize already-understood objects/scenes.

## 2｜Canonical Web story spine

This is an **editorial act sequence**, not a fixed chapter count. Web may split or merge beats according to finished-pixel quality.

### ACT 0｜HERO — WHAT IS THE PROMISE?
**Question:** Why should I care?

First read:
- real Qingjiang;
- `先游清江，再读清江。`

Only one sentence of system logic:
> The project does not add thirteen mandatory attractions. It organizes a real Qingjiang journey, then lets culture, observation, play, rest and memory appear where they belong.

Do not explain route modes, App screens or technical states here.

### ACT 1｜PLACE / CULTURE — WHAT IS WORTH READING?
**Question:** What does Qingjiang contain that is worth noticing and remembering?

Owner content:
- regional/local culture;
- place names/local stories;
- landscape knowledge;
- traditional landscape view as cultural interpretation;
- daily/local wisdom;
- memory language.

Primary carrier:
- one strong Culture Map / Content Constellation or Qingjiang-specific culture field;
- 1–2 concise scene examples.

Do not repeat the full BOAT/CABLE/WALK journey here.
Do not fully deepen R06 and R13 here.

Narrative handoff:
> Qingjiang has many things worth reading — but the visitor first needs to know how to move through it.

### ACT 2｜JOURNEY + MAP — HOW DO I ACTUALLY TRAVEL?
**Question:** How do I arrive, cross, walk, recover and return?

This act owns the route explanation.

Sequence:
`ARRIVE → BOAT / CABLE → WALK NETWORK → RECOVER / CHOOSE → RETURN`

Required visible relations:
- two banks;
- water / cable / walking scales;
- branch / loop network;
- service / rest / return;
- no-phone fallback;
- CLOSED / UNKNOWN fail-closed only as subordinate state evidence.

The Game Map is the designed carrier for this relation. It must not become a second route chapter after the route has already been explained.

Narrative handoff:
> Once the journey is clear, content can become optional rather than controlling.

### ACT 3｜READING SYSTEM — HOW DOES THE THIRTEEN-IMPRINT LAYER ENTER?
**Question:** What is the “Stone Book” system without turning the trip into 13 tasks?

Two independent systems remain visible but work as one narrative act:
1. **App / Digital designed outcome** — user-owned next delta; Web consumes but does not redesign it.
2. **R01–R13 complete content library** — optional, reorderable, skippable.

Public message:

- thirteen imprints own optional content;
- Service / Return remains always available;
- no 13/13 completion authority.

Do not present six equal App screens as the whole project story. The App is a primary designed outcome, but this act should show its role in the journey, not become a product tutorial.

Narrative handoff:
> The system only becomes meaningful when it behaves differently in different places.

### ACT 4｜SCENE EXPERIENCE — WHAT ACTUALLY HAPPENS HERE?
**Question:** At a specific Qingjiang scene, what does the visitor actually do and gain?

Use a small number of **differentiated scenes**, not repeated project summaries.

Recommended scene logic:

- R13: `BODY → PASS → EXIT → RETURN` — high-attention content withdrawal.

Each scene should answer:
`visitor situation → action → gain → physical/digital carrier → fallback`.

This act is the primary owner of R06/R13 experience logic. Other chapters should not re-explain the same scene sequence at equal depth.

These are **editorial responsibility changes**, not pixel edit instructions.

- Keep v1.7 principle: `culture enters after/with real experience`.
- Move the full `BOAT → CABLE → WALK → RETURN` diagram ownership out of Culture and into Journey + Map.

- Culture may retain one short place-name/local-story example.

- Memory object should foreshadow at most; full Memory belongs to the final close.

### MERGE Journey + Game Map narratively
Both systems stay visible, but they answer one question: **how do I travel?**

### KEEP App + Thirteen Imprints separate as design systems, pair as one story act
Do not delete either system.

### KEEP Audience after Scene
Audience only becomes legible after the user understands what a scene is. This order is correct.

### KEEP Physical after Audience
The body-support argument becomes stronger after attention/effort differences are established.

### MOVE Memory after Return
Current `Memory → Technical → Motion → Return` order is narratively reversed.
Preferred close:
`... Physical → Technical Proof → Motion Synthesis → Return → Memory`  
or one final combined `Return → Memory` act.
