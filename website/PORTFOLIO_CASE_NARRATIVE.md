# OLEANDER Portfolio Case Narrative Framework v0.1

## Purpose

项目页不是把 OLEANDER 内部方法阶段直接暴露给读者，而是把一个项目完整讲清楚：为什么存在、什么条件已知、真正的问题是什么、做过哪些关键选择、最后交付了什么、现实证据支持到哪里、哪些判断仍然开放。

内部方法继续使用：
`Read → Frame → Hypothesize → Vary → Construct → Attack → Test → Decide → Archive`

公开作品集不直接用这些 Operation 名称当章节标题。网页采用以下 Narrative Spine。

---

## Canonical Project Narrative｜9 sections

### 00｜Project Snapshot / First Reading
回答：这是什么项目？我做了什么？最终形成了什么？

必须包含：
- 项目名称 / 类型 / 时间；
- Role / Scope；
- 一句项目命题；
- 1 个主视觉 Presentation Crop；
- 2–4 个最有代表性的最终结果缩略视觉；
- 当前成熟度 / Evidence Boundary。

这一屏只建立判断，不解释全部过程。

### 01｜Brief & Constraints
回答：为什么会有这个项目？原始任务和不可变条件是什么？

对应内部：Project Charter / Governance Object。

公开内容：
- 原始任务 / 目标；
- 目标对象 / 使用者 / 利益相关者；
- 已知约束；
- Out-of-scope；
- 项目成功不能由什么简单替代指标证明。

避免：用最终方案反推 Brief。

### 02｜Existing State & Evidence
回答：设计开始前，真实世界已经是什么状态？什么证据改变了我的理解？

对应内部：READ / Existing-State Reading。

公开内容：
- 市场 / 场地 / 品牌 / 用户 / 材料 / 技术 / 历史证据；
- Existing State；
- Contradiction / Missing Evidence；
- 关键图片、图表、现状对照。

视觉要求：证据必须说明“它证明了什么”，不能只是 Moodboard。

### 03｜Decision Question
回答：最终我决定解决的到底是哪一个问题？

对应内部：FRAME。

公开内容：
- 1 个主要 Decision Question；
- Locked Variables；
- Open Variables；
- Failure Signs；
- Success / Exit Condition。

这一章应把前面的研究压缩为一句明确的设计判断，而不是继续堆资料。

### 04｜Hypothesis & Exploration
回答：我认为可能有效的方向是什么？我比较过什么？什么被否决？

对应内部：HYPOTHESIZE + VARY + Candidate Gate。

公开内容：
- 设计假设；
- 2–4 组真正有差异的方向 / Controlled Variants；
- 固定条件与变化变量；
- Rejected routes；
- 保留理由；
- Acceptable Corridor，而不是伪造“数学最优”。

视觉优先：比较图 / 变体 / 草模 / 小样 > 解释文字。

### 05｜Key Decisions & System
回答：保留方向如何从概念变成可重建的设计系统？

对应内部：CONSTRUCT + DECIDE。

公开内容：
- 3–5 个最关键的 Design Decisions；
- 生成规则 / 参数 / 网格 / 几何 / 色彩 / 材料 /空间 / 交互逻辑；
- 各决定之间的依赖；
- 哪些变量已锁定，哪些仍开放；
- 必要时展示 Before / After 或 Decision → Consequence。

不要把所有过程图都放入；只保留真正改变结果的决策。

### 06｜Final Outcome / Delivered State
回答：最后实际形成了什么？

对应 Case Evidence Model 的 DELIVERED STATE。

公开内容：
- 最终主视觉；
- 完整产品 / 空间 / 品牌 / CMF / 数字界面系统；
- 关键应用场景；
- Full Board / System Board；
- Detail Crop。

这是项目第二个视觉峰值。

必须区分“概念效果图”“原型”“正式交付”“已建成 / 已生产”。

### 07｜Validation, Attack & Outcome
回答：方案被怎样攻击和验证？现实结果到哪里？

对应内部：ATTACK + TEST；对应 Evidence Model 的 OBSERVED OUTCOME。

公开内容按事实状态分层：
- Tested / Observed；
- Simulated；
- Prototype only；
- Pending；
- Unknown。

允许展示：
- 用户 / 场景 / 浏览器 / 材料 / 光线 / 制造 / 印刷 / 结构 / 设备测试；
- 测试失败；
- 真实结果与原假设的差异；
- 如果没有真实测试，明确写 Test Planned / Not Run。

禁止：效果图 PASS → 设计 PASS。

### 08｜Trade-offs, Revision & Continuation
回答：这个项目改变了我的什么判断？付出了什么代价？下一步是什么？

对应内部：ARCHIVE + Change Management + G9 / CONTINUE。

公开内容：
- Initial Position → Revised Position；
- Trade-offs；
- Failure / Adaptation；
- 已知限制；
- Next Validation；
- Transfer Rule：什么可以迁移，什么不能直接迁移。

这一章不是“总结感想”，而是留下可继续的设计判断。

## WHY / HOW / PROOF Overlay

9 段叙事可以压缩为三大阅读幕：

### ACT I｜WHY
`00 Snapshot → 01 Brief → 02 Existing State → 03 Decision Question`

建立项目存在理由、真实条件与设计问题。

### ACT II｜HOW
`04 Hypothesis & Exploration → 05 Key Decisions & System → 06 Final Outcome`

展示设计如何通过比较与构造产生，而不是突然出现一个最终效果。

### ACT III｜PROOF
`07 Validation & Outcome → 08 Trade-offs / Revision / Continuation`

说明哪些真的成立，哪些只是提案，以及项目如何改变下一轮判断。

## Visual Hierarchy Contract

每个项目都遵循：

**大图 > 小图 > 可视化关系 / 图表 > 表格 > 文字**

但各章节的视觉职责不同：

- Snapshot：Presentation Crop / Hero；
- Evidence：证据图 / 图表；
- Exploration：对照组 / 变体；
- Decisions：系统图 / 关键局部；
- Outcome：最终大图 + Full Board；
- Validation：测试 / 对比 / 失败证据；
- Revision：简洁关系图或 Before → After。

一屏一个主要视觉中心。文字用于命名判断，不与图像争夺第一阅读。

## Crop Roles

### Presentation Crop
用于 Snapshot / 项目开场 / Section Break。允许明确裁剪，建立第一阅读。

### Editorial Crop
用于过程和关键决策。根据内容重新构图，不机械统一比例。

### Detail Crop
用于材料、CMF、字体、构造、导视、产品局部等明确局部判断。

### Full Board
完整设计板、分析板、系统板、证据板。不得为了视觉冲击而裁掉关键信息；必须可放大查看。

裁剪图不能替代 Full Board 的证据角色。

## Project-type Adaptation

### Brand / Space Project
Brief → Audience / Context → Positioning Question → Brand Hypothesis → Identity System → Touchpoints / CMF → Space / Experience → Validation → Revision

### Product / CMF Project
Brief → Existing Product / Trend / Material Evidence → CMF Decision Question → Concept Directions → Color / Material / Finish System → Process / Manufacturing Path → Final Series → Sample / Light / Durability Validation → Revision

### Research / Cultural Project
Source / Context → Relationship Break → Evidence → Research Question → Hypothesis / Competing Interpretations → Translation Decisions → Application / Prototype → Validation / Limits → Transfer Rule / Responsibility

---

## Anti-patterns

项目页不得退化为：
- READ / FRAME / FORM 等内部方法词的机械目录；
- 一张效果图 + 一段设计说明；
- Moodboard → Logo → Mockup；
- 研究资料长墙后突然出现最终方案；
- 只有成功路线，没有被否决方向；
- 把设计者 Claim 当作真实 Outcome；
- 把 Prototype 当作 Delivered / Built；
- 用大量文字弥补没有视觉证据的问题；
- 为统一网页比例破坏设计板和关键关系。

## Definition of a complete portfolio case

读者看完一个项目后必须能够回答：
1. 为什么做？
2. 面对什么真实条件？
3. 真正的问题是什么？
4. 设计假设是什么？
5. 比较和否决过什么？
6. 哪些关键决定形成最终系统？
7. 最后实际形成了什么？
8. 哪些结果已经被现实验证？
9. 哪些仍是假设 / 待验证？
10. 项目最终改变了什么设计判断？

如果其中任一项只能靠设计师口头补充，项目网页仍不算完整。
