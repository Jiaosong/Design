# OLEANDER Portfolio Case Narrative Framework v0.2

## Purpose

OLEANDER 项目页不采用一套统一章节模板覆盖全部设计类型。

内部项目仍统一服从：
- `Design Intelligence → Execution Runtime → Evidence & Governance`
- `Exploration Loop + Canonical Production Loop`
- `WHY → HOW → PROOF`
- `Read → Frame → Hypothesize → Vary → Construct → Attack → Test → Decide → Archive`

但这些是项目运行、认知操作与证据治理，不是公开作品集必须逐章暴露的页面目录。

**公开作品集采用：`Core Coverage Contract + Project Type Router + Hybrid Profile + Project-specific Editorial Sequence`。**

原则：
1. 先判断项目是什么类型，再决定如何讲；
2. 不同设计类型使用不同 Case Profile；
3. 混合项目只确定一个 Primary Profile，再叠加必要 Supporting Lens；
4. 不把两个完整 Profile 首尾相接；
5. 页面章节名称使用项目本身的语言，不显示内部 Router / Gate / Operation 术语；
6. 完整性由 Coverage Contract 检查，不由“是否凑齐固定 9 章”判断。

---

# 01｜Core Coverage Contract｜共同完整性契约

以下内容所有正式项目案例都必须能够回答，但**不规定页面顺序，也不要求各自独立成章**。

### A｜First Reading / Project Identity
- 这是什么项目；
- Role / Scope / Time / Type；
- 一句项目命题；
- 项目当前成熟度；
- 一个真实、具有代表性的第一阅读视觉。

### B｜Why / Brief / Boundary
- 为什么存在这个项目；
- 面向哪些主体与任务；
- 哪些条件不可变；
- 哪些问题不属于本项目可解决范围。

### C｜Evidence / Existing State
- 设计前真实状态是什么；
- 哪些事实、现场、用户、材料、技术、业务、历史或运行证据影响了判断；
- 哪些仍然是 Source Claim / Inference / Hypothesis / Unknown。

### D｜Decision Trace
- 真正决定过什么；
- 比较过什么；
- 为什么保留 / 否决；
- 哪些变量锁定，哪些仍开放。

### E｜Delivered / Proposed State
- 最后实际形成了什么；
- 区分 Concept / Visualized / Prototype / Delivered / Built / Produced / Shipped；
- 不能用表现图成熟度替代现实完成度。

### F｜Proof / Validation Boundary
- 哪些被真实测试、观察、制造、建造、运行或发布验证；
- 哪些只是模拟或原型；
- 哪些 Pending / Unknown；
- 什么证据出现后才能升级项目主张。

### G｜Revision / Continuation
- 项目改变了什么判断；
- 有什么 trade-off、失败或限制；
- 下一轮需要验证什么；
- 哪些规则可以迁移，哪些不能脱离当前条件复用。

> `A–G` 是 Coverage Checklist，不是统一的七章网页模板。

# 02｜Project Type Router｜项目类型路由

每个项目先判断 `Primary Profile`，必要时再声明 `Supporting Lens`。

可用 Primary Profiles：
1. `BRAND-STRATEGY`｜品牌战略
2. `VISUAL-IDENTITY`｜视觉识别 / 平面 / 传播
3. `PRODUCT`｜工业 / 产品设计
4. `CMF`｜Color / Material / Finish
5. `SPACE-ARCH`｜空间 / 建筑 / 室内 / 展陈
6. `SERVICE-EXPERIENCE`｜服务 / 体验
7. `DIGITAL-INTERACTION`｜网站 / App / 数字产品 / 交互
8. `RESEARCH-CULTURAL`｜研究 / 文化转译

可按项目需要增加 Supporting Lenses：
- `DATA-VIS`｜数据 / 信息可视化
- `MOTION`｜动效 / 时间行为
- `DESIGN-LANGUAGE`｜跨产品 / 跨触点设计语言
- `GOVERNANCE`｜品牌 / 系统 / 内容治理
- `SPATIAL` / `CMF` / `SERVICE` / `VISUAL` 等跨领域辅助镜头

### Router Rule
- 一个项目只设 **1 个 Primary Profile**；
- Supporting Lens 通常不超过 2 个；
- Supporting Lens 只在相关章节插入必要证据与决策，不复制完整流程；
- 若两个领域同等决定项目成败，应重新判断项目是不是一个上位 Program 下的两个 Workstream，而不是把网页无限拉长。

# 03｜BRAND-STRATEGY Profile｜品牌战略

品牌项目不能从 Logo 或 Moodboard 开始。核心要讲清品牌为什么需要改变、真实供给能承诺什么，以及身份如何晚于主张形成。

### 推荐公开叙事
`First Reading → Business Problem / Actors → Offer & Alternatives → Evidence & Value → Positioning Choice / Trade-off → Brand Architecture → Identity / Narrative Translation → Experience / Touchpoints → Measurement / Failure → Governance / Revision`

### 必须回答
- Business Problem 是什么；
- 谁购买、使用、影响、运营或被品牌影响；
- 真实 Offer 是什么；
- Alternative 包括哪些不购买 / 跨品类替代；
- Distinct Value 由什么证据支持；
- Position 主动放弃什么；
- Brand Architecture 如何处理背书、独立、扩展、退出；
- 品牌承诺如何在产品、包装、网站、空间、服务、售后等触点中被履行或破坏；
- 哪些指标只是一种 proxy，不能独立证明品牌有效。

### 视觉重点
真实触点 / 产品 / 空间 / 使用状态 > Identity System > Position / Architecture Diagram > 指标图表 > 文字。

### 禁止退化
`Moodboard → Logo → VI Mockup → Brand Story`。

---

# 04｜VISUAL-IDENTITY Profile｜视觉识别 / 平面 / 传播

视觉项目的核心不是“做了一套好看的图形”，而是内容、主体、媒介与层级如何被组织成跨触点可识别、可生产、可维护的视觉关系。

### 推荐公开叙事
`First Reading → Communication Brief / Content → Audience / Medium / Context → Information & Meaning Hierarchy → Visual Principle / Relation Grammar → Controlled Routes / Rejected Routes → Identity System → Cross-media Applications → Production / Accessibility / Recognition Test → Version / Revision`

### 关键内容
- 第一阅读单元是什么；
- 什么信息必须先被读到；
- 哪些关系稳定，哪些变量可变；
- 标志、字体、色彩、图形、图像、版式、动效分别承担什么角色；
- 为什么某条视觉路线被否决；
- 不同媒介 / 尺寸 / 语言 / 响应式条件下哪些规则必须变化；
- 印刷、屏幕、字体授权、对比、可访问性等生产现实是否验证。

### 视觉重点
应用中的真实视觉 > 核心系统关系 > 路线比较 > 细节 / Production Evidence > 规范文字。

---

# 05｜PRODUCT Profile｜工业 / 产品设计

产品设计重点是任务、人体、功能、结构、部件、操作、制造与产品语言共同形成一个可用、可生产的对象。公开叙事不应只剩外观演化。

### 推荐公开叙事
`First Reading → User / Task / Context → Product Baseline & Constraints → Product Decision Question → Functional / Structural Concepts → Form / Ergonomics / Interaction Variants → Product Architecture & Key Interfaces → Material / CMF / Manufacturing Integration → Prototype → Use / Engineering / Assembly / Durability Validation → Final Product / Family → Revision`

### 关键内容
- 主体执行什么任务；
- 产品现状中真正的 failure / friction 是什么；
- 功能、安全、尺寸、受力、人体、成本、制造、法规等硬约束；
- 关键结构和操作语义如何形成；
- Stable Relation / Controlled Variable / Context-specific Exception；
- 部件—整体、连接、拆装、维护接口；
- 样件 / 人体 / 制造 / 装配 / 耐久验证到什么程度。

### 视觉重点
真实产品 / Prototype > Exploded / Functional / Interaction Visual > 结构与人体图 > CMF / Detail > 工程表格。

### 注
此 Profile 是 OLEANDER Project Runtime + Design Language Method + 产品现实验证要求的作品集转译，不新增一套独立产品开发方法。

---

# 06｜CMF Profile｜Color / Material / Finish

CMF 案例必须区别“灵感 / 感知研究”“数字方向”“完整 CMF System”“实体与量产证据”。趋势和 Moodboard 不能直接跳到最终综合色。

### 推荐公开叙事
`First Reading / Final Glimpse → Product / Strategy / Constraints → Evidence → Research Question → Visual & Material Research → Perception Model / Variable Space → Territory Hypotheses → Role Grammar / SKU / Geometry Translation → Controlled Digital Study → Complete CMF System → Material / Process Path → Physical Sample / Specification / Prototype → Sensory / Reliability Validation → Final Series → Production Boundary / G9`

### 核心内容
- 产品定位、用户任务、环境、结构、材料/BOM与制造边界；
- Real / Technical / Exploratory / Unknown Evidence；
- `Reference → Visual Cue → CMF Variable → Hypothesis`；
- 色彩、材料、Finish、Texture、反射、透明度如何成为变量；
- 不同 SKU / 几何如何翻译同一综合色语言；
- Evidence Render / Design Review Render / Presentation Render 分工；
- Material / Process Longlist、样片、规格、工程样机、可靠性、金样 / 限度样是否真实存在。

### 视觉重点
真实产品 / 材料 / 光照状态 > Controlled Comparison > Physical Sample > CMF System Board > Process / Specification。

### 成熟度硬规则
研究完整、Render PASS、视觉系列完整，都不能自动写成“专业 CMF 方案完成”。

---

# 07｜SPACE-ARCH Profile｜空间 / 建筑 / 室内 / 展陈

空间项目以场地和现实关系为基础；造型、流线、结构、环境、机电、材料、消防、无障碍、成本与运营不能在最后补入。

### 推荐公开叙事
`First Spatial Reading → Project Value / Boundary → Site / Existing Evidence → Actors / Actions / Relation Problem → Spatial Strategy & Alternatives → Plan / Section / Sequence / Scale → Structure / Environment / Material / Technical Integration → Key Nodes / Prototype / Constructability → Delivered / Built State → Actual Use / Maintenance / G9 → Revision`

### 核心内容
- 为什么项目值得发生；
- 场地、历史、气候、使用、结构、设备、材料和法规证据；
- Existing / Broken / Intended Relation；
- 主体—动作—对象—情境；
- 总图、邻接、流线、边界、空间层级与时间序列；
- 平面 / 剖面必须解释空间判断，不作为制图展示；
- 结构、环境、消防、无障碍、机电、成本、建造与运营的关键 trade-off；
- 1:1 节点、样板、施工、建成质量、真实使用和维护证据。

### 视觉重点
空间体验大图 / Section-Perspective > Plan / Section / Site Evidence > 关键构造 / Material Node > 性能 / 运营证据。

### 边界
概念空间项目不能借用完整建筑 Profile 暗示“已建成 / 已验证”；只展示实际完成到的层级。

---

# 08｜SERVICE-EXPERIENCE Profile｜服务 / 体验

服务设计不是“画用户旅程”。重点是主体任务、前台接触、后台能力、责任、失败与恢复是否形成可持续运行的系统。

### 推荐公开叙事
`First Experience / Service Proposition → Actors / Goals / Triggers → Journey Evidence / Existing Failure → Service Decision Question → Frontstage / Backstage / Support / Capacity Design → Touchpoint / Space / Interface Prototype → Failure Injection / Recovery → Rights / Accessibility / Responsibility → Operations / Outcome Evidence → Revision`

### 核心内容
- 不同 Actor 的目标与权力差异；
- Trigger / Journey State / Touchpoint；
- 前台和后台依赖；
- 人员、库存、设备、权限、数据、供应和峰值容量；
- Failure / Recovery：Detect / Inform / Recover / Escalate / Compensate / Learn；
- 可访问性、隐私、退出权；
- 服务原型与真实运营证据。

### 视觉重点
真实旅程 / 场景 / 触点 > Journey / Blueprint > Failure-Recovery Diagram > Capacity / Operations Evidence > 文字。

### 禁止退化
一条理想用户旅程 + 一张漂亮 Service Blueprint。

---

# 09｜DIGITAL-INTERACTION Profile｜网站 / App / 数字产品 / 交互

数字项目首先是主体完成任务的信息与状态系统，然后才是 UI 风格。

### 推荐公开叙事
`First Product State → Actor / Task / Context → Content Object / Existing IA → Core Task / Decision Question → Information Architecture / Retrieval → User Flow / State Model → Interaction & Interface System → Responsive / Visual Hierarchy → Prototype → Usability / Accessibility / Browser / Device Failure Test → Shipped / Current State → Feedback / Revision`

### 核心内容
- Content Object / Actor / Task / Relation / Metadata；
- Taxonomy、Ontology / Relation、Navigation / Retrieval 分开说明；
- Entry、Search / Filter、State、Permission、Recovery；
- 关键 Flow 及异常状态；
- 页面和组件如何支持任务，不从 Design System 开始倒推产品；
- 响应式层级、顺序、裁剪和交互在不同断点如何变化；
- 可用性、键盘、辅助技术、错误恢复、浏览器 / 设备测试；
- 若已上线，再展示真实行为 / 反馈；若未上线则明确 Prototype Boundary。

### 视觉重点
真实界面状态 / Task Flow > Interaction Sequence > IA / State Diagram > Component / Design System > Test Evidence。

---

# 10｜RESEARCH-CULTURAL Profile｜研究 / 文化转译

研究型文化项目不以“最终视觉”证明研究成立。必须保留来源、主体、解释权、竞争解释、转译边界和责任。

### 推荐公开叙事
`Source / First Context → Provenance / Actors / Rights → Existing Relation → Break / Contradiction → Evidence States → Research Question → Competing Interpretations / Hypotheses → Translation Logic / Do-not-copy Boundary → Application / Prototype → Participation / Reality Test → Limits / Responsibility → Transfer Rule / Revision`

### 核心内容
- 来源对象与历史 / 当代语境；
- 谁拥有、制作、使用、解释、维护；
- Fact / Source Claim / Inference / Hypothesis / Unknown；
- 原有关系、当前断点、目标关系；
- 至少保留竞争解释，避免单因果故事；
- 转译的是机制 / 关系还是表面符号；
- 哪些形式明确禁止复制；
- 参与、使用、文化影响是否有真实主体证据；
- 权利、解释、归属、维护和撤回责任；
- Transfer Rule 必须说明适用边界。

### 视觉重点
真实来源 / 场所 / 行为证据 > Relation / Translation Diagram > Prototype / Application > Final visual expression。

---

# 11｜Supporting Lens Profiles｜辅助镜头

这些不独立主导项目时，只插入 Primary Profile 的相关节点。

### DATA-VIS
`Question → Data / Evidence State → Semantic Model → Encoding Alternatives → Visual Hierarchy → Interaction / Uncertainty → Validation → Final View / Limit`

### MOTION
`State Change / Task → Motion Purpose → Temporal / Spatial Variables → Controlled Variants → Motion Grammar → Target-device Prototype → Performance / Reduced-motion / Comprehension Test → Final State`

### DESIGN-LANGUAGE
`Value / Task → Current Audit → Relation Extraction → Stable / Variable Split → Rule Candidates → Controlled Variants → Cross-object Attack → Reality Test → Version / G9`

---

# 12｜Hybrid Project Rule｜混合项目

混合项目不把多个流程全部展示。

### 规则
1. 先判断哪个设计对象承担项目主要价值与最终判断，作为 Primary Profile；
2. Supporting Lens 只在真正改变结果的位置插入；
3. 若某 Lens 只是表现手段，不升级为项目类型；
4. 同一个视觉证据可以服务多个判断，但必须明确它在当前段落证明什么；
5. 页面章节标题根据项目内容命名，不显示“Brand Strategy / CMF Stage 03 / Architecture G4”等后台术语。

### 当前 OLEANDER 三个案例路由

#### C02｜忘也 Daylily
**Primary：BRAND-STRATEGY / SERVICE-EXPERIENCE 之间以品牌体验为主。**
Supporting：`VISUAL-IDENTITY + SPATIAL + CMF`

建议公开主线：
`First Experience → Urban Rest Problem / Audience → Evidence & Positioning → Brand Proposition → Experience Path → Identity System → Touchpoints / CMF → Space as Experience → Integrated Outcome → Validation Boundary → Next Test`

Daylily 是品牌 / 体验 / 空间概念项目，不按完整建筑 Gate 叙事，也不把空间概念图写成建成证据。

#### C03｜The Light Collection / Reno CMF
**Primary：CMF。**
Supporting：`PRODUCT + DESIGN-LANGUAGE / VISUAL-EVIDENCE`

建议公开主线：
`Final Series Glimpse → Product / Constraint → Existing CMF & Trend Evidence → Light / Material Research → CMF Decision Question → Variable Space / Territories → Color / Material / Finish System → Geometry / SKU Translation → Process Intent → Final Series → Sample / Reliability Boundary → Next Physical Validation`

当前项目若仍为 Visualized / Sample Test Pending，则在实体样片、规格、工程样机、可靠性、Pilot 之前明确停止，不补写未执行阶段。

#### C01｜一脉广渡
**Primary：RESEARCH-CULTURAL。**
Supporting：`BRAND-STRATEGY + SERVICE / EXPERIENCE`

建议公开主线：
`Source Context → Making / Use / Memory → Relationship Break → Evidence → Research Question → Competing Interpretation → Translation Rule → Identity / Packaging / Space / Participation Prototype → Validation Limit → Responsibility / Transfer Rule → Revision`

C01 没有与 C02/C03 对等的真实成果照片时，不伪造项目 Hero；允许来源证据、关系图或真实原型成为第一视觉。

# 13｜Visual Hierarchy Contract

所有 Profile 继续遵循：

**大图 > 小图 > 可视化关系 / 图表 > 表格 > 文字**

但“大图”必须对应当前设计类型的主要证据：
- Brand：真实触点 / 体验；
- Visual：跨媒介应用；
- Product：真实产品 / Prototype；
- CMF：产品 + 材料 + 光照状态；
- Space：空间 / 剖面关系；
- Service：真实场景 / 触点；
- Digital：真实界面状态 / 任务；
- Research：来源 / 场所 / 行为证据。

若缺少真实视觉证据，不得用 AI 生成图、Mockup 或效果图冒充；提升下一种有效媒介的阅读优先级。

一屏一个主要视觉中心。文字负责命名判断、说明证据边界与必要解释，不与视觉对象等权竞争。

---

# 14｜Crop Roles

### Presentation Crop
项目开场 / Section Break。允许明确裁剪，制造第一阅读。

### Editorial Crop
按叙事问题重新构图，用于过程、比较、决策和应用。

### Detail Crop
材料、CMF、字体、结构、导视、产品局部等明确局部判断。

### Full Board
完整设计板、分析板、系统板、证据板。不得裁掉关键信息，必须可放大查看。

**裁剪图负责阅读；Full Board 负责完整证据。两者不能相互替代。**

---

# 15｜Anti-patterns

不得出现：
- 所有项目固定同一组 00–08 章节；
- 把 `READ / FRAME / FORM` 等内部 Operations 当公开目录；
- 品牌项目从 Logo 开始；
- 产品项目只讲造型；
- CMF 项目用 Moodboard 直接证明最终综合色；
- 建筑 / 空间概念项目暗示已建成；
- 服务项目只画理想 Journey；
- 数字项目先展示 Design System、后补用户任务；
- 文化项目用视觉转译覆盖来源、主体与权利；
- 只有成功路线，没有被否决方向；
- 把设计者 Claim 当 Outcome；
- 用大量文字补偿没有视觉 / 现实证据；
- 为统一网页模板破坏项目自己的设计逻辑。

---

# 16｜Definition of a complete portfolio case

“完整”不再意味着使用同一章节数，而意味着：

1. 项目类型与 Primary Profile 正确；
2. 读者能理解为什么做、为谁做、受什么约束；
3. 关键证据与真正 Decision Question 可追溯；
4. 项目特有的设计机制被讲清，而不是只看最终图；
5. 关键比较、否决和取舍被保留；
6. Final / Delivered State 与概念、原型、建成、量产状态不混淆；
7. Validation Boundary 清楚；
8. 失败、限制、责任和下一步存在；
9. 视觉叙事与项目类型一致；
10. 如果设计师离开页面，读者仍能理解项目为何形成现在的结果。

如果某个项目必须套统一模板才能被讲清，说明 Portfolio Framework 仍然覆盖了项目本身，而不是服务项目。
