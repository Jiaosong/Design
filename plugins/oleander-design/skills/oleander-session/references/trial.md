# Practical first-use trial

The aim is to test the plugin's **visible design behavior**. This guide refines the existing execution guide; it does not create a second project process, state store or authority.

1. Select a real, bounded question from the user's supplied current material. With no project object, use an isolated fixture from the existing OLEANDER Design Surface requirement: how to show genuinely different directions and enable select / modify / mix / reject / reopen while folding governance behind the design. Label the fixture as a test, not Project Current.
2. State the source, one comparison question, critical unknowns and the claim ceiling in one short paragraph. Do not require a task ID for a fresh fixture. Check current authority for production mutations; missing authority blocks that side effect, not local exploration.
3. Propose two or more **causally distinct** directions. Explain the difference in ordinary design language; reject cosmetic variants and preserve a useful wildcard. Avoid giving both directions the same cards with different colors.
4. Make the smallest editable domain-native artifact: an interface with actual states and controls, spatial geometry with measured/inferred bounds distinguished, or a product assembly/use/service sketch with editable parts. Keep text editable or vector. Do not substitute an AI image for this object.
5. Inspect the actual object. For an interface, exercise at least one interaction and one narrow/mobile state if a runtime is available; if visual or interactive runtime is absent, say precisely which checks remain untested. For space/product, inspect geometry/assembly at the fidelity actually made. Repair an observed defect before handoff.
6. Show the design first: working object, two material differences, strongest failure risk for each, and a concrete human steering action. Put authority/receipt details in a compact expandable or final trace section when needed. Never report human steering or a second-round artifact until the user actually responds.
7. Distinguish `plugin loads`, `source resolves`, `native artifact exists`, `actual readback`, `human steer changed round 2`, `cross-domain use`, and `full-flow completion`. A PASS on one does not imply the next. Record the observed behavior and modify the existing Skill or plugin candidate through normal review if it repeats.

If a user says the result feels wrong without naming the reason, treat that as genuine negative feedback but do not invent their preference. Offer sufficiently different work to make the next judgment concrete.
